# Interview: 1인 사용자용 스케줄 관리 칸반보드

> 작성일: 2026-11-03 · 깊이: standard · 라운드: 8
> 사전 자료: docs/02-research/01-overview.md, docs/02-research/05-sources.md
> 상태: 확정
> 확정 라운드: 8

## 요약

- 문제: 개발 버그와 할 일을 한곳에서 관리할 도구가 지금 없다 (R1)
- 사용자: 본인 1명, 내 PC 한 대에서 사용
- 핵심 가치: 이슈 등록부터 해결까지의 카드를 상태별로 한 화면에서 보고, 캘린더로도 본다
- MVP 범위: 카드 생성, 상태 변경(할 일 → 진행 중 → 완료), 캘린더 보기가 필수. 제외한 항목은 없다

## 문제와 배경

- 이슈나 할 일을 관리하는 도구가 지금은 없어서 직접 만들려 한다. [U] R1
- 기존 도구를 안 쓰는 이유나 불편했던 사례는 듣지 못했다. 열린 질문 Q-001로 남긴다. R1
- 조사에서 확인한 사실: 개인용 칸반 도구는 범용 SaaS(Trello 등), 셀프호스팅(Planka, Vikunja), 오프라인 개인용(Kanri)으로 나뉜다. 대부분 벤더 글이라 순위는 신뢰하기 어렵다. [조사] docs/02-research/01-overview.md
- 해결 대상에는 개발 버그와 일반 할 일이 모두 포함된다. [U] R2

## 사용자

| 구분 | 설명 | 사용 맥락 | 출처 |
|------|------|-----------|------|
| 주 사용자 | 본인 1명. 개발 버그와 할 일을 모두 다룬다 | 내 PC 한 대에서 사용, 인터넷 없이도 동작해야 한다 | [U] R2, R5 |
| 부 사용자 | 없음 | 계정·공유 기능 없음 | [S] R5 |

## 핵심 시나리오

### SC-001 카드 등록부터 해결까지
- 상황: 개발 버그나 할 일 하나가 생겨 본인이 보드에서 관리하려 한다
- 행동: 1) 카드를 만들고 종류(버그/할 일), 상세 설명, 마감일, 우선순위를 적는다 2) 카드의 상태를 할 일 → 진행 중 → 완료로 바꾼다 3) 진행 중에 생긴 추가 이슈와 검토사항을 카드의 기록으로 남긴다 4) 상태별 보드와 캘린더로 전체 진행 상황을 본다 5) 완료된 카드는 보관한다
- 기대 결과: 해야 할 일이 전부 보드에 모여 있고, 카드마다 진행 과정이 남아 있다
- 예외: 미확인
- 출처: [U] R2, R4, [S] R3, R7

- 우선순위는 후보다. 사용자가 직접 Must로 꼽은 것은 카드 생성, 상태 변경, 캘린더 보기 세 가지(R6)이고 나머지는 사용자가 순위를 말하지 않았다. 나머지 우선순위는 PRD 단계에서 정한다. RC-003과 RC-006, RC-011은 위 세 가지가 성립하려면 필요해 Must 후보로 둔다.

## 범위

- **MVP 포함**: 카드 생성, 상태 변경, 캘린더 보기 (사용자가 꼽은 필수 세 가지, R6). 카드 항목(상세 설명, 마감일, 우선순위, 메모), 카드별 진행 기록, 완료 카드 보관, 카드 수정·삭제, 마감 알림, 검색·필터도 요구로 받았지만 우선순위는 PRD에서 정한다
- **이번에 하지 않음**: 정해진 제외 항목은 없다 [U] R6. 단, 백업·내보내기는 기각했다 (D-009), 여러 기기 동기화와 모바일은 하지 않는다 (D-004)
- **나중에**: 해당 없음 (사용자가 나중으로 미룬 항목을 말하지 않았다)

## 성공 기준

해야 할 일이 메모나 머릿속에 없고 전부 보드에 모여 있는 상태 (D-007). 수치 기준은 정해지지 않음.

## 결정 사항

| ID | 결정 | 이유 | 기각한 대안과 사유 | 출처 | 근거 |
|----|------|------|-------------------|:----:|------|
| D-001 | 상태는 할 일 → 진행 중 → 완료 3단계로 한다 | 칸이 적어 한 화면에 들어오고 가장 단순하다 | 4~5단계, 사용자가 칸을 직접 편집: 선택하지 않음 | [S] | R3 |
| D-002 | 개발 버그와 할 일은 같은 카드에 종류 표시만 다르게 한다 | 화면과 입력이 단순하다 | 종류별로 입력 항목이 다른 카드, 구분 안 함: 선택하지 않음 | [S] | R3 |
| D-003 | 날짜는 마감일 표시에 그치지 않고 캘린더 보기까지 포함한다 | 스케줄 관리를 날짜로도 봐야 한다 | 마감일 표시만, 날짜 없음: 선택하지 않음 | [S] | R4 |
| D-004 | 사용 기기는 내 PC 한 대로 한다. 여러 기기 동기화와 모바일은 하지 않는다 | 서버·계정 없이 가장 단순한 구조 | PC 여러 대, PC+휴대폰: 선택하지 않음 | [S] | R5 |
| D-005 | 데이터는 내 PC에만 저장하고 인터넷 없이 동작한다 | 서버·운영 비용이 없다 | 서버 저장·온라인 전제: 선택하지 않음 | [S] | R5 |
| D-006 | 1차 버전에서 일부러 제외하는 항목은 없다 | 사용자가 제외를 말하지 않았다 | 해당 없음 | [U] | R6 |
| D-007 | 성공 기준은 해야 할 일이 전부 보드에 모여 있는 상태다 | 사용자가 고른 기준 | 매일 열어서 쓴다, 마감을 덜 놓친다, 정하지 않음: 선택하지 않음 | [S] | R7 |
| D-008 | 완료 카드는 보관(숨김) 처리하고 필요할 때 찾아본다 | 완료 카드가 쌓여도 보드가 복잡해지지 않는다 | 완료 칸에 계속 남김, 삭제만 가능: 선택하지 않음 | [S] | R7 |
| D-009 | 데이터 백업·내보내기 기능은 넣지 않는다. PC 고장 시 데이터 유실은 감수한다 | 사용자가 기각했다 (이유는 말하지 않음) | 파일로 내보내고 불러오기: 기각 | [S] | R8 |

## 조사 필요 항목

- 웹(브라우저 저장소)과 Electron 중 어느 쪽이 "내 PC 한 대, 로컬 저장, 오프라인, 마감 알림"에 맞는지: 브라우저 로컬 저장소의 용량·보존 한도, PC 알림 지원 범위. 설계 단계의 기술 스택 비교에서 확인한다. 기존 조사에서 PWA와 로컬 저장은 다뤄지지 않았다 (docs/02-research/01-overview.md)

## 확인되지 않은 추론

- [I] A-001: 지금 쓰는 도구가 없어서 만든다는 해석 (R1)
- [I] 사용자 본인이 개발 버그를 다루므로 개발자일 것이라는 추론 (R2). 사용자가 직접 말하지 않았다
- [I] 1년 사용 시 카드가 수백~수천 건 쌓일 수 있다는 규모 추정 (조사 일반 지식 폴백)
