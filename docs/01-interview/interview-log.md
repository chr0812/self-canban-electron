## R1 — 문제·배경
Q: 지금은 이슈·할 일을 어디에 어떻게 관리하나요? 가장 최근 불편했던 순간은?
A: "없어서 만들려고함."
→ 기록: A-001 (현재 쓰는 도구가 없어서 만든다는 뜻으로 이해함 [I], 기존 도구가 맞지 않아서인지 단순히 안 쓰고 있어서인지는 미확인), Q-001 (불편 사례·기존 도구를 안 쓰는 이유 미확인)

## R2 — 핵심 시나리오
Q: 카드(이슈) 하나가 만들어져 해결되기까지를 예시로. 어떤 종류의 일이고, 등록 시 무엇을 적고, 어떤 단계를 거치나?
A: "개발 버그도있고 할일도있는걸로, 각 카드생성 후 상태변경으로 카드가 상태별로 진행상황을 볼수 있엇으면 좋겠슴."
→ 기록: SC-001 (카드 생성 → 상태 변경 → 상태별 진행 확인), RC-001 (카드를 만든다), RC-002 (카드의 상태를 바꾼다), RC-003 (카드를 상태별로 모아 본다), 카드 종류는 개발 버그와 할 일 두 가지로 언급됨 (구분 방식·필드는 미확인)

## R3 — 핵심 시나리오 / MVP 범위 (상태·카드 종류)
Q: 카드 상태(칸)를 어떻게 나눌까요? / 개발 버그 카드와 할 일 카드를 어떻게 구분할까요?
A: 상태 = "3단계" (제시한 안: 할 일 → 진행 중 → 완료). 카드 종류 = "같은 카드, 종류 표시만" (카드 모양은 같고 버그/할 일 라벨만 다름).
→ 기록: D-001 (상태는 3단계 [S], 칸 이름은 제시안 '할 일/진행 중/완료'를 쓴다고 이해, 정확한 이름·사용자 편집 여부 미확인), D-002 (버그/할 일은 같은 카드 + 종류 표시 [S]), RC-004 (카드에 종류(버그/할 일)를 표시한다)

## R4 — MVP 범위 (카드 항목, 날짜의 역할)
Q: 카드에 적고 싶은 항목을 모두 골라 달라 / 스케줄 관리에서 날짜는 어떤 역할이어야 하나?
A: 항목 = "상세 설명, 마감일, 우선순위, 추가메모가 있으면 좋겠슴. 진행별로 추가이슈 및 검토사항 및 히스토리추적이 가능한 기록을 카드별로 넣을 수 있게". 날짜 = "캘린더로도 보기".
→ 기록: RC-005 (상세 설명), RC-006 (마감일), RC-007 (우선순위), RC-008 (추가 메모), RC-009 (카드별로 진행 단계마다 추가 이슈·검토사항 기록을 남긴다), RC-010 (카드를 날짜 기준 캘린더로도 본다), D-003 (날짜는 캘린더 보기까지 포함한다 [S]), Q-002 (히스토리 추적이 사용자가 직접 쓰는 기록인지, 상태 변경 등을 자동으로 남기는 이력인지 미확인)

## R5 — 제약 (사용 기기, 오프라인·저장)
Q: 어느 기기에서 쓰실 건가요? / 인터넷이 없는 곳에서도 써야 하나요, 데이터는 어디에 두나요?
A: 기기 = "내 PC 한 대만". 저장 = "내 PC에만 저장, 오프라인 OK".
→ 기록: D-004 (사용 기기는 내 PC 한 대 [S], 여러 기기·모바일 동기화는 하지 않음), D-005 (데이터는 내 PC에만 저장하고 인터넷 없이 동작한다 [S], 서버·계정 없음), RC-011 (데이터를 내 PC에 저장하고 오프라인에서 동작한다), Q-003 (백업·내보내기를 어떻게 할지 미확인 — 내 PC에만 저장하면 PC 고장 시 유실)

## R6 — MVP 범위·우선순위
Q: 1차 버전에 없으면 안 쓸 것 세 가지 / 이번에 일부러 안 만들 것
A: "카드 생성, 상태 변경, 캘린더 보기. 제외는 없음"
→ 기록: RC-001·RC-002·RC-010 Must 후보 [U], 나머지 RC(003~009, 011)는 사용자가 순위를 말하지 않음 (우선순위 미분류, PRD 단계에서 분류), D-006 (1차 버전에서 일부러 제외하기로 한 항목은 없다 [U])

## R7 — 성공 기준 / 예외 (완료 카드)
Q: 이 보드가 '잘 되었다'고 느낄 기준은? / 완료된 카드는 어떻게 할까?
A: 성공 기준 = "이슈가 다 보드에 있다" (제시안 '내가 해야 할 일이 메모·머릿속에 없고 전부 한 화면에 모여 있는 상태'를 고름). 완료 카드 = "보관(숨김) 처리" (제시안 '보드에서 숨기고 필요할 때 찾아볼 수 있게 한다').
→ 기록: D-007 (성공 기준은 해야 할 일이 전부 보드에 모여 있는 상태 [S], 수치 기준은 정해지지 않음), D-008 (완료 카드는 보드에서 숨기는 보관 처리를 하고 필요할 때 찾아볼 수 있다 [S]), RC-012 (완료 카드를 보관하고 보관한 카드를 다시 찾아볼 수 있다)

## R8 — 실현 요건 점검 (Step 2c)
제안: (1) 데이터 백업·내보내기 — 데이터·운영, 내 PC에만 저장하면 PC 고장 시 전부 유실, 근거 D-005. (2) 카드 수정·삭제 — 데이터·운영, 오타·잘못 만든 카드를 고치려면 필요, 근거 RC-001. (3) 마감 임박·지연 알림 — 외부 연동, 마감일을 넣어도 보드를 열어야만 알 수 있음, 근거 RC-006. (4) 검색·필터 — 비기능, 1년 쓰면 카드 수백~수천 건 가능 (조사 추정치, 일반 지식 폴백), 근거 RC-012.
처리: (1) 기각 (이유 입력 없음) (2) 수락 (3) 수락 (표시 방식은 정하지 않음) (4) 수락
→ 기록: D-009(기각: 백업·내보내기 없음, PC 고장 시 유실 감수. 이유는 말하지 않음), RC-013(수락 [S], 카드 수정·삭제), RC-014(수락 [S], 마감 임박·지연 카드 알림), RC-015(수락 [S], 검색·필터), Q-004(알림을 화면 표시로 할지 PC 알림으로 할지 미확인), Q-005(웹으로 할지 Electron으로 할지 — 설계 단계에서 후보를 비교해 사용자가 결정). Q-003은 D-009로 해소.
