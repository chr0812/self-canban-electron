# 인터뷰 템플릿

`/interview` 가 만드는 두 파일의 구조. 섹션 순서와 제목은 유지하고, 해당 없는 섹션도 지우지 말고 "해당 없음"으로 둔다.
섹션 헤딩에 번호를 붙이지 않는다.

---

## A. interview-log.md (진행 중 갱신, 이어하기 기준)

````markdown
# Interview Log: {아이디어 한 줄}

> 시작: {YYYY-MM-DD} · 깊이: {depth} · 라운드 상한: {N}
> 사전 자료: {경로 목록 / 없음}

## 커버리지

| ID | 토픽 | 상태 | 비고 |
|----|------|------|------|
| T1 | 문제·배경 | 미확인/부분/확정 | [사전자료]/[추론]/R{n} |
| T2 | 대상 사용자 | | |
| … | | | |

## 기록 번호 현황

D: {마지막 번호} · RC: {…} · SC: {…} · A: {…} · C: {…} · Q: {…}

---

## R1 — {토픽}
Q: {질문}
A: {답변 요지 / 핵심 인용}
→ 기록: D-001, RC-001

## R2 — {토픽}
…

## R{n} — 실현 요건 점검 (Step 2c)
제안: {항목 한 줄씩 — 분류, 왜 필요한가, 근거}
처리: {항목: 수락/기각(이유)/보류}
→ 기록: RC-007(수락 [S]), D-004(기각), Q-005(보류)
````

- 기록 번호 현황은 이어하기 때 번호가 겹치지 않게 하려는 용도다. 매 라운드 갱신한다.
- 라운드 블록은 사용자의 말을 되도록 원문에 가깝게 남긴다. 해석은 `→ 기록` 줄에만 둔다.

---

## B. interview.md (최종 정리본)

````markdown
# Interview: {아이디어 한 줄}

> 작성일: {YYYY-MM-DD} · 깊이: {depth} · 라운드: {N}
> 사전 자료: {경로 목록 / 없음}
> 상태: 초안

## 요약

- 문제: {1줄}
- 사용자: {1줄}
- 핵심 가치: {1줄}
- MVP 범위: {1줄}

## 문제와 배경

{현재 대안, 불편, 근거. 각 문장 끝에 출처 태그 [U]/[S]/[조사] 와 R{n}}

## 사용자

| 구분 | 설명 | 사용 맥락 | 출처 |
|------|------|-----------|------|
| 주 사용자 | | | |
| 부 사용자 | | | |

## 핵심 시나리오

{`### SC-NNN` 헤딩 블록 (question-bank.md 의 형식)}

## 요구사항 후보

| ID | 내용 | 우선순위 후보 | 출처 | 근거 |
|----|------|:------------:|:----:|------|
| RC-001 | | Must | [U] | R3 |

## 범위

- **MVP 포함**: …
- **이번에 하지 않음**: …
- **나중에**: …

## 성공 기준

{수치 또는 관찰 가능한 상태. 없으면 "정해지지 않음" — 열린 질문에 Q-n 으로 등록}

## 제약과 가정

| ID | 구분 | 내용 | 출처 |
|----|------|------|------|
| C-001 | 제약 | | [U] |
| A-001 | 가정 | | [S] |

## 결정 사항

| ID | 결정 | 이유 | 기각한 대안과 사유 | 출처 | 근거 |
|----|------|------|-------------------|:----:|------|
| D-001 | | | | [U] | R2 |

## 충돌

{서로 모순되는 답이 해소되지 않은 채 남았을 때만. 없으면 "없음"}

| 항목 | 답 A (라운드) | 답 B (라운드) |
|------|---------------|---------------|

## 실현 요건 점검

{Step 2c 의 결과. 사용자가 말하지 않았지만 아이디어를 실현하려면 필요해 보여 **모델이 제안한** 항목과 사용자의 처리. 건너뛰었거나 제안할 것이 없으면 "해당 없음: 사유"}

| 항목 | 분류 | 처리 | 연결 |
|------|------|------|------|
| 공유 대상(친구) 관리 | 사용자·권한 | 수락 | RC-002 |
| 로그인 방식 선택 | 사용자·권한 | 보류 | Q-001 |
| 웹 버전 제공 | 운영·지원 | 기각 | D-001 |

- `분류`: 사용자·권한 / 데이터·운영 / 외부 연동 / 규제·개인정보 / 비기능 / 운영·지원
- `처리`는 수락 / 기각 / 보류 중 하나다. **사라지는 항목이 없도록 `연결`에 결과가 남은 곳을 적는다**: 수락 → `RC-NNN`(출처 `[S]`), 기각 → `D-NNN`(기각한 대안과 사유 칸에 이유), 보류 → `Q-NNN`. (게이트 `VAL-19`)
- 사용자가 다루지 않기로 한 영향 보통 이하 항목은 이 표에 넣지 않고 `확인되지 않은 추론`에 `[I]`로 둔다.

## 열린 질문

| ID | 질문 | 영향 | 누가 답할 수 있나 |
|----|------|------|------------------|
| Q-001 | | 높음/중간/낮음 | |

## 조사 필요 항목

{사실 확인이 필요한데 인터뷰에서 해소하지 못한 것. /pre-research 권장 대상. 없으면 "없음"}

## 확인되지 않은 추론

{[I] 태그 항목만 모음. 사용자가 확인하기 전까지 요구사항으로 취급하지 않는다. 없으면 "없음"}

## 커버리지

| ID | 토픽 | 상태 | 비고 |
|----|------|------|------|
| T1 | 문제·배경 | 확정 | R1 |

{log 의 최종 커버리지 표를 그대로 옮긴다. 상태는 미확인 / 부분 / 확정 중 하나. 이 깊이에서 다루는 토픽은 모두 행이 있어야 한다}

## 다음 단계

- PRD 작성: `prd-writer` (`docs/01-interview/interview.md`가 필수 입력)
- 조사 필요 항목이 있으면: `/pre-research {주제}`
````

작성 규칙:
- 머리의 `> 상태:`는 `초안` 또는 `확정` 한 값만 쓴다. 사용자가 확정하면 `확정`으로 바꾸고, 바로 아래에 `> 확정 라운드: {그때의 라운드 N}` 줄을 쓴다. `prd-writer`는 `확정`일 때만 PRD를 작성한다.
- 확정 뒤에 보강하면 `> 라운드:`를 올리고 `> 상태:`를 `초안`으로 되돌린 뒤 다시 확정을 받는다. `확정 라운드`는 다시 확정할 때 갱신한다 (게이트 `VAL-12`가 둘의 차이로 재확정 누락을 잡는다).
- ID는 3자리(`RC-001`)이고, 표의 첫 열 또는 `###` 헤딩에서 정의한다. 한 번 쓴 번호는 재사용하지 않는다.
- 모든 항목에 출처 태그를 붙인다. 태그 없는 항목은 만들지 않는다.
- [I] 항목은 "요구사항 후보" 표에 넣지 않고 "확인되지 않은 추론"에만 둔다. 사용자가 확인하면 [S] 로 바꿔 표로 옮긴다.
- 사용자가 말하지 않은 수치·고유명사를 채우지 않는다.
