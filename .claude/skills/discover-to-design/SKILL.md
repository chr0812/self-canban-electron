# /discover-to-design — 아이디어 → 승인된 설계

사용자가 `interview`, `prd-writer`, `spec-planner`, `design-architect`를 하나씩 실행하지 않아도, 이 허브가 **다음 단계를 직접 호출**하고 게이트와 승인을 관리한다.
허브는 **순서와 안전장치**를 맡는다. 내용 판단은 게이트(결정적 검사), 리뷰어(의미 검토), 사용자(승인)가 한다.

---

## 하는 일 / 하지 않는 일

| 한다 | 하지 않는다 |
|------|-------------|
| 진행 상태를 확인하고 중단한 곳에서 이어간다 | 사용자 대신 승인하거나 확정한다 |
| 다음 스킬·에이전트를 직접 호출한다 | `_approval.md`를 손으로 쓴다 |
| 단계마다 게이트를 실행하고 결과를 쉬운 말로 전한다 | 게이트 실패를 조용히 넘긴다 |
| 승인 지점에서 멈추고 내용 요약을 보여 준다 | 단계 스킬의 질문을 대신 답한다 |
| 단계 전환 때 "지금까지 / 다음 선택지와 의미"를 안내한다 | **구현(코드 작성)을 한다** — 설계 승인에서 끝난다 |

## 트리거

```
/discover-to-design [아이디어 또는 자료 경로] [--depth light|standard|deep]
/discover-to-design --status        # 진행 상태만 보여 주고 끝낸다
```

`--depth`는 인터뷰에 그대로 넘긴다 (기본 `standard`).

## 진행 지도

| 순서 | 단계 | 허브가 부르는 방법 | 끝 조건 | 사용자가 정하는 것 |
|:---:|------|-------------------|---------|-------------------|
| 1 | 인터뷰 | Skill `interview` | `interview.md` 상태 `확정` + 게이트 통과 | 질문 답변, 확정 |
| (선택) | 조사 | Skill `pre-research` | 조사 산출물 + 인터뷰 반영 | 조사 여부 |
| 2 | PRD | Agent `prd-writer` | 게이트 통과 + **승인** | 승인 / 수정 |
| 3 | 명세 | Skill `spec-planner` | 게이트 통과 + **승인** | 승인 / 수정, 미확인 가정 확인 |
| 4 | 설계 | Skill `design-architect` | 게이트 통과 + **승인** | 승인 / 수정 |
| 끝 | 종료 | — | 설계 승인 | — |

## 항상 지키는 규칙

1. **매번 상태부터 확인한다.** 어디까지 왔는지 추측하지 않는다 (Step 0).
2. **사용자 결정 지점에서는 반드시 멈춘다.** 인터뷰 확정, 조사 여부, PRD·명세·설계 승인, 게이트 면제.
3. **승인은 사용자가 승인한 직후에만, `node scripts/gate.js approve <단계> --by <이름>`으로만 기록한다.** 이 명령이 실패하면(종료 코드 1·2) 승인 파일이 없는 것이다. 손으로 만들지 않는다.
4. **스킬·에이전트의 "완료" 주장을 믿지 않는다.** 파일 존재와 게이트 결과로 확인한다.
5. **사용자에게는 ID가 아니라 내용을 먼저 보여 준다.** (`RC-004`가 아니라 "배지를 받는다")
6. **질문은 한 번에 1~2개**, 묻는 이유를 한 줄 붙인다. 선택지에는 각각 무엇이 달라지는지 쓴다.
7. **승인된 문서를 고치기 전에 알린다.** 고치면 승인이 무효가 되고 하류 단계 재검토가 필요하다 ("변경 요청 처리").
8. 화면 형식은 `.claude/skills/discover-to-design/references/screens.md`를 따른다. 필요할 때 읽는다.
9. **스킬·에이전트 호출이 끝난 것처럼 보이는 메시지 뒤에 턴을 끝내지 않는다.** 하위 스킬의 "완료" 배너는 작업 전체의 끝이 아니다. 턴을 끝내도 되는 곳은 ① 사용자 응답을 기다릴 때 ② Step 6(`start_build` 이후) ③ 실패를 보고할 때뿐이다. 스킬·에이전트 호출 직후에는 여러 턴이 지났더라도 항상 Step 0으로 돌아가 `status --json`이 알려 주는 다음 행동을 한다.

## Step 0 — 상태 확인 (매번)

```
node scripts/gate.js init            # docs/README.md(산출물 안내)와 하네스 지문(docs/_gate/harness.json)이 없으면 만든다. 있으면 그대로 둔다
node scripts/gate.js status --json
```

결과를 "상태 화면"(screens.md)으로 보여 준다. `--status`로 불렸으면 여기서 끝낸다.

`next.action`에 따라 이어간다.

| action | 의미 | 이동 |
|--------|------|------|
| `start_interview` | 아무것도 없음 | Step 1 |
| `confirm_interview` | 인터뷰가 확정 전, 확정 뒤 내용이 바뀜(`VAL-12`), 또는 이 프로젝트의 확정 기록이 없거나 그 뒤 바뀜(`VAL-17`) | Step 2 (인터뷰 이어가기 — 바뀐 내용을 보여 주고 다시 확정). 가져온 정리본이면 "가져온 인터뷰" |
| `write_prd` | PRD 없음 | Step 3 |
| `write_spec` | 명세 없음 | Step 4 |
| `write_design` | 설계 없음 | Step 5 |
| `fix` | 어떤 단계의 내용 검사 실패 (`stage`가 `build`·`test`면 구현 허브의 일) | "게이트 실패 처리" |
| `request_approval` | 내용 통과, 승인 대기 (`stage`가 `test`면 인수 승인 — 구현 허브의 일) | 해당 단계의 승인 절차 |
| `reapprove` / `recheck_stale` | 승인 뒤 문서가 바뀜 / 상류가 바뀜 | "변경 요청 처리" |
| `start_build` | 설계 승인까지 끝 (구현 전) | Step 6 |
| `continue_build` · `start_test` · 시험 단계의 행동 · `done` | 구현 단계가 진행 중이거나 끝남 | "구현·시험은 `/design-to-build`가 맡는다"고 알리고 끝 |

- 산출물이 있으면 **처음부터 다시 하지 않는다.** 사용자가 처음부터를 원하면 기존 `docs/` 산출물을 지우지 않고 보존하는 방법(폴더 이름 바꾸기)을 확인한 뒤 진행한다.
- 승인자 이름이 필요해지면(첫 승인 직전) 한 번만 묻는다. `git config user.name`이 있으면 그것을 기본 선택지로 제시한다.

## Step 1 — 입력 접수 (산출물이 없을 때만)

아이디어가 인자로 오지 않았으면 한두 문장으로 묻는다. 그다음 한 번의 질문(2개)으로 경로를 정한다.

```
AskUserQuestion — 2개
  Q1. 아이디어가 얼마나 구체적인가요?  (묻는 이유: 조사와 인터뷰 중 무엇을 먼저 할지 정하려고요)
      · 구체적 — 누구를 위해 무엇을 왜 만드는지 말할 수 있다
      · 대략적 — 영역은 있는데 세부는 모른다
      · 아직 없음 — 뭘 만들지부터 정하고 싶다
      · 기존 자료 있음 — 문서나 초안이 있다 → 경로를 받는다
  Q2. 이 분야를 얼마나 아시나요?  (잘 안다 / 조금 / 처음)
```

| 상황 | 경로 | 순서 |
|------|------|------|
| 구체적 + 잘 안다·조금 | **A** | 인터뷰 → (조사 결정) → PRD |
| 구체적 + 처음, 또는 대략적 | **B** | 가벼운 조사 → 인터뷰 → (조사 결정) → PRD |
| 아직 없음 | **C** | 동향 조사 → 인터뷰(대안 발산 중심) → PRD |
| 기존 자료 있음 | **D** | 자료를 사전 자료로 넘겨 인터뷰 → (조사 결정) → PRD |

판정은 한 줄로 알리고 "이 경로로 갈까요?"를 확인한다. 애매하면 사용자에게 고르게 한다.

## Step 2 — 발견 (인터뷰 ↔ 조사)

**조사 호출** (경로 B·C, 또는 Step 2의 조사 결정에서 선택했을 때)

```
Skill(pre-research, args: "{주제} --depth light. 허브가 호출했다.")     # 인터뷰가 있으면 '조사 필요 항목'을 자동으로 읽는다
```

**인터뷰 호출**

```
Skill(interview, args: "{아이디어} --depth {depth}")        # 이어가기는 "--resume"
```

인자에 다음을 덧붙인다: "허브가 호출했다. 끝의 완료 배너와 '다음 단계 안내'는 출력하지 않고 한 줄만 알린 뒤 허브의 다음 단계로 계속한다."

스킬에서 돌아오면(여러 턴이 걸렸어도) **같은 턴에서** 곧바로 `node scripts/gate.js interview`와 `status --json`을 실행하고 다음 행동으로 넘어간다.

**인터뷰가 확정되면** `node scripts/gate.js interview`를 실행한다. 실패하면 "게이트 실패 처리". 확정 기록(`docs/01-interview/_confirmation.md`)은 인터뷰 스킬이 `gate.js confirm interview`로 남긴다. 없으면(`VAL-17`) 사용자에게 확정을 받고 허브가 같은 명령을 실행한다. 손으로 만들지 않는다.

**가져온 인터뷰** — 다른 프로젝트의 정리본을 복사해 시작하면 `확정` 상태여도 이 프로젝트의 확정 기록이 없어 `VAL-17`이 난다. 그대로 넘기지 않는다:
1. 출처(어느 프로젝트의 어느 판), 지금 정리본이 가리키는 조사 자료가 이 프로젝트에 있는지(`VAL-18`), 바꾼 곳을 보여 준다.
2. `AskUserQuestion`: **이대로 재사용** / **인터뷰로 보강 후 확정** / **처음부터 인터뷰**.
3. 재사용이면 `node scripts/gate.js confirm interview --by <이름> --note "재사용: <출처>"`. 없는 조사 참조는 지우거나 출처로만 남긴다 (조사를 새로 할지는 조사 결정 지점에서 묻는다).

**조사 결정 지점** — 인터뷰 확정 후, 조사를 아직 하지 않았다면 반드시 묻는다. 사용자가 조사를 모를 수 있으니 설명을 붙인다 (screens.md "조사 결정 화면").

| 선택 | 의미 |
|------|------|
| 조사 후 PRD | 인터뷰로는 알 수 없는 외부 사실(경쟁 서비스·규제·시장)을 웹에서 찾아 근거와 함께 정리한다. PRD의 배경·시장 맥락이 채워진다. `조사 필요 항목`이 있으면 이쪽을 권한다 |
| 조사 없이 PRD | PRD에는 "조사 없음"으로 쓰이고, 확인이 필요한 것은 열린 질문으로 남는다 |
| 인터뷰 더 | 아직 정리가 덜 됐을 때 |

- 조사를 했다면 결과를 인터뷰에 반영하는 보강(`Skill(interview, "--resume")`)을 **1회만** 한다. 그 뒤에도 남는 것은 열린 질문으로 둔다 (왕복 제한).
- **보강하면 재확정을 받는다.** 보강 호출 인자에 다음을 덧붙인다: "보강으로 내용이 바뀌면 상태를 초안으로 되돌리고, 끝에 '이번 보강에서 바뀐 것'을 보여 주며 확정 질문(Step 3-3)을 다시 한다. 허브가 호출했어도 생략하지 않는다." 스킬이 돌아온 뒤 `gate.js status`가 `confirm_interview`(확정 뒤에 인터뷰 내용이 바뀌었다)를 알리면 PRD로 넘어가지 말고 인터뷰를 이어서 확정한다. 게이트 `VAL-12`가 이 누락을 막는다.
- 알려 둘 점: 명세 단계(`spec-planner`)가 자체 도메인 조사를 한 번 더 수행한다. 조사를 건너뛰어도 규제 같은 사실은 명세 단계에서 나올 수 있다. 이 중복은 정리 대기 중이다.

## Step 3 — PRD

```
Agent(subagent_type: "prd-writer", prompt: "docs/01-interview/interview.md(확정)를 입력으로 docs/03-prd/prd.md를 작성한다.
  조사 결과(docs/02-research/)는 {있음|없음}. 조사를 건너뛰었으면 시장 맥락은 '조사 없음'으로 쓴다.")
```

1. 끝나면 `node scripts/gate.js prd`를 실행한다 (`prd-writer`는 Bash가 없어 직접 못 돌린다). 실패하면 "게이트 실패 처리".
2. 통과하면 **PRD 승인 화면**(screens.md)을 보여 준다: 비전, 핵심 기능(우선순위순), 제외 범위, 열린 질문 개수, 후보 처리 집계.
3. `AskUserQuestion`: **승인** / **수정 요청** / **인터뷰 보강 후 다시 작성** / **조사 후 다시 작성**.
   - 승인 → `node scripts/gate.js approve prd --by {이름} --note "{사용자가 승인하며 남긴 조건, 없으면 생략}"`
   - 수정 요청 → 요구사항의 추가·삭제·우선순위 변경이면 **먼저 인터뷰 정리본에 반영**(`Skill(interview, "--resume")`, 인자에 위 보강 재확정 문구를 덧붙인다)하고 인터뷰를 다시 확정받은 뒤 PRD를 다시 만든다. 표현만 고치는 것이면 PRD만 고친다. 고친 뒤 게이트를 다시 돌리고 승인 화면으로 돌아간다.

---

## Step 4 — 명세

```
Skill(spec-planner, args: "입력: docs/03-prd/prd.md(승인)와 docs/01-interview/interview.md. 산출물 계약(contracts/artifact-contract.md)을 따른다.
  경로는 docs/04-spec/ 고정. Step 6의 최종 확정 질문은 허브가 하므로 생략한다.")
```

1. 끝나면 `node scripts/gate.js spec`. 실패하면 "게이트 실패 처리".
2. **명세 승인 화면**: 요구사항 수(우선순위별), 범위 제외, 화면·유스케이스 수, **P0 인수 기준**(사용자가 "다 됐다"의 기준을 승인한다), 리뷰 결과 요약(검증 기록), 그리고 반드시 **가정(ASM)을 `설계 영향`으로 나눠** 보여 준다 — `높음`인 가정은 하나씩 이유와 함께(틀리면 어떤 설계 문서를 다시 만들어야 하는지), `보통`·`낮음`은 개수만. 승인하면 이 가정이 설계의 전제가 된다는 설명을 붙인다. 사실인지 조사한 결과가 아니라 **설계가 무엇에 기대는지**를 보여 주는 것임을 밝힌다.
3. `AskUserQuestion`:
   - **`설계 영향: 높음`인 가정이 있으면** "승인"을 바로 주지 않는다. 먼저 높음 가정을 한 번에 최대 4개씩 묶어 하나씩 묻는다: **이 가정으로 설계한다** / **가정을 바꾼다**(명세를 고친다. "변경 요청 처리") / **보류**(열린 질문으로 남기고 설계 전에 확인). 사용자가 영향 판정이 틀렸다고 하면 명세의 `설계 영향` 줄을 고친다.
   - 확인이 끝나면 **승인** / **수정 요청**. 승인 → `approve spec --note "확인한 가정: ASM-002(높음) …"` 처럼 **사용자가 설계 전제로 확인한 높음 가정의 ID를 승인 비고에 남긴다.** 게이트는 확인했는지 알 수 없으므로 이 기록이 유일한 증거다.
   - 높음 가정이 없으면 기존처럼 **승인** / **가정을 먼저 확인** / **수정 요청**.
   - 우선순위가 PRD와 달라진 FR이 있으면(게이트 경고 `VAL-11`) 승인 화면에 적고, 사용자가 수락한 것을 `--note`에 남긴다.

## Step 5 — 설계

```
Skill(design-architect, args: "입력: docs/04-spec/spec.md(승인). 경로는 docs/05-design/ 고정. 계약의 산출물 목록을 따르고
  08-tasks.md의 covers로 모든 P0 FR이 Task에 매핑되게 한다. 07-test-plan.md는 명세의 모든 인수 기준(AC)을 시험 시나리오(TC)로 덮고,
  Task의 check:가 자동 TC를 맡는다. 01-tech-stack.md에 명령·시험 환경 표와 후보 비교를 두고 사용자가 후보를 보고 고르게 한다. 화면(SCR)이 있으면 서로 다른 방향의 시안을 만들고 사용자가 보고 고르게 한다(스킬의 3-0b). 구현(코드 작성)은 하지 않는다.")
```

1. 스킬 안의 확인은 4곳(기술 스택 **후보 선택** / 화면 **시안 선택** / 데이터·UI / 아키텍처·Task)이다. 허브는 이를 대신하지 않는다. 앞의 두 곳은 사용자가 후보·시안을 비교해 고르는 자리이고, 화면 형식은 `references/screens.md`의 "기술 스택 후보 화면", "시안 선택 화면"이다.
   - 설계 리뷰(스킬 Step 8)의 지적은 `contracts/review-handling.md`의 유형으로 처리된다. 오기·구현 보완은 스킬이 근거를 기록하고 고치며, **요구·정책 지적만** 스킬이 모아서 한 번 더 묻는다(위 3곳 외의 추가 확인). 그 결정이 승인된 명세를 바꾸면 아래 "명세가 바뀌는 결정"을 따른다. 처리 결과는 `docs/05-design/_review/resolution.md`에 남는다.
   - **설계 중 사용자 결정이 나오면 먼저 분류한다.**

     | 종류 | 예 | 처리 |
     |------|----|------|
     | 설계 안에서 정할 수 있음 | 기술 선택, 구조, 화면 배치, 화면 순서 | 설계 문서에 반영한다. 명세는 그대로 |
     | 승인된 명세를 바꿈 | 기능 추가·삭제, 우선순위, 범위 제외, 제약·가정, 정책(로그인·보관 기간 등), 명세에 이미 고정된 기술·화면 선택을 바꾸는 것 | 바로 고치지 않고 아래 "명세가 바뀌는 결정"을 따른다 |

   - **명세가 바뀌는 결정**: 결정이 모일 때까지 명세를 고치지 않는다. 사용자에게 알린다 — "이 결정은 승인된 명세를 바꿉니다. 명세를 고치면 설계 문서 {n}개를 다시 만들어야 합니다." 그리고 `AskUserQuestion`: **지금 명세를 고친다**(결정을 모두 모아 **한 번만** 고친다) / **명세는 그대로 두고 설계를 진행한다**(바꾸고 싶다는 의사는 `README.md`의 "명세 개정 후보" 표에 적기만 하고 설계에는 반영하지 않는다) / **보류**. 명세를 고치면 "변경 요청 처리"를 따른다.
- **설계는 항상 승인된 명세와 같은 방향이어야 한다.** 명세와 달라진 설계를 승인받지 않는다. 명세 개정이 필요하면 설계 승인 **전에** 명세 개정과 재승인을 끝낸다. "명세 개정 후보"로 남긴 것은 설계 승인 뒤에 명세를 고치면 설계 승인이 낡아진다는 점(`recheck_stale`)을 설계 승인 화면에서 알린다.
- 명세가 정한 범위 안에서 아직 구체화되지 않은 것(예: 문구, 보존 기간의 값)은 임시 가정으로 두고 `README.md` 미해결 표에 적을 수 있다. 이것은 명세를 바꾸는 결정이 아니다.
   - 사용자가 "더 정할 게 있으면 물어봐"라고 하면, 설계에서 정할 것과 명세를 바꿀 것을 나누어 보여 준다. 명세를 바꿀 것은 한 번에 모아서 묻는다.
2. 끝나면 `node scripts/gate.js design`. 실패하면 "게이트 실패 처리". `REV-01`(미해결 CRITICAL)은 해당 지적을 닫아야 한다. `REV-03`은 요구·정책/선호 지적을 사용자 결정 없이 고친 기록이므로, 기록을 고치기 전에 그 수정이 사용자 결정을 받은 것인지 확인한다. `REV-02` 경고(리뷰 기록 없음)는 승인 화면에서 알린다.
3. **설계 승인 화면**: 기술 스택, 화면·와이어프레임 수, Task 수와 Wave 수, **리뷰 처리 요약**(지적 N건 — 수정 a / 사용자 결정 b / 기록 c / 기각 d, `resolution.md` 경로), 남은 미해결 사항(`README.md` 마지막 표), "명세 개정 후보"가 있으면 그 건수와 "설계 승인 뒤 명세를 고치면 이 승인이 낡아진다"는 안내.
4. `AskUserQuestion`: **승인** / **수정 요청**. 승인 → `approve design`.
   - `README.md` 등 승인 대상 문서 안에 승인 여부를 적지 않는다 (해시가 어긋난다).

## Step 6 — 종료

`node scripts/gate.js status`로 최종 상태를 보여 주고 다음을 알린다 (종료 화면).

- 산출물 위치(`docs/`)와 승인 기록.
- "**이 허브의 범위는 설계 승인까지입니다. 구현은 시작하지 않았습니다.**"
- 열린 질문·미확인 가정 중 구현 전에 확인할 것을 한 줄 요약.

그다음 `AskUserQuestion`: **구현을 시작한다** / **여기서 멈춘다**.
- **구현을 시작한다** → `Skill(design-to-build)`. 구현 허브가 자기 Step 0 부터 진행한다. 기획 대화가 길었다면 "새 세션에서 `/design-to-build`로 시작해도 이어진다"고 먼저 한 줄 알리고, 사용자가 이 세션에서 계속하길 원할 때만 호출한다.
- 이미 구현 단계가 진행 중이면(`status`의 `next.action`이 `continue_build`·`start_test` 등) 묻지 않고 "구현은 `/design-to-build`로 이어간다"고만 알린다.

## 게이트 실패 처리 (모든 단계 공통)

1. 실패한 규칙을 **쉬운 말로** 전한다 ("PF-004의 근거가 인터뷰에 없습니다" 정도로 ID를 쓰되 뜻을 같이).
2. 고친다: PRD는 `prd-writer`를 오류 목록과 함께 다시 호출한다. 명세·설계는 해당 줄만 최소한으로 고친다. 고친 곳을 사용자에게 알린다.
3. 게이트를 다시 돌린다. **최대 3회.**
4. 계속 실패하면 멈추고 `AskUserQuestion`: **직접 고치겠다** / **이 규칙을 면제한다**(사유를 입력받는다) / **중단**.
   - 면제는 `docs/_gate/waivers.md`에 계약 형식으로 기록한다 (허브가 직접 쓸 수 있는 유일한 승인성 기록).
   ```
   ## {YYYY-MM-DD} {단계} {규칙 ID}
   - 대상: {파일·ID}
   - 사유: {사용자가 말한 사유}
   - 승인자: {이름}
   ```

## 변경 요청 처리 (이미 승인된 뒤에 바뀔 때)

사용자가 승인된 문서의 변경을 원하거나 `status`가 `reapprove`·`recheck_stale`을 알릴 때.

1. **알린다**: "{단계}는 이미 승인됐습니다. 고치면 승인이 무효가 되고, 그 뒤 단계({하류 목록})도 영향을 받는지 다시 봐야 합니다."
2. 사용자가 진행하겠다고 하면 **고쳐야 하는 가장 상류의 문서부터** 고친다. 요구사항이 바뀌는 경우는 PRD 승인 여부로 갈린다.
   - PRD가 아직 승인 전이면 인터뷰 → PRD → 명세 → 설계 순으로 고친다.
   - PRD가 승인된 뒤면 **PRD는 고치지 않고 명세부터** 고친다 (아래 6). 사용자가 PRD 자체를 다시 쓰겠다고 하면 PRD 동결을 풀고 PRD → 명세 → 설계 순으로 재승인한다는 점을 먼저 확인한다.
3. 고친 단계의 게이트를 돌리고 **재승인**을 받는다.
4. `node scripts/gate.js status`로 하류의 `stale`·`blockedBy`를 보고(`staleBy`가 바뀐 상류 문서를 알려 준다), 하류 단계마다 "영향 없음 확인 후 재승인" 또는 "수정 모드로 다시 실행"을 사용자와 정한다. (`spec-planner`와 `design-architect`는 수정 모드가 있다.) 영향 없음으로 재승인해도 `approve`가 새 상류 해시를 기록하므로 `stale`이 풀린다.
5. 승인 상태를 문서에 적어 두지 않는다.
6. **PRD는 동결 문서다.** 요구사항이 PRD와 달라지는 변경은 PRD를 고치지 않고 명세에만 반영한다. 달라진 점은 명세 `변경 이력`과 `approve spec --note`에 남기고, 승인 화면에서 사용자에게 "PRD와 달라진 점"으로 보여 준다.
   - PRD의 **Must 기능을 사용자가 제외**하기로 했다면, 명세 `범위 제외`에 `[PRD: PF-NNN]`과 `[사용자 입력]`을 한 줄에 함께 적는다. 게이트(`TRC-02`)는 이 줄을 사용자가 승인한 제외로 인정한다. 사용자가 말하지 않은 제외는 인정되지 않는다.
   - 다른 기능으로 바뀐 경우는 새 FR의 근거에 `[PRD: PF-NNN]`을 그대로 두고, 달라진 내용을 `변경 이력`에 적는다.
7. 명세를 고쳤으면 `docs/04-spec/notes/`의 보조 자료(여정, 도메인 조사)가 바뀐 결정과 어긋나는지 확인한다. 어긋나는 문서는 맨 위에 `> {날짜} 명세 개정 전 분석이다. 현행 기준은 spec.md`를 적어 과거 자료임을 표시한다. (이 자료는 승인 해시 대상이 아니라 자동으로 잡히지 않는다.)

## 에러 처리

| 상황 | 처리 |
|------|------|
| 스킬·에이전트 호출 실패, 응답 없음 | 사용자에게 알리고 "재시도 / 중단"을 묻는다. 네트워크 단절일 수 있으니 재시도를 권한다 |
| 리뷰어 일부 실패 | 단계 스킬의 오류 처리 규정을 따른다 (스킬이 사용자에게 묻는다) |
| `approve`가 종료 코드 1 | 내용 검사 실패다. 승인 파일이 만들어지지 않았다. "게이트 실패 처리"로 간다 |
| `status`가 예상과 다름 | 추측하지 말고 결과를 그대로 사용자에게 보여 준다 |
| 사용자가 "구현까지 해줘" | 이 하네스의 범위 밖임을 알리고, 설계 승인 뒤 따로 요청하면 시작한다고 안내한다 |
