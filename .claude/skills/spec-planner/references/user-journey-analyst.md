# User Journey Analyst

요구사항에서 사용자 유형을 식별하고, 각 유형별 핵심 여정을 설계한다.

## Role

Step 4에서 호출. 결과는 `{out}/references/user-journeys.md`에 저장하고,
Step 5 Phase A에서 spec.md의 ## 화면 구조(SCR) 와 FR 보강에 반영된다.

## Input

- `{out}/spec.md` (Step 3 초안 — FR 목록 포함)
- 사용자 원문 입력
- 도메인 키워드 (Step 4-1 도메인 조사와 병행)

## 수행 작업

### 1. Persona 식별 (2~4개)

각 Persona 정의:
- **이름** (예: "직장인 김다은")
- **나이/직업** (구체적으로)
- **목표**: 이 앱으로 달성하려는 것
- **맥락**: 사용 상황 (언제/어디서/왜)
- **불편사항**: 해결하려는 문제

> Persona는 너무 많으면 분석 발산. 2~4개로 한정.
> P0 FR의 주요 수혜자 1명 + 부 사용자 1~2명 + 엣지 사용자 1명 정도.

### 2. 핵심 여정 설계

각 Persona별 핵심 여정 1~3개. 각 여정:

```
Journey N: {여정명} ({Persona})

| 단계 | 사용자 행동 | 시스템 응답 | 필요 기능 (FR) | 화면 (SCR) |
|------|-----------|-----------|---------------|----------|
| 1. 진입 | 앱 실행 | 로그인 화면 표시 | FR-001 | SCR-001 |
| 2. 인증 | 이메일/비번 입력 | 인증 처리 | FR-001, FR-002 | SCR-002 |
| 3. 핵심 액션 | ... | ... | FR-003 | SCR-003 |
| 4. 결과 확인 | ... | ... | FR-004 | SCR-004 |
| 5. 이탈 | 종료 또는 다음 단계 | ... | ... | ... |
```

여정 단계는 **진입 → 핵심 액션 → 결과 확인 → 이탈** 패턴을 기본으로.
모든 P0 FR이 최소 1개 여정에 등장하도록 설계.

### 3. Edge Case 시나리오 (최소 3개)

다음 카테고리에서 골고루:

- **빈 상태 (Empty State)**: 데이터 없을 때 (최초 사용)
- **오류 상황**: 네트워크 실패, 권한 거부, 서버 오류
- **대량 데이터**: 수천 개 항목, 무한 스크롤
- **경계 조건**: 동시 사용, 백그라운드 복귀, 화면 회전
- **악의적 사용**: 비정상 입력, 어뷰징

각 Edge case:
```
Edge {N}: {시나리오명}
- 상황: {언제 발생하는가}
- 사용자 경험: {사용자가 보는 것}
- 시스템 대응: {시스템이 해야 하는 것}
- 관련 FR: {커버하는 FR 또는 "신규 FR 필요"}
```

### 4. 유스케이스 명세화 (UML 표준)

여정 결과를 **유스케이스 명세(UC-NNN)** 로 정형화. 설계자가 API 설계 + 화면 흐름 + 트랜잭션 경계 결정 시 직접 활용.

각 P0 US에 대응하는 UC 작성 (1:1 매핑 권장). 핵심 P1 UC도 작성.

UC 명세 형식:

```
### UC-NNN: {유스케이스명}

- **Actor**: {주 행위자 — User / Trainer / Admin / Guest / System}
- **Goal**: {1줄 목적}
- **Precondition**: 
  - {조건 1}
  - {조건 2}
- **Trigger**: {시작 이벤트 — 버튼 탭/알림/스케줄}
- **Main Flow**:
  1. {단계 1 — 사용자 액션 또는 시스템 응답}
  2. {단계 2}
  3. ...
- **Alt Flow 1: {대안 상황명}**
  - {분기 조건} → {대안 흐름}
- **Alt Flow 2: {예외 상황명}**
  - {예외 처리}
- **Postcondition**:
  - {결과 상태 1}
  - {결과 상태 2}
- **관련 FR**: FR-001, FR-023
- **관련 SCR**: SCR-005, SCR-006, SCR-007
```

Edge case → Alt Flow 통합:
- Edge case 시나리오를 별도 섹션이 아닌 **해당 UC의 Alt Flow**로 흡수
- 예: "Edge 2: 네트워크 끊김" → UC-001 (운동 기록 저장) Alt Flow 1
- 통합 후에도 ## Edge Cases 섹션은 빠른 조회용 인덱스로 유지

작성 우선순위:
1. 모든 P0 US → UC (필수)
2. P1 US 중 Alt Flow가 복잡한 것 (예: 권한/네트워크/외부 시스템 의존)
3. P2는 선택

### 5. FR 커버리지 검증

```
FR 커버리지 테이블 작성:

| FR | 등장 여정 | 미등장 시 사유 |
|----|---------|---------------|
| FR-001 | Journey 1, 2 | - |
| FR-002 | Journey 1 | - |
| FR-005 | (없음) | ❌ 어느 여정에도 등장하지 않음 → 검토 필요 |

규칙:
  - 모든 P0 FR은 최소 1개 여정에 등장해야 함
  - 미등장 P0 FR은 ⚠️ 경고 표시 → Step 5에서 처리
```

### 5. 잠재 요구사항 발견

여정/Edge case 설계 중 발견된 미정의 요구사항:

```
## 발견된 잠재 요구사항

> Step 5 Phase A에서 spec.md의 FR 또는 Candidate Requirements로 승격.

### 핵심 여정 누락 → Candidate 후보 (사용자 확인 후 FR로 승격)
- 여정 X의 단계 N: "프로필 사진 업로드" — 현재 FR에 없음

### 엣지 시나리오 → Candidate Requirements 후보
- 오프라인 모드 임시 저장
- 다크모드
```

## Constraints

- Persona는 2~4개로 한정 (분석 발산 방지)
- 모든 P0 FR이 최소 1개 여정에 등장 (미커버 시 경고)
- Edge case 최소 3개
- 여정은 **사용자 관점**으로 작성 (기술 용어 최소화)
- "필요 기능 (FR)" 컬럼에서 spec.md의 FR ID와 매핑 — 신규 FR이 필요하면 명시
