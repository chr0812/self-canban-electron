# 질문 은행

`/interview` 가 질문을 고를 때 쓰는 참고 자료. **그대로 읽어 내려가는 체크리스트가 아니다.**
직전 답변에 맞는 질문 씨앗을 골라 상황에 맞게 바꿔 쓴다.

---

## 토픽 목록

|----|------|-----------------|:----:|:--------:|:----:|
| T1 | 문제·배경 | 누가 어떤 불편을 겪는가, 지금은 어떻게 해결하는가 | ● | ● | ● |
| T2 | 대상 사용자 | 주 사용자·부 사용자, 사용 맥락(언제/어디서/무엇으로) | ● | ● | ● |

| T8 | 데이터·콘텐츠 | 다루는 정보, 출처, 양, 민감도 | | ● | ● |

| T11 | 수익·운영 | 수익 모델, 운영 인력, 고객 지원, 유지보수 | | | ● |

## 질문 규칙

1. **한 번에 1~2개.** 세 개 이상 던지면 사용자는 쉬운 것만 답한다.
2. **이유를 한 줄 덧붙인다.** "이걸 묻는 이유: 범위를 정하려면 필요해서요."
3. **사례를 묻는다.** 의견("이런 기능이 필요해요")보다 경험("가장 최근에 그 일을 한 게 언제였나요?")이 정확하다.
4. **전문용어를 쓰지 않는다.** 사용자가 개발자가 아닐 수 있다. 용어가 필요하면 풀어서 쓴다.
5. **유도하지 않는다.** 선택지에 내 선호를 심지 않는다. 추천은 하나만, 이유와 함께 표시한다.
6. **아는 것은 다시 묻지 않는다.** 사전 자료에 있으면 "~로 되어 있는데 맞나요?"로 확인만 한다.
7. **모순은 즉시 보여준다.** 앞선 답과 충돌하면 두 답을 나란히 인용하고 어느 쪽이 맞는지 묻는다.
8. **붙잡지 않는다.** 같은 항목을 두 번 물어도 모호하면 가정(A-n)으로 기록하고 넘어간다.
9. **질문 형식 선택**
   - 답이 몇 가지로 갈린다 → AskUserQuestion (선택지 2~4개)
   - 사례·서술이 필요하다 → 채팅으로 직접 묻는다

## 되묻기 패턴

| 사용자가 한 말 | 되묻기 |
|---------------|--------|
| "빠르게 / 쉽게 / 편하게" | "지금은 얼마나 걸리나요? 어느 정도면 '빠르다'고 느끼실까요?" |
| "많은 사용자" | "처음 3개월 안에 몇 명 정도를 생각하세요? 대략 10 / 100 / 1,000 / 그 이상 중에서요." |
| "가끔 / 자주" | "한 사람이 일주일에 몇 번쯤 쓰나요?" |
| "~ 등 / 기타" | "나머지로 떠오르는 것을 하나만 더 꼽는다면요?" |
| "당연히 있어야죠" | "그게 없으면 어떤 일이 생기나요? 1차 버전에도 꼭 필요한가요?" |
| "다른 앱처럼" | "그 앱의 어떤 부분을 말씀하시는 거예요? 반대로 따라 하고 싶지 않은 부분은요?" |
| "알아서 해주세요" | "그럼 제가 [안]으로 가정하고 진행할게요. 나중에 바꿀 수 있어요." → A-n 기록 |

## 토픽별 질문 씨앗

### T1 문제·배경
- 이 서비스가 없을 때, 지금은 그 일을 어떻게 하고 계세요? (대안·우회 방법)
- 가장 최근에 그 일 때문에 불편했던 때를 이야기해주실 수 있나요?
- 그 불편이 사라지면 누가 가장 먼저 좋아할까요?

### T2 대상 사용자
- 가장 먼저 쓸 사람 한 명을 떠올리면 어떤 사람인가요? (직업, 나이대, 익숙한 기기)
- 그 사람이 이 서비스를 쓰는 순간은 언제, 어디서인가요?
- 쓰지 않았으면 하는 사람이 있나요? (관리자, 외부인 등 권한 구분)

### T3 핵심 시나리오
- 사용자가 서비스를 열고 → 목적을 달성하고 → 닫기까지, 순서대로 이야기해주세요.
- 그 과정에서 사용자가 "됐다!"라고 느끼는 순간은 어디인가요?
- 가장 자주 반복될 행동 한 가지는요?

### T4 MVP 범위·우선순위
- 기능이 딱 세 개만 가능하다면 무엇인가요?
- 이번에는 일부러 안 하기로 할 것이 있다면요?
- 나중에 추가해도 되는 것과 처음부터 없으면 안 되는 것을 나눈다면?

### T5 성공 기준
- 3개월 뒤 "잘 됐다"고 말하려면 무엇이 달라져 있어야 하나요? (숫자 하나)
- 실패했다고 판단하는 신호는 무엇인가요?

### T6 제약
- 언제까지, 몇 명이, 어떤 예산으로 만드나요? (모르면 "정해지지 않음"으로 기록)
- 반드시 써야 하거나 쓸 수 없는 기술·서비스가 있나요?
- 웹 / 모바일 앱 / 둘 다 중 무엇이 필요한가요?

### T7 예외·엣지 케이스
- 입력이 비어 있거나 잘못되면 사용자에게 무엇을 보여주나요?
- 같은 일을 두 번 하면(중복) 어떻게 되어야 하나요?
- 인터넷이 끊기면 어떻게 되어야 하나요?
- 다른 사람의 데이터를 보거나 고치려 하면요?

### T8 데이터·콘텐츠
- 서비스가 다루는 정보는 어떤 것들인가요? (예: 글, 사진, 주문, 일정)
- 그 정보는 어디서 오나요? 사용자가 입력하나요, 외부에서 가져오나요?
- 정보가 얼마나 쌓이나요? 오래된 정보는 어떻게 하나요?

### T9 외부 연동
- 로그인은 어떻게 하나요? (이메일, 소셜, 사내 계정)
- 결제·알림·지도·메신저처럼 연결해야 하는 외부 서비스가 있나요?
- 이미 쓰고 있는 시스템과 데이터를 주고받아야 하나요?

### T10 비기능
- 동시에 쓰는 사람이 가장 많을 때가 언제이고 몇 명쯤인가요?
- 지켜야 하는 보안 수준이 있나요? (개인정보, 금융정보 등)
- 고령자·장애인 접근성이나 다국어가 필요한가요?

### T11 수익·운영
- 이 서비스는 어떻게 비용을 회수하나요? (무료 / 구독 / 광고 / 수수료 / 내부용)
- 운영 중 문의·장애는 누가 처리하나요?

### T12 규제·개인정보
- 개인정보(이름, 연락처, 위치 등)를 수집하나요? 수집 목적과 보관 기간은요?
- 이 분야에 특별한 법규나 심의가 있나요? (의료, 금융, 교육, 아동 등)
- 모르는 경우 → "조사 필요 항목"에 기록한다 (추측으로 채우지 않는다).

## 설계 영향이 큰 질문 (선택지로 묻는다)

아래는 답에 따라 설계가 크게 달라지는데 사용자가 먼저 꺼내지 않는 주제다. T6·T9·T10에서 **선택지**(AskUserQuestion)로 묻고, 모르겠다고 하면 가정(A-n)으로 기록한다. 각 선택지에 "고르면 달라지는 것"을 한 줄 붙인다.

| 주제 | 질문 | 선택지 (고르면 달라지는 것) |
|------|------|----------------------------|
| 계정 | 사용자를 구분해야 하나요? | 계정 없이 (기기에만 저장, 가장 단순) / 이메일 가입 / 소셜 로그인 (가입 부담이 적고 연동 설정이 필요) |
| 기기 간 이어 쓰기 | 폰을 바꾸거나 여러 기기에서 같은 기록을 봐야 하나요? | 한 기기만 (서버 불필요) / 여러 기기 (서버와 계정이 필요) |
| 오프라인 | 인터넷이 없는 곳에서도 써야 하나요? | 항상 인터넷 있음 / 없을 때도 기록 가능 (나중에 동기화 설계가 필요) |
| 규모 | 처음 3개월 안에 쓰는 사람이 몇 명쯤인가요? | 10명 안팎 / 수백 / 수천 이상 (서버·비용 설계가 달라짐) |
| 개인정보 | 위치·건강·연락처 같은 민감한 정보를 다루나요? | 아니오 / 예 (수집 동의와 보관 기간 설계가 필요) |
| 운영 | 출시 뒤에 문의·장애를 누가 맡나요? | 직접 / 팀 / 아직 모름 (모름이면 운영 부담이 적은 구조를 우선) |

## 실현 요건 도출 기준 (Step 2c)

사용자가 말한 RC·SC가 **암묵적으로 전제하는데 아직 항목이 없는 것**을 모델이 먼저 제안하기 위한 기준이다. 이 표는 체크리스트가 아니라 **찾는 방향**이다. 이미 D·RC·Q로 다룬 것은 다시 제안하지 않는다.

| 분류 | 찾는 기준 | 예 (이런 말이 있으면) | 제안 |
|------|----------|----------------------|------|
| 사용자·권한 | 누가 무엇을 볼 수 있는가가 전제된 말 | "친구와 공유" → 친구 관계는 어떻게 맺나, 남의 기록은 어디까지 보이나 | 친구 추가·공개 범위 |
| 데이터·운영 | 저장·보관·삭제가 전제된 말 | "기록을 저장" → 얼마나 오래 두나, 지우면 어떻게 되나, 내려받기 | 보관 기간, 삭제·내보내기 |
| 외부 연동 | 서비스 밖의 것을 쓰는 말 | "지도에 경로" → 지도 서비스, "알림" → 푸시 | 연동 대상과 대안 |
| 규제·개인정보 | 사람·돈·건강·아이가 나오는 말 | "위치 기록" → 위치정보 동의, "결제" → 결제 규정 | 동의 화면, 보관 기간 (확정하지 말고 확인 필요 항목으로) |
| 비기능 | 많이, 빨리, 오래가 전제된 말 | "많은 사용자" → 몇 명, "실시간" → 몇 초 | 수치 기준 |
| 운영·지원 | 만든 뒤에 누군가 해야 하는 일 | "신고 기능" → 신고를 누가 처리하나 | 운영 방법, 문의 창구 |

**제안 규칙**
- 제안은 **사용자가 말하지 않은 것**이라고 밝힌다 ("말씀하지 않으셨지만 이 기능이 있으면 필요해 보이는 것입니다").
- 가격·법규·규제·외부 서비스의 조건처럼 **사실로 단정할 수 있는 내용은 단정하지 않는다.** "~로 알려져 있는데 확인이 필요합니다"로 쓰고, 작은 사실은 2-5(b)의 검색 1~2회로 확인해 근거와 함께 보인다. 큰 것은 `조사 필요 항목`에 남긴다.
- 한 번에 4개 안팎, 영향이 큰 순서. 항목마다 **왜 필요한가 / 안 하면 어떻게 되나**를 한 줄씩 쓴다.
- 선호를 심지 않는다. 추천이 있으면 하나만 이유와 함께 표시한다.

## 시나리오 기록 형식 (SC-n)

interview.md 의 `핵심 시나리오` 절에 아래 형식으로 쓴다. 헤딩이 ID의 정의 위치다.

```markdown
### SC-001 {이름}
- 상황: {누가, 언제, 왜}
- 행동: 1) … 2) … 3) …
- 기대 결과: {끝났을 때 상태}
- 예외: {실패·중단 경우 — 없으면 "미확인"}
- 출처: [U] R3
```

## 요구사항 후보 기록 형식 (RC-n)

```
RC-001 | {한 문장, "~한다"} | Must/Should/Could/Won't 후보 | 출처 [U]/[S]/[I] | R{n}
```

- 우선순위는 **후보**다. PRD 승인으로 확정된다.
- 정형 ID(PF/FR/NFR 등)는 붙이지 않는다. PRD·명세 단계에서 부여한다.
