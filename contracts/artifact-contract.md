# 산출물 계약 (Artifact Contract)

> 버전: 0.16 (초안) · 작성일: 2026-10-30
> 용어와 약어의 뜻: `contracts/glossary.md`
> 적용 대상: 게이트 스크립트, 허브 스킬, 각 단계의 스킬·에이전트·리뷰어

이 문서는 하네스의 모든 단계가 따르는 **단일 규약**이다.
스킬 문서·템플릿과 이 문서가 충돌하면 **이 문서가 우선**한다. 충돌은 스킬·템플릿을 고쳐서 해소한다.

---

## 목적과 범위

- 단계 간 인수인계(산출물)의 **이름, 위치, 구조, ID, 값 규칙**을 정한다.
- 게이트 스크립트가 기계적으로 검사할 수 있는 것만 규칙으로 둔다. 의미 판단은 리뷰어와 사용자 승인의 몫이다.
- 기획(인터뷰~설계 승인)과 구현·시험(코드, 검증, 인수 승인)을 다룬다. 허브는 둘로 나뉜다: 기획 `/discover-to-design`, 구현·시험 `/design-to-build`. 단계 사이는 파일로만 넘어간다.

## 하네스의 층과 위치

| 층 | 위치 | 규칙 |
|----|------|------|
| 규칙 | `contracts/`, `scripts/` | 무엇이 통과인가를 정한다. 순서나 실행 방법을 말하지 않는다 |
| 역할 | `.claude/agents/` | 단일 책임. 공통 규약(`contracts/role-protocol.md`)을 따른다. **`Agent`·`Skill`·`Task`를 호출하지 않고 사용자에게 질문하지 않는다** |
| 계획 | `.claude/plans/<단계>.md` | 역할, 입력, 출력, 선행, 체크포인트만 선언하는 마크다운 표. 절차 설명을 넣지 않는다 |
| 오케스트레이터 | 허브 스킬 | `Agent`·`Skill`을 호출하는 **유일한 곳**. 계획을 읽어 실행한다 |
| 대화형 스킬 | `interview` 등 | 사용자와 대화하는 일만 한다 |

- 층 규칙은 `npm run lint`가 검사한다 (역할·대화형 스킬의 호출 표기 금지, 계획 검증, 이름 충돌).
- 아직 정리되지 않은 곳은 `.claude/layers.json`의 예외 목록에 **사유와 정리 시점**을 적는다. 호출이 사라진 예외는 지우라고 점검이 알린다.
- 오케스트레이션이 일어나는 곳은 별도 프로그램이 아니라 **메인 세션의 모델이 허브 지시문과 계획을 따라 호출하는 것**이다. 결정성은 스크립트(`status`, `plan.js next`)와 게이트가 준다.
- 설계 근거와 마이그레이션 계획: `proposals/design-stage-pilot.md`

### 경로와 이름

- **폴더 번호는 작성 순서이고 고정이다** (`01-interview` … `07-test`). 선택 단계(조사)를 건너뛰어도 뒤 번호를 당기지 않는다.
- **파일 번호는 문서가 4개 이상인 폴더(조사, 설계)에만 붙인다.** 설계 파일 번호는 작성 순서다. 개발할 때 읽는 순서는 `docs/05-design/README.md`가 안내한다.
- **`_` 접두사는 하네스가 만드는 기록이다**: `_approval.md`, `_review/`, `_evidence/`, `_gate/`, `_variants/`. 손으로 고치지 않고, 구현할 때 보지 않는다. (`_variants/`는 설계 단계의 화면 시안 비교 기록이다. 승인 해시 대상이 아니고, 선택 결과만 `04-ui-spec.md`로 올라간다.)
- **파일 이름은 영문**이고, 한글 이름은 각 문서의 첫 줄 제목과 `docs/README.md`(산출물 안내)에 둔다. 한글 파일 이름은 OS 간 유니코드 정규화(NFC/NFD) 차이로 경로 비교와 승인 해시가 깨질 수 있어 쓰지 않는다.
- 스크립트의 경로는 `scripts/lib/paths.js` 한 곳에서 정한다. 이 표와 다르면 이 표를 고치고 `paths.js`를 맞춘다.
- 0.12 이전 경로(`docs/interview`, `docs/planning` 등)는 지원하지 않는다. 옛 경로의 프로젝트는 그 시점의 하네스로 본다.

**경로는 고정이다.** `spec-planner`의 `--out`처럼 경로를 바꾸는 옵션은 쓰지 않는다.

**발견 단계의 내부 순서는 계약이 정하지 않는다.** 허브가 입력 상태(아이디어의 구체성, 분야 지식, 기존 자료)에 따라 경로를 정한다. 어느 경로든 `interview.md`로 모인다. PRD의 입력으로 `interview.md`는 필수, `02-research/*`는 선택이다.

**PRD는 `prd-writer` 에이전트(`.claude/agents/prd-writer.md`)가 `contracts/templates/prd-template.md` 구조로 작성한다.** 사용자 승인은 허브가 받는다.

**PRD는 승인 시점의 스냅샷이다.** 승인 후에는 수정하지 않는다. 이후의 요구사항 변경은 `spec.md`에만 반영한다.

## 승인 파일

각 승인 대상 단계는 `_approval.md`를 가진다. 사용자가 승인했다는 유일한 증거다.

```markdown
# 승인: {단계}

승인: 예
승인자: {이름}
승인일: YYYY-MM-DD
대상: {승인 대상 파일 경로, 설계는 쉼표로 여러 개}
대상 해시: sha256:{hex}
상류 해시: {상류 문서 경로} sha256:{hex}
비고: {조건·메모, 없으면 "없음"}
```

- `승인: 예`가 아니면 승인이 아니다.
- **해시는 승인 대상 파일 내용의 sha256이다.** 개행은 `\n`으로 정규화해서 계산한다(Windows `\r\n` 차이로 인한 오탐 방지).
- 승인 후 대상 파일이 바뀌면 해시가 달라지고, 게이트는 **승인 무효**로 판정한다. 다시 승인을 받아야 한다.
- 설계는 대상 파일마다 해시를 한 줄씩 적는다(`대상 해시: <경로> sha256:<hex>`).
- **상류 해시는 승인 시점에 이 단계가 근거로 삼은 상류 문서의 sha256이다** (`approve`가 자동으로 적는다). PRD ← `docs/01-interview/interview.md`, 명세 ← `docs/03-prd/prd.md`, 설계 ← `docs/04-spec/spec.md`. 승인 뒤에 상류 문서 내용이 바뀌면 이 단계의 승인은 **낡은 것**이다 (`APR-03`, `status`의 `stale`). 다시 승인하면(`approve`) 새 상류 해시로 갱신된다. 상류 해시가 없는 옛 승인 파일은 수정 시각으로만 판단한다 (호환).
- **PRD는 동결 문서다.** 상류(인터뷰·PRD)와 달라지는 요구사항 변경은 명세에만 반영하고, 달라진 점은 명세 `변경 이력`과 승인 `비고`에 남긴다. PRD 자체는 고치지 않는다. 예외는 사용자가 PRD를 다시 쓰겠다고 **명시**한 경우뿐이며, 이때는 PRD → 명세 → 설계 순으로 재승인한다 (상류 해시로 하류 승인이 낡아진다).

## 문서 공통 규칙

1. 인코딩은 UTF-8, 개행은 `\n`.
2. **헤딩에 번호를 붙이지 않는다.** (`## 배경`, 아님 `## 1. 배경`)
3. 필수 섹션은 헤딩 텍스트가 **계약의 이름으로 시작**하면 인정한다. (`## 비전 및 목표 (Vision & Goals)`는 `비전 및 목표`로 인정)
4. 섹션이 있어도 **본문이 비어 있으면 없는 것으로 본다.** 해당 없으면 "해당 없음"이라고 쓴다.
5. 확정되지 않은 것은 확정처럼 쓰지 않는다. 열린 질문 섹션에 둔다.
6. 문서 머리에 `> 작성일: YYYY-MM-DD` 줄을 둔다.

## ID 체계

형식은 `접두사-NNN`이다. 접두사는 **대문자**, 번호는 **3자리, 1부터**, 한 번 쓴 번호는 **재사용하지 않는다**(삭제해도 결번으로 둔다).

**정의와 참조를 구분한다.** 중복 검사는 **정의 위치**에서만 센다. 본문의 참조(`관련 FR: FR-001`)는 중복이 아니다.

| 접두사 | 의미 | 만드는 단계 | 정의 형식 |
|--------|------|-------------|-----------|
| `RC` | 요구사항 후보 | 인터뷰 | 표 첫 열 |
| `SC` | 시나리오 | 인터뷰 | 헤딩 `### SC-NNN 이름` |
| `D` | 결정 | 인터뷰 | 표 첫 열 |
| `A` | 가정(인터뷰) | 인터뷰 | 표 첫 열 |
| `C` | 제약(인터뷰) | 인터뷰 | 표 첫 열 |
| `Q` | 열린 질문 | 인터뷰 | 표 첫 열 |
| `PF` | 제품 기능 | PRD | 핵심 기능 표 첫 열 |
| `FR` | 기능 요구사항 | 명세 | 불릿 `- **FR-NNN**` |
| `AC` | 인수 기준 | 명세 | FR 불릿 아래 `- 인수 기준:` 밑의 들여쓴 불릿 `- AC-NNN: 기준` |
| `NFR` | 비기능 요구사항 | 명세 | 불릿 `- **NFR-NNN**` |
| `CON` | 제약 조건 | 명세 | 불릿 `- **CON-NNN**` |
| `ASM` | 가정 | 명세 | 불릿 `- **ASM-NNN**` (`[가정]` 태그 필수) |
| `US` | 사용자 스토리 | 명세 | 헤딩 `### US-NNN` |
| `UC` | 유스케이스 | 명세 | 헤딩 `### UC-NNN` |
| `SCR` | 화면 | 명세 | 주요 화면 정의 표 첫 열 |
| `CAND` | 후보 요구사항 | 명세 | 줄 첫머리: 불릿 `- **CAND-NNN**` (표 행·`###` 헤딩도 인정) |
| `RISK` | 리스크 | 명세 | 줄 첫머리: 표 첫 열 (불릿·`###` 헤딩도 인정) |
| `KPI` | 성공 지표 | 명세 | 줄 첫머리: 표 첫 열 (불릿·`###` 헤딩도 인정) |

## 우선순위

정식 척도는 **Must / Should / Could / Won't**이다. 단계에 따라 표기만 다르다.

| 정식 | 인터뷰·PRD 표기 | 명세·설계 표기 |
|------|-----------------|---------------|
| Must | `Must` | `P0` |
| Should | `Should` | `P1` |
| Could | `Could` | `P2` |
| Won't | `Won't` | **범위 제외** (FR을 만들지 않는다) |

- PRD 템플릿의 `Nice`는 `Could`로 바꾼다.
- 우선순위 값은 위 표기 외의 값을 쓰지 않는다.
- 인터뷰의 우선순위는 **후보**다. **PRD 승인으로 확정**되고, 명세는 PRD의 우선순위를 `P0/P1/P2`로 옮긴다. 명세에서 우선순위를 올리거나 내리려면 사용자 확인이 필요하다.

## 출처 태그

### 인터뷰 항목 태그

모든 `D`, `RC`, `SC`, `A`, `C` 항목에 붙인다.

| 태그 | 의미 |
|------|------|
| `[U]` | 사용자가 직접 말함 |
| `[S]` | Claude가 제안하고 사용자가 수락함 |
| `[I]` | Claude 추론, 사용자 미확인 |

`[I]` 항목은 요구사항 후보(`RC`) 표에 넣지 않는다. 별도 섹션에 둔다. 사용자가 확인하면 `[S]`로 바꿔서 옮긴다.

### 근거 태그 (PRD의 근거 열, 명세 FR의 `근거:` 필드)

| 태그 | 형식 | 성격 |
|------|------|------|
| 인터뷰 | `[인터뷰: RC-NNN]` | 사용자 유래 |
| PRD | `[PRD: PF-NNN]` | 사용자 유래 (승인됨) |
| 사용자 입력 | `[사용자 입력]` | 사용자 유래 (대화에서 직접, 기록 번호 없음) |
| 조사 | `[조사: 출처]` | 외부 근거 |
| 경쟁 분석 | `[경쟁 분석: 서비스명]` | 외부 근거 |
| 사용자 여정 | `[사용자 여정: 이름]` | 도출 근거 |

**FR은 사용자 유래 근거가 최소 하나 있어야 한다.** 조사·경쟁 분석·여정에서만 나온 항목은 FR이 아니라 `CAND`로 올리고, 사용자가 확인한 뒤에 FR로 승격한다.

## 산출물별 필수 섹션

### interview.md

`요약`, `문제와 배경`, `사용자`, `핵심 시나리오`, `요구사항 후보`, `범위`, `성공 기준`, `제약과 가정`, `결정 사항`, `열린 질문`, `조사 필요 항목`, `확인되지 않은 추론`, `커버리지`

커버리지 표의 `상태` 열은 `미확인` / `부분` / `확정` 중 하나다.

**0.16 선택 섹션: `실현 요건 점검`.** 필수 섹션 목록에 넣지 않는다(이 섹션이 없는 옛 정리본은 검사하지 않는다). 다만 **확정한 정리본에 없으면 `VAL-19` 경고**다. 해당 없으면 `해당 없음`이라고 쓴다.

- **`실현 요건 점검`**: 아이디어를 실현하려면 암묵적으로 필요한데 사용자가 말하지 않은 것을 모델이 제안하고, 사용자가 처리한 결과다. 사용자가 말하지 않은 것을 확정하지 않는 원칙은 그대로이고, 제안은 사용자가 수락해야 `RC [S]`가 된다.

  | 항목 | 분류 | 처리 | 연결 |
  |------|------|------|------|

  `처리`는 `수락` / `기각` / `보류`다. 사라지는 항목이 없도록 `연결`에 결과가 남은 곳을 적는다: 수락 → `RC-NNN`, 기각 → `D-NNN`(기각 이유와 함께), 보류 → `Q-NNN`.

### prd.md

- 필수: `배경`, `비전 및 목표`, `타겟 사용자`, `핵심 기능`, `범위 및 제약`, `열린 질문`, `요구사항 후보 처리 현황`
- 선택: `차별화 전략`, `비즈니스 모델`, `리스크`, `참고 자료` (깊이가 얕으면 생략 가능)
- `핵심 기능` 표는 `ID`, `우선순위`, `기능`, `설명`, `근거` 열을 가진다. ID는 `PF-NNN`.
- `범위 및 제약`에는 `MVP 범위`와 `제외 범위`가 있다. 제외된 항목도 근거 태그를 가진다.
- `요구사항 후보 처리 현황` 표는 인터뷰의 모든 `RC`를 한 번씩 담고, 열 `처리`는 `PF` / `제외` / `질문` 중 하나다. `내용` 열에 RC 내용을 한 줄로 적어 ID 없이도 읽히게 한다.
- `처리`가 `제외`인 RC는 `제외 범위`에, `질문`인 RC는 `열린 질문`에 `[인터뷰: RC-NNN]` 태그로 나타나야 한다.

### spec.md (21섹션)

`프로젝트 개요`, `조사 근거`, `기능 요구사항`, `범위 제외`, `유스케이스 명세`, `비기능 요구사항`, `제약 조건`, `가정`, `사용자 스토리`, `권한 매트릭스`, `화면 구조`, `데이터 모델 (개념)`, `상태 전이`, `외부 시스템 카탈로그`, `도메인 규칙`, `Candidate Requirements`, `Risk Assessment`, `KPI`, `마일스톤`, `검증 기록`, `변경 이력`

**P0·P1 FR은 인수 기준(`AC`)을 1개 이상 가진다** (`VAL-13`). "무엇이 되면 이 요구가 충족되었는가"를 관찰할 수 있는 결과로 쓴다. 사용자가 명세 승인으로 이 기준을 승인하고, 설계의 시험 계획(`TC`)이 이것을 펼친다. P2는 선택이다.

```markdown
- **FR-001**: 상담 신청을 접수한다.
  - 근거: [PRD: PF-001]
  - 관련 UC: UC-001
  - 인수 기준:
    - AC-001: 필수 항목이 모두 차 있으면 제출 후 접수 완료 화면이 보인다
    - AC-002: 필수 항목이 비면 제출되지 않고 그 칸에 오류 문구가 보인다
```

**모든 `ASM`에 설계 영향을 적는다**(0.16, `VAL-20` 경고). 가정 아래에 `  - 설계 영향: 높음|보통|낮음 — 이유`(이유는 선택)를 둔다. "이 가정이 틀리면 설계가 얼마나 뒤집히는가"이다: `높음`은 플랫폼·인증·데이터 보관·외부 연동·규모처럼 틀리면 여러 설계 문서를 다시 만들어야 하는 것, `낮음`은 한 곳의 값이나 문구만 바뀌는 것. 사실인지 조사하지 않는다. 설계가 무엇에 기대는지를 사용자에게 드러내는 표시이고, 명세 승인 화면은 `높음`인 가정을 따로 보여 주고 사용자가 그 가정으로 설계해도 되는지 확인한다(승인 화면은 허브의 몫이고 게이트는 확인했는지 알 수 없다).

`범위 제외`는 `기능 요구사항` 바로 뒤에 둔다. 인터뷰·PRD에서 Won't로 정했거나 하지 않기로 한 항목과 사유를 `[인터뷰: RC-NNN]` 또는 `[PRD: PF-NNN]` 태그와 함께 적는다. FR을 만들지 않는다. 없으면 `해당 없음`.

**사용자가 제외하기로 한 Must PF**는 이 섹션의 **목록 항목(`- `, `* `, `1. `) 또는 표 행** 한 줄에 `[PRD: PF-NNN]`과 `[사용자 입력]`을 함께 적는다. 게이트(`TRC-02`)는 이 형식만 승인된 제외로 읽는다. HTML 주석, 코드(블록·인라인), 인용문, `\[`로 escape한 태그, 서로 다른 줄에 흩어진 태그는 제외로 읽지 않는다. `TRC-02`는 **형식 검사**이고, 사용자가 실제로 그렇게 말했는지는 게이트가 알 수 없다. 그것은 허브의 사용자 확인과 승인 기록(`approve --note`)이 담당한다.

- FR은 `기능 요구사항` 아래 `### P0|P1|P2` 소제목과 `- **FR-NNN**` 불릿으로 정의하고, 하위 불릿에 `근거:`, `관련 US|UC|SCR:`를 쓴다.

- 시험 시나리오는 `07-test-plan.md`의 `### TC-NNN 제목` 헤딩이 정의이고, 블록 안의 `- 근거: ID, ID`(AC·UC·NFR 등)와 `- 실행: cli|browser|device|manual`, `manual`이면 `- 수동 사유:`(자동화하지 않는 근거와 대상 브라우저·기기)를 읽는다.
- 모든 문서의 `## 변경 이력` 구간의 ID 는 정의 없는 ID 검사(`IDN-02`)에서 제외하고, 그 표에서 헤더에 `삭제`가 든 열의 ID 는 결번(`IDN-03`)으로 보지 않는다. 삭제한 ID 는 여기에 적는다 (코드 블록에 숨기지 않는다).
- 설계 문서가 `BI-NNN`을 참조하면 `docs/06-build/issues.md`가 그 정의다.
- Task는 `- [ ] **T-NNN** ... (covers: ID, ID / ... / check: TC-NNN, TC-NNN)  deps: T-NNN` 줄이고, `### Wave N` 소제목 아래에 둔다. `check:`는 그 Task가 테스트 코드로 구현할 시나리오이고, 없으면 `check: -`라고 쓴다.
- Task의 체크박스는 설계에서 `- [ ]`로 두고 구현 중에도 바꾸지 않는다 (승인 해시 대상이다). 구현 진행은 구현 단계의 기록에 둔다.
- `변경 이력` 섹션의 ID는 정의 없는 ID 검사(IDN-02)에서 제외한다. 삭제한 ID를 거기에 적기 때문이다.
- 문서 머리의 `> 상태:`, `> 작성일:` 줄은 첫 25줄 안에서 읽는다.
- 코드 블록(```) 안의 내용은 검사하지 않는다.
- 헤딩 번호(`## 1. 요약`)는 섹션 이름 비교에서 무시하고 `FMT-02`로 경고한다.

## 구현과 시험

설계 승인 뒤의 단계다. 오케스트레이터는 `/design-to-build`, 결정적 도구는 `node scripts/build.js`, 설계안은 `proposals/build-stage.md`.

### 시작 조건과 코드 위치

- **설계 승인이 유효해야 한다** (설계 게이트 `--approved` 통과, 상류 해시 포함). 무효이면 `build.js`가 Task 를 내주지 않고 검증하지 않는다.
- 앱 코드는 프로젝트 루트의 **`app/`** 에 둔다. 설계 문서의 파일 경로는 `app/` 기준이다. `01-tech-stack.md` `명령` 표의 명령은 `app/`에서 실행한다.
- 테스트는 **각 테스트(testcase) 이름에 TC ID** 를 넣는다. 검증은 결과 파일의 testcase 이름·classname 과 그것을 감싸는 testsuite 이름에서 TC ID 를 찾는다 (describe 를 testsuite 로 내보내지 않는 러너가 있으므로 describe 이름만으로는 보장되지 않는다. 주석은 인정하지 않는다).

### 개발 진행 기록

`build.json`의 Task 마다 `work`(개발 진행)를 둔다. **완료 판정은 계속 `verify`만 한다.**

| 상태 | 명령 | 뜻 |
|------|------|----|
| 개발 중 | `build.js start <T>` | 개발자에게 맡겼다 |
| 검증 대기 | `build.js handoff <T> --files --note --decisions` | 개발자가 돌아왔다 (바꾼 파일·설계와 다른 점·결정 필요) |
| 중단 | `build.js pause <T> --reason --files` | 사용량 제한·세션 종료 등으로 끊겼다. **검증 실패 횟수에 넣지 않는다** |

- `next`는 검증 대기 → 중단(재개) → 실행 가능 순으로 안내한다. 새 세션도 이 기록으로 이어 간다.
- **조건부 병렬**: 개발 중인 Task 가 있으면 `start`는 의존 관계(deps 로 이어짐)가 없고 파일(`file:`)이 겹치지 않는 Task 만 허용한다. 파일이 지정되지 않은 Task 는 함께 시작하지 않는다.
- **검증 직렬화**: `verify`는 다른 Task 가 개발 중이면 거부하고, 실행하는 동안 잠금(`build.lock`)을 둔다. 잠금이 있으면 `start`·다른 `verify`·`test-run`을 거부한다 (1시간 넘은 잠금은 남은 것으로 본다). 실행 전후의 앱 지문이 다르면(검증 중 파일 변경) 결과를 버린다.

### 완료 판정

- **완료는 `build.js verify <T-NNN>`만 기록한다.** `install`(성공 기록이 없거나 `--install`일 때) → `lint` → `build` → 시험 명령을 실제로 실행하고, 실행한 명령이 모두 통과하고, 그 Task 의 `check:` 중 `manual`이 아닌 TC 가 모두 확인되어야 통과다. 선행 Task 가 검증되지 않았거나 미해결 설계·명세·하네스 결함에 막힌 Task 는 검증하지 않는다.
- **시험 명령의 범위**: 실행 위치가 없는 시험 명령은 매번 돌린다. 실행 위치가 있는 시험 명령은 **이 Task 나 이미 완료된 Task 가 그 실행 위치의 TC 를 맡았을 때만** 돌린다 (화면이 생기기 전 Task 를 화면 시험이 막지 않게, 한번 생긴 뒤에는 회귀 확인으로 계속). 건너뛴 명령은 기록에 남긴다. 시험 단계의 `test-run`은 모든 명령을 돌린다.
- **TC 확인은 결과 파일(JUnit XML)로 한다.** 결과 파일이 있는 명령은 실행 전에 옛 파일을 지우고, 실행 뒤에 TC 마다 `통과`·`실패`·`건너뜀`·`결과에 없음`을 정한다. 한 TC 에 테스트가 여럿이면 하나라도 실패면 실패, 통과가 있으면 통과, 모두 건너뜀이면 건너뜀이다. 담당 TC 가 통과가 아니거나 결과 파일이 만들어지지 않으면 검증 실패다. 속성값 안의 `>`·엔티티·주석을 바르게 읽는다.
- 결과 파일이 설정되지 않은 설계에서는 앱 코드에 TC ID 가 있는지로 대신한다 (`perTc: false`). 건너뛴·실행되지 않은 테스트를 구별하지 못하므로 `VAL-16`, `TST-08`로 경고한다.
- 결과는 `완료`·`실패`·`실행 불가`(실행 파일을 찾지 못함)·`충돌`(포트 사용 중 같은 환경 충돌, 또는 검증 중 파일 변경)이다. 실행 불가와 충돌은 완료가 아니고, **실패 횟수에는 코드 실패만 넣는다.**
- 검증 통과 때 **Task 지시서의 해시와 지시서 판**을 기록한다. 지시서에는 Task 줄, 덮는 요구사항 원문, 담당 TC, 파일 명세, 명령 표의 발췌와 **참조 설계 문서(데이터 모델·API·UI·와이어프레임·아키텍처)의 내용 해시**가 들어간다. 재승인 뒤 지시서 해시가 달라졌거나 지시서 판이 기록과 다르면(옛 기록 포함) 완료 Task 는 **재검증 필요**다.
- 통과하면 `verify`가 구현 기록에 Task 블록을 쓴다 (handoff 의 바꾼 파일·설계와 다른 점, 또는 `--note`). 다시 검증하면 그 블록에 재검증 줄을 더한다.
- `08-tasks.md`의 체크박스는 바꾸지 않는다 (설계 승인 해시 대상).

### 구현 중 보고 (`docs/06-build/issues.md`)

에이전트는 승인된 설계·명세를 고치지 않는다. 개발자·시험자는 `결정 필요`로 보고하고 오케스트레이터가 분류한다.

| 유형 | 판단 | 처리 | 멈춤 |
|------|------|------|------|
| `코드 결함` | 설계는 맞고 코드가 틀림 | 개발자가 고치고 재검증 | 아니오 |
| `구현 차이` | 그 Task 안에서 끝나는 차이 | 진행하고 기록. 구현이 끝날 때 설계 정정 또는 `기록` | 아니오 |
| `설계 결함` | 다른 Task·설계 문서에 영향, **설계 문서끼리 모순** (애매하면 여기) | 사용자 결정 → 설계 수정·재승인(권고) → 영향 Task 재검증 | 영향 Task 와 그 뒤 Task |
| `명세 결함` | 요구가 모순·검증 불가 | 사용자 결정 → 명세·설계 수정·재승인 | 영향 Task 와 그 뒤 Task |
| `하네스 결함` | 하네스(검증 스크립트·지시서·지침)가 올바른 결과를 잘못 판정 | 사용자 결정 → 임시 패치(프로젝트 사본) 또는 하네스 원본 수정 | 미해결이면 영향 Task 와 그 뒤 Task |

- 표: `| ID | 발견 | 유형 | 영향 | 상태 | 내용 | 처리 |`. `ID`는 `BI-NNN`, `영향`은 Task ID 목록 또는 `전체`. 닫힌 행은 `처리`를 쓴다.
- 상태: `코드 결함`·`구현 차이` = `미해결`/`해결`/`기록`, `설계 결함`·`명세 결함` = `미해결`/`해결` (`기록`으로 닫지 않는다), `하네스 결함` = `미해결`/`임시 패치`/`원본 반영`.
- **고치는 방법은 `build.js issue add|set`뿐이다.** 고치기 전에 제목·표 구조·중복 ID·칸 수를 검사하고, 한 행만 바꾸고, 고친 뒤 다시 읽어 제목·다른 행이 그대로인지 확인한다. 어긋나면 원본을 되돌리고 실패한다.
- 이미 내려진 사용자 결정(예: 설계 문서끼리 모순인 차이를 `기록`으로 둔 것)은 분류 기준이 바뀌어도 소급해 바꾸지 않는다.
- **하네스 지문**: `harness.json`과 지금의 하네스 파일이 다르면 `하네스 결함` 보고(`임시 패치` 또는 `원본 반영`)가 있어야 한다 (`BLD-08`). `임시 패치`는 원본 반영 전까지 경고(`BLD-09`)로 남고 인수 승인 화면에 드러낸다.

### 구현 기록 (`docs/06-build/build-log.md`)

- 필수 섹션 `Task 기록`. 검증을 통과한 Task 마다 `### T-NNN 제목` 블록과 `- 설계와 다른 점:` 줄(없으면 "없음"). `verify`가 쓴다.
- 제목은 `# 구현 기록`이다. 기록·보고 문서의 제목·필수 표가 깨지면 `BLD-07`.

### 시험 보고서 (`docs/07-test/test-report.md`)

- 필수 섹션 `요약`, `시나리오 결과`. 표 `| TC | 실행 | 결과 | 증거 | 확인자 | 비고 |`에 시험 계획의 모든 TC 가 한 번씩.
- `결과`: `통과` / `실패` / `실행 불가` / `면제`. 자동 TC 의 통과는 최근 `build.js test-run`(기록 `docs/_gate/test.json`)이 통과하고, 결과 파일에서 그 TC 가 `통과`일 때만 (결과 파일이 없는 설계는 코드에 TC ID 가 있을 때). 결과 파일은 `docs/07-test/_evidence/`에 보관된다. `manual`의 통과에는 `확인자`(사용자). `면제`에는 `비고`에 사유.
- 요약에 `- 시나리오 N개: 통과 a · 실패 b · 실행 불가 c · 면제 d` 줄이 있고 결과 표와 같다 (`TST-10`).
- **시험의 근거**: `test-run`은 앱 지문(코드·시험 코드·설정·잠금 파일, 생성물·결과물·로그 제외)과 시험 계획·명령 표의 해시를 `test.json`의 `basis`에 남긴다. 지금과 다르면 다시 시험한다 (`TST-09`). 근거가 없는 옛 기록도 다시 시험한다.
- 인수 승인(`gate.js approve test`)의 대상은 시험 보고서, 상류는 `spec.md`·`08-tasks.md`·`test.json`이다 (시험을 다시 돌리면 인수 승인이 낡는다).

### 인터뷰 확정 기록

- 사용자가 인터뷰를 확정하면 `node scripts/gate.js confirm interview --by <이름> [--note]`로 `docs/01-interview/_confirmation.md`(정리본 해시)를 남긴다. 상태가 `확정`이 아니거나 다른 내용 오류가 있으면 남기지 않는다.
- 상태가 `확정`인데 기록이 없거나 그 뒤 정리본이 바뀌었으면 `VAL-17` (인터뷰·PRD 게이트, `status`의 `confirm_interview`). 다른 프로젝트에서 가져온 정리본은 사용자가 재사용을 확인한 뒤 `--note "재사용: <출처>"`로 확정한다.

## 게이트 실행과 기록

- 게이트는 종료 코드로 결과를 말한다: `0` 통과, `1` 규칙 위반, `2` 사용법 오류.
- 실행할 때마다 `docs/_gate/<단계>-<YYYYMMDD-HHMM>.md`에 **규칙별 결과와 종료 코드**를 기록한다.
- 게이트가 실패하면 허브는 사유를 사용자에게 보여 주고 멈춘다. 자동으로 우회하지 않는다.

### 실행 방법

구현: `scripts/gate.js` (Node.js, 외부 의존성 없음). 여섯 단계(`interview`, `prd`, `spec`, `design`, `build`, `test`)를 지원한다.

```
node scripts/gate.js status [--root <경로>] [--json]
node scripts/gate.js <단계> [--approved] [--root <경로>] [--json] [--no-log]
node scripts/gate.js approve <단계> --by <승인자> [--note <메모>] [--root <경로>]
node scripts/gate.js confirm interview --by <확정자> [--note <메모>] [--root <경로>]
node scripts/gate.js init [--root <경로>]
```

- `status`는 산출물·게이트·승인 파일에서 현재 진행 상태와 다음 할 일(`next.action`)을 계산한다. 별도 상태 파일이 없다. 승인 파일의 `상류 해시`가 현재 상류 문서와 다르면 `stale`(상류 변경 감지)로 표시하고 어느 상류 문서가 바뀌었는지(`staleBy`) 알린다. 상류 해시가 없는 옛 승인 파일은 수정 시각으로 판단한다. 파일은 만들지 않고 종료 코드는 항상 0이다.
- `<단계>`만 주면 **내용 검사**를 한다(승인 전에 허브가 결과를 사용자에게 보여 줄 때).
- `--approved`를 더하면 그 단계를 **나가는 조건**(`APR-01`, `APR-02`, `APR-03`)까지 검사한다.
- `approve`는 **사용자가 승인한 뒤에만** 호출한다. 내용 검사를 먼저 통과해야 `_approval.md`를 만들고, 기존 승인 파일은 `.bak`으로 보존한다.
- 테스트: `npm test` (`scripts/test/`). 스킬·에이전트 점검: `npm run lint` (`scripts/lint-skills.js`)

### 구현 도구

```
node scripts/build.js init                       # 구현 기록·보고 파일, app/, 하네스 지문(없을 때) 생성
node scripts/build.js doctor                     # 시험 환경 표의 확인 명령 실행
node scripts/build.js status | next [--json]     # Task 진행, 지금 할 일 (검증 대기·중단·개발 중·실행 가능·함께 시작 가능)
node scripts/build.js brief <T-NNN>              # Task 지시서 (지시서 판, 근거 문서 판)
node scripts/build.js start <T-NNN>              # 개발 시작 (병렬 조건 검사)
node scripts/build.js handoff <T-NNN> [--files] [--note] [--decisions]   # 검증 대기
node scripts/build.js pause <T-NNN> --reason [--files]                   # 중단 (실패 횟수 아님)
node scripts/build.js verify <T-NNN> [--install] [--note]                # 명령 실행으로 검증하고 기록
node scripts/build.js test-run                   # 시험 단계 전체 실행과 증거·근거 해시
node scripts/build.js issue add|set ...          # 구현 중 보고 (행 단위 안전 수정)
```

- 다음 Task 는 deps 가 모두 완료이고 미해결 설계·명세 결함에 막히지 않은 것 중 재검증 필요 → 실패 → 할 일, 낮은 Wave 순이다. Wave 는 정렬 기준이고, 막힌 Task 가 관계없는 Task 를 막지 않는다.

```
node scripts/plan.js check [<계획>]                 # 계획 검증 (생략하면 전부)
node scripts/plan.js next <계획> [--json]           # 지금 실행할 노드
node scripts/plan.js confirm <계획> <체크포인트>     # 사용자 확인 기록
node scripts/plan.js done <계획> <노드>              # reconcile 노드 완료 기록
node scripts/plan.js reset <계획>                   # 진행 기록 삭제
```

- 노드의 완료는 **산출물 존재**(review는 관점별 파일, gate는 검사 통과)로 판정하고, 체크포인트가 있으면 사용자 확인까지 필요하다. 그래서 세션이 끊겨도 이어서 계산한다.
- 병렬 노드(선행 관계가 없는 노드)는 한 번의 응답에서 동시에 호출한다. 출력이 겹치면 `plan.js check`가 거부한다.

### 면제

사용자는 **사유를 적고** 오류를 면제할 수 있다. `docs/_gate/waivers.md`에 기록한다.

```markdown
## {YYYY-MM-DD} {단계} {규칙 ID}
- 대상: {파일·ID}
- 사유: {왜 면제하는가}
- 승인자: {이름}
```

면제된 규칙은 게이트 로그에 `면제`로 표시한다. 면제는 해당 항목에만 적용되고, 같은 규칙의 다른 위반에는 적용되지 않는다.
