# 용어와 약어

하네스 문서에서 쓰는 약어와 용어의 뜻. 규칙은 `artifact-contract.md`가 정하고, 이 문서는 뜻만 설명한다.

표의 `단계`는 그 ID를 처음 만드는 단계다: 발견(인터뷰) → PRD → 명세 → 설계.

---

## ID 접두사

형식은 `접두사-NNN`(예: `RC-001`)이다. 번호는 3자리이고 한 번 쓴 번호는 재사용하지 않는다.

### 인터뷰에서 만드는 것

| 접두사 | 영문 | 뜻 | 예 |
|--------|------|----|----|
| `RC` | Requirement Candidate | **요구사항 후보.** 인터뷰에서 사용자가 말한 "이런 게 필요하다". 아직 확정이 아니고, PRD에서 기능·제외·질문 중 하나로 처리된다 | `RC-003` 친구와 러닝 기록을 공유한다 |
| `SC` | Scenario | **시나리오.** 사용자가 서비스를 쓰는 한 이야기 (상황 → 행동 → 기대 결과 → 예외) | `SC-001` 출근 전 러닝 기록 확인 |
| `D` | Decision | **결정.** 사용자가 명시적으로 정한 것, 기각한 대안과 이유 포함 | `D-002` 1차 버전은 모바일 앱만 |
| `A` | Assumption | **가정(인터뷰).** 확인되지 않았지만 진행을 위해 둔 것 | `A-001` 사용자는 한국어만 쓴다 |
| `C` | Constraint | **제약(인터뷰).** 일정, 예산, 기술 등 이미 정해진 조건 | `C-001` 2개월 안에 출시 |
| `Q` | Question | **열린 질문.** 답이 없거나 사용자도 모르는 것 | `Q-004` 결제 수단은 무엇으로? |

### PRD에서 만드는 것

| 접두사 | 영문 | 뜻 | 예 |
|--------|------|----|----|
| `PF` | Product Feature | **제품 기능.** PRD의 `핵심 기능` 표에 있는 기능 하나. 근거로 `RC`를 가진다 | `PF-001` 러닝 기록 공유 |

### 명세(spec.md)에서 만드는 것

| 접두사 | 영문 | 뜻 | 예 |
|--------|------|----|----|
| `FR` | Functional Requirement | **기능 요구사항.** "시스템이 무엇을 해야 한다" | `FR-001` 사용자는 러닝 기록을 친구에게 공유할 수 있다 |
| `AC` | Acceptance Criterion | **인수 기준.** FR이 충족되었다고 판단하는 관찰 가능한 결과. P0·P1 FR 아래에 둔다 | `AC-001` 저장을 누르면 기록이 목록 맨 위에 보인다 |
| `NFR` | Non-Functional Requirement | **비기능 요구사항.** 성능·보안·접근성 같은 품질. 수치가 있어야 한다 | `NFR-001` 기록 저장 응답 P95 1초 이내 |
| `CON` | Constraint | **제약 조건(명세).** 플랫폼, 규제 등 | `CON-001` iOS 14+, Android 8+ |
| `ASM` | Assumption | **가정(명세).** 합리적 추론. 반드시 `[가정]` 태그를 붙인다 | `ASM-001` 주 사용자는 한국어 사용자 |
| `US` | User Story | **사용자 스토리.** "AS 역할 / I WANT 기능 / SO THAT 가치" 형식 | `US-001` |
| `UC` | Use Case | **유스케이스.** 행위자가 목표를 달성하는 상세 흐름 (주 흐름 + 대안 흐름) | `UC-001` |
| `SCR` | Screen | **화면.** 화면 하나 | `SCR-005` |
| `CAND` | Candidate Requirement | **후보 요구사항(명세).** 조사·여정에서 나온 제안. 사용자가 확인하기 전에는 요구사항이 아니다 | `CAND-003` |
| `RISK` | Risk | **리스크** | `RISK-001` |
| `KPI` | Key Performance Indicator | **핵심 성과 지표** | `KPI-001` |
| `MS` | Milestone | **마일스톤** | `MS-001` |

### 설계에서 만드는 것

| 접두사 | 영문 | 뜻 | 예 |
|--------|------|----|----|
| `TC` | Test Case | **시험 시나리오.** `07-test-plan.md`의 `### TC-NNN`. 근거(AC·UC·NFR), 실행 위치, 절차, 기대 결과를 가진다 | `TC-001` 거리 누락 시 저장 차단 |
| `T` | Task | **구현 작업.** `08-tasks.md`의 체크박스 항목 하나. `check:`에 담당 TC를 적는다 | `T-001` |

### 구현·시험에서 만드는 것

| 접두사 | 영문 | 뜻 | 예 |
|--------|------|----|----|
| `BI` | Build Issue | **구현 중 보고.** 개발자·시험자가 올린 문제를 `issues.md`에 유형(코드 결함·구현 차이·설계 결함·명세 결함·하네스 결함)과 함께 기록한 것. `build.js issue`로만 고친다 | `BI-001` 공유 모듈이 순환 의존을 만든다 |

- **하네스 결함**: 하네스(검증 스크립트·지시서·지침)가 올바른 결과를 잘못 판정하는 것. 상태는 `미해결` → `임시 패치`(프로젝트 사본을 고침) → `원본 반영`(하네스 원본에 반영).
- **하네스 지문**: 프로젝트에 복사된 하네스 파일의 해시 기록(`docs/_gate/harness.json`). 프로젝트 안에서 하네스를 고치면 구현 게이트가 알아챈다.
- **지시서 판·근거 문서 판**: Task 지시서 형식의 판과, 지시서가 가리키는 설계 문서의 내용 해시. 바뀌면 완료한 Task 를 다시 검증한다.
- **실행 위치(시험 명령)**: 명령 표의 시험 명령이 돌리는 시나리오의 실행 위치. 그 실행 위치의 시나리오를 맡은 Task 부터 Task 검증에서 그 명령을 돌린다.

### ID가 아닌 번호

| 표기 | 뜻 |
|------|----|
| `R3` | **Round.** 인터뷰 로그의 3번째 라운드. 근거를 라운드 번호로 가리킬 때 쓴다 |
| `T1` ~ `T12` | **토픽(Topic).** 인터뷰에서 다루는 주제 12개 (아래 표). Task의 `T-001`과 다르다: 하이픈과 3자리 숫자가 없다 |

## 헷갈리기 쉬운 것

| 구분 | 차이 |
|------|------|
| `RC` vs `FR` | `RC`는 사용자가 말한 후보(인터뷰), `FR`은 명세에서 확정한 요구사항. `RC` → `PF` → `FR`로 이어진다 |
| `RC` vs `CAND` | `RC`는 **사용자**가 말한 것. `CAND`는 **조사·분석**이 제안한 것. 둘 다 아직 확정 아님 |
| `PF` vs `FR` | `PF`는 PRD의 기능(제품 관점, 몇 줄). `FR`은 명세의 요구사항(시스템 관점, 상세). 하나의 `PF`가 여러 `FR`이 될 수 있다 |
| `A` vs `ASM` | 같은 "가정"이지만 `A`는 인터뷰 기록, `ASM`은 명세 항목. 인터뷰의 `A`가 명세에서 `ASM`이 된다 |
| `C` vs `CON` | 같은 "제약"이지만 `C`는 인터뷰, `CON`은 명세 |
| `SC` vs `SCR` | `SC`는 시나리오(이야기), `SCR`은 화면 |
| `T1` vs `T-001` | `T1`은 인터뷰 토픽, `T-001`은 구현 작업 |

## 출처 태그

### 인터뷰 항목 (D, RC, SC, A, C에 붙임)

| 태그 | 뜻 |
|------|----|
| `[U]` | User. 사용자가 직접 말함 |
| `[S]` | Suggested. Claude가 제안하고 사용자가 수락함 |
| `[I]` | Inferred. Claude의 추론이고 사용자는 아직 확인하지 않음. 요구사항 후보 표에 넣지 않는다 |

### 근거 태그 (PRD의 근거 열, 명세 FR의 `근거:`)

| 태그 | 뜻 | 성격 |
|------|----|------|
| `[인터뷰: RC-NNN]` | 인터뷰의 요구사항 후보에서 나옴 | 사용자 유래 |
| `[PRD: PF-NNN]` | 승인된 PRD의 기능에서 나옴 | 사용자 유래 |
| `[사용자 입력]` | 대화에서 사용자가 직접 말함 (기록 번호 없음) | 사용자 유래 |
| `[조사: 출처]` | 웹 조사 등 외부 근거 | 외부 근거 |
| `[경쟁 분석: 서비스명]` | 경쟁 서비스에서 확인한 사실 | 외부 근거 |
| `[사용자 여정: 이름]` | 여정을 분석하다 도출 | 도출 근거 |
| `[가정]` | 가정임을 명시하는 표시. `ASM`에 필수 | |

**FR은 사용자 유래 근거가 최소 하나 있어야 한다.** 외부 근거와 도출 근거만 있으면 `CAND`다.

### 기타 표시

| 표기 | 뜻 | 쓰는 곳 |
|------|----|--------|
| `[일반 지식 폴백]` | 웹 검색 없이 모델의 일반 지식으로 쓴 부분 | pre-research |
| `[사전자료]` | 이미 있던 자료에서 채운 항목 (사용자 확인 전) | interview 커버리지 |
| `[추론]` | 아이디어 문장에서 읽은 항목 (사용자 확인 전) | interview 커버리지 |
| `[스케치]` | 정형 명세 없이 임시로 만든 요구사항 | design-architect (계약 이후 제거 예정) |
| `[보강]` | 기존 산출물에 나중에 추가한 항목 | pre-research |

## 우선순위

| 정식 | 인터뷰·PRD | 명세·설계 | 뜻 |
|------|-----------|----------|----|
| Must | `Must` | `P0` | 없으면 출시할 수 없다 |
| Should | `Should` | `P1` | 중요하지만 1차에서 빠져도 출시는 된다 |
| Could | `Could` | `P2` | 있으면 좋다 |
| Won't | `Won't` | 범위 제외 | 이번에는 하지 않기로 했다 (FR을 만들지 않는다) |

- **MoSCoW**: 위 4단계 우선순위 기법의 이름 (Must / Should / Could / Won't).
- **후보 vs 확정**: 인터뷰의 우선순위는 후보이고, **PRD 승인으로 확정**된다.

## 게이트 규칙 ID

게이트 스크립트가 검사하는 규칙의 번호다. 접두사별로 영역이 다르다.

| 접두사 | 영역 | 예 |
|--------|------|----|
| `FMT` | 구조·형식 (Format) | `FMT-01` 필수 섹션 존재 |
| `IDN` | ID (Identifier) | `IDN-01` ID 정의 중복 없음 |
| `VAL` | 값 (Value) | `VAL-04` FR에 근거 필드 |
| `REF` | 참조 무결성 (Reference) | `REF-01` 가리키는 ID가 실존 |
| `TRC` | 추적 사슬 (Trace) | `TRC-01` 사라진 요구사항 후보 없음 |
| `APR` | 승인 (Approval) | `APR-01` 이전 단계 승인 파일 존재 |
| `REV` | 리뷰 처리 (Review) | `REV-01` 미해결 CRITICAL 리뷰 이슈 없음 |
| `DSN` | 디자인 방향 (Design direction) | `DSN-01` 선택한 시안과 기각 사유가 있음 |

규칙 ID는 두 자리(`FMT-01`)이고, 산출물 ID는 세 자리(`RC-001`)다.

## 단계와 구성 요소

| 용어 | 뜻 |
|------|----|
| 발견 (discover) | 아이디어를 인터뷰와 조사로 구체화하는 단계. 산출물은 `interview.md`(필수)와 `02-research/*`(선택) |
| PRD | Product Requirements Document. 제품 요구사항 문서. 사용자가 읽고 승인하는 짧은 문서. 승인 후 수정하지 않는다 |
| 명세 (spec) | `spec.md`. ID가 붙은 정형 요구사항 문서. 이후 변경은 여기에만 반영한다 |
| 설계 (design) | 기술 스택, 데이터·API, UI, 아키텍처, 파일 맵, 작업 목록 |
| 게이트 (gate) | 다음 단계로 넘어가도 되는지 검사하는 스크립트 |
| 승인 (approval) | 사용자의 승인 기록. `_approval.md`에 승인한 문서의 해시를 함께 적는다 |
| 면제 (waiver) | 사용자가 사유를 적고 게이트 오류 하나를 통과시키는 것 |
| 허브 (hub) | 입력을 접수해 경로를 정하고 단계 순서·게이트·승인을 관리하는 스킬 |
| 스킬 (skill) | 메인 세션이 따르는 절차서. 사용자와 대화하는 일에 쓴다 |
| 서브에이전트 | 격리된 컨텍스트에서 일하는 역할. 대화하지 못하고 결과를 파일과 요약으로 돌려준다. 예: `prd-writer` |
| 리뷰어 | 산출물을 읽고 지적만 하는 서브에이전트. 직접 고치지 않는다 |
| 추적 사슬 | `RC` → `PF` → `FR` → `T` 로 이어지는 연결. 빠지거나 지어낸 요구사항을 찾는 데 쓴다 |
| 실현 요건 점검 | 아이디어를 실현하려면 암묵적으로 필요한데 사용자가 말하지 않은 것을 모델이 제안하고 사용자가 수락·기각·보류하는 인터뷰의 마지막 점검 |
| 시안 (variant) | 설계 단계에서 방향을 달리해 그린 화면 초안(`V-A`, `V-B` …). 사용자가 비교해 하나를 고르거나 조합한다. 기록은 `_variants/`에 둔다 |
| 디자인 토큰 | 선택한 방향의 색·글꼴·글자 크기·간격·모서리·움직임 값. 구현이 따르는 기준이다 |
| 설계 영향 | 명세의 가정(`ASM`) 아래에 적는 표시(높음/보통/낮음). 그 가정이 틀리면 설계가 얼마나 뒤집히는가. 사실인지 조사하지 않고, 설계가 무엇에 기대는지를 승인 화면에서 사용자에게 드러내는 데 쓴다 |
| 시선 위계 | 화면에서 먼저 보여야 할 것의 순서. 모든 요소가 같은 비중이면 안 된다 |
| 스냅샷 | 승인 시점에 고정된 문서. PRD가 해당 |
| SSOT | Single Source of Truth. 단일 진실 원천. 변경은 한 곳(`spec.md`)에만 한다 |

## 기술 약어

| 약어 | 뜻 |
|------|----|
| MVP | Minimum Viable Product. 가장 작게 출시할 수 있는 1차 버전 |
| ERD | Entity Relationship Diagram. 데이터 엔티티와 관계를 그린 도표 |
| API | Application Programming Interface. 프로그램끼리 데이터를 주고받는 약속 |
| ADR | Architecture Decision Record. 아키텍처 결정 기록 (결정과 이유) |
| SVG | 벡터 이미지 형식. 와이어프레임 파일 형식으로 쓴다 |
| WCAG | Web Content Accessibility Guidelines. 웹 접근성 지침 |
| LOC | Lines Of Code. 코드 줄 수 (파일 맵에서 파일당 300줄 이하 권장) |
| Wave | 의존성 순서로 묶은 구현 단계. 앞 Wave가 끝나야 다음을 시작한다 |
| P95 | 95번째 백분위. 요청의 95%가 이 시간 안에 끝난다는 뜻 (NFR 수치 표기) |
