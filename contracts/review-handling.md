# 리뷰 지적 처리 규칙

> 버전: 0.1 · 적용: 설계 리뷰(`design-architect` Step 8, `design-reviewer` 역할), 명세 리뷰(`spec-planner`)
> 게이트 규칙: `REV-01`~`REV-03`은 `contracts/artifact-contract.md`. 이 문서는 지적을 **어떻게 분류하고 누가 결정하는지**를 정한다.

## 원칙

1. **처리 권한은 지적의 성격(유형)이 정한다.** 리뷰어 몇 명이 같은 말을 했는지(합의 수)는 **검토 순서**에만 쓴다. 합의가 많아도 사용자가 정할 일을 대신 정하지 않고, 단독 지적이어도 명백한 오기는 고친다.
2. 지적마다 **유형, 처리, 근거**를 기록한다. 기록 없는 수정을 하지 않는다.
3. 사용자가 말하지 않은 것을 확정하지 않는다. 승인된 명세와 사용자가 확인한 선택을 리뷰어의 제안으로 바꾸지 않는다.

## 유형과 처리

| 유형 | 무엇인가 | 처리 | 사용자에게 묻나 |
|------|----------|------|-----------------|
| `불일치` | 문서 사이 모순, 이름·번호·개수 오기, **기준이 되는 문서**(승인된 명세, 사용자가 확인한 설계)와 다른 곳 | 기준 문서를 따라 **수정**. 근거에 "어느 문서의 어디가 기준인지"를 적는다 | 아니오 |
| `구현` | 승인된 명세 범위 안의 방법·도구·테스트·구조·상세 보완 | 근거를 적고 **수정**. 단, 사용자가 확인한 선택(체크포인트에서 승인한 기술 스택, 화면 구성 등)을 뒤집는 것은 `요구·정책` | 아니오 |
| `요구·정책` | 기능 추가·삭제, 동작·화면·문구 정책, 우선순위, 범위, 명세에 고정된 선택, 사용자가 확인한 선택을 바꾸는 것. **어느 쪽이 기준인지 불분명한 불일치**도 여기 | **사용자 결정** 없이 수정하지 않는다. 사용자가 "그대로 둔다/후보로 남긴다"를 고르면 `기록` (설계에 반영하지 않는다) | 예 |
| `선호` | 취향·권장·개선 제안 (대부분 INFO) | **기록**. 수정하지 않는다 | 아니오 |

- 리뷰어가 문서를 잘못 읽은 **오해**는 `기각`이다. 유형 칸에는 원래 지적이 해당하는 유형을 쓰고, 근거에 "어느 문서의 어디를 보면 되는지"를 적는다.
- 명세를 바꿔야 하는 `요구·정책` 결정은 허브의 "명세가 바뀌는 결정" 절차를 따른다 (지금 명세를 고친다 / 명세는 그대로 두고 후보로 남긴다 / 보류).

## 심각도별 의무

| 심각도 | 의무 |
|--------|------|
| CRITICAL | 유형과 관계없이 **반드시 닫는다**: `수정`, `기각`(근거 필수), `사용자 결정` 중 하나. 닫히지 않으면 `REV-01`로 승인이 막힌다 |
| WARN | 처리 기록에 모두 올린다. 빠지면 `REV-02` 경고 |
| INFO | 생략해도 된다. 올리면 `선호`·`기록`이 보통이다 |

## 사용자에게 묻는 방법

- `요구·정책` 지적은 **모아서 한 번에** 묻는다. 한 질문 묶음에 최대 4개. 넘치면 심각도와 영향이 큰 순서로 묻고, 나머지는 `기록`(후보)으로 두되 건수를 사용자에게 알린다.
- 질문에는 지적 내용, 제안, 영향받는 문서를 쓴다. 선택지는 **수정 적용 / 그대로 둔다(기록) / 기각(사유)**.
- 합의 수가 많은 순서로 묻는다. 단독 지적이라는 이유로 묻지 않고 넘기지도, 합의가 많다는 이유로 묻지 않고 고치지도 않는다.

## 기록: `docs/05-design/_review/resolution.md`

리뷰어 출력(`<관점>.json`)은 기계용이고, 처리 기록은 사람이 확인하는 마크다운이다. 승인 해시 대상이 아니다.

```markdown
# 리뷰 처리 기록

| 이슈 | 유형 | 처리 | 근거 |
|------|------|------|------|
| DC-001 | 불일치 | 수정 | wireframes/SCR-001.svg 버튼 문구를 ui-spec 화면 상세(SCR-001)에 맞췄다 |
| FE-003 | 구현 | 수정 | lint 범위를 app/ 로 한정했다 (명세 NFR-004 범위 안) |
| RK-001 | 요구·정책 | 사용자 결정 | 사용자가 공유 링크 만료를 두지 않기로 했다 (그대로 유지) |
| DC-005 | 선호 | 기록 | 표기 통일은 구현 단계에서 정한다 |
```

- `이슈`: 리뷰 JSON의 이슈 ID. 이슈마다 한 행.
- `유형`: `불일치` / `구현` / `요구·정책` / `선호`. `처리`: `수정` / `사용자 결정` / `기록` / `기각`.
- `근거`: 수정이면 **바뀐 문서와 곳**, 기각이면 **사유**, 사용자 결정이면 **사용자가 고른 내용**.
- 게이트가 보는 것: CRITICAL이 닫혔는가(`REV-01`), WARN이 기록에 있는가(`REV-02`), 값이 허용 범위이고 `요구·정책`·`선호`를 사용자 결정 없이 수정하지 않았는가(`REV-03`). **유형을 맞게 골랐는지는 게이트가 알 수 없다.** 그 판단은 이 문서의 표와 사용자 승인 화면이 맡는다.

## 수정을 맡길 때

- 수정을 에이전트 하나에게 일괄로 맡겨도 된다. 단 **지적 ID별로 어느 문서의 어디를 어떻게 바꿨는지** 목록을 돌려받아 처리 기록의 `근거`로 옮긴다. 목록이 없는 수정은 받아들이지 않는다.
- 수정 뒤 `node scripts/gate.js design`을 다시 돌린다. CRITICAL을 `수정`으로 닫았다면 해당 관점의 재확인(`design-reviewer`의 재확인 모드)을 권한다. 게이트가 재확인을 요구하지는 않는다.
- 리뷰는 **1회**다. 한 번 더는 사용자가 요청할 때만 하고 총 2회를 넘지 않는다 (수렴을 보장할 수 없다).

## 아직 없는 것

- 명세 리뷰(`spec-planner`)는 같은 유형 규칙을 쓰지만 기록은 `spec.md`의 `검증 기록` 절에 두고, 게이트 검사는 없다.
- 수정이 실제로 근거대로 이뤄졌는지는 확인하지 않는다 (기록의 정직함은 사용자 승인 화면에서 요약으로 드러낸다).
