# 설계 산출물 안내 (개발 진입점)

> 작성일: 2026-11-03
> 수정: 2026-11-05 (명세 v4 반영, `변경 이력` 참고)

이 폴더는 1인 사용자용 스케줄 관리 칸반보드(Electron + React + TypeScript 데스크톱 앱)의 **설계**다. 개발자는 이 문서에서 시작한다. 코드는 앱 루트 `app/` 안에만 쓰고, `docs/` 아래 문서는 읽기만 한다.

## 명세와 설계의 구분

| 구분 | 위치 | 답하는 질문 | 개발 때 쓰는 법 |
|------|------|-------------|------------------|
| 명세 (spec) | `docs/04-spec/spec.md` | **무엇을, 왜** 만드는가. 요구사항(FR, NFR), 유스케이스(UC), 인수 기준(AC), 도메인 규칙 | "다 됐다"의 기준(AC)을 확인할 때 읽는다. 구현 방식은 여기 없다 |
| 설계 (design) | `docs/05-design/` (이 폴더) | **어떻게** 만드는가. 기술 스택, 데이터, 인터페이스, 화면, 구조, 파일, 시험, 작업 순서 | 구현할 때 매 Task마다 읽는다 |

명세와 설계가 어긋나 보이면 코드를 바꾸지 말고 `결정 필요`로 보고한다. 아래 `미해결 잔존 사항`에 이미 알려진 어긋남이 있다.

## 개발 시 보는 순서

1. **`01-tech-stack.md`로 셋업한다.** 환경(Windows 11, Node.js 24.22.2 권고), 패키지 핀 버전, `app/` 초기화 방법, `명령` 표(install, lint, build, test, test:e2e, package)를 본다.
2. **`08-tasks.md`가 메인 지시서다.** 위에서부터 Task를 하나씩 처리한다. Task 줄은 `covers`(연결된 요구사항), `data`·`api`(관련 엔티티·인터페이스), `file`(만들 파일, `app/` 기준), `check`(그 Task가 시험 코드로 구현할 TC), `deps`(먼저 끝나야 하는 Task)로 읽는다. 줄에 적힌 `임시 가정`은 사용자가 아직 정하지 않은 항목이라는 표시다. Task 번호는 T-001~T-042를 처음 그대로 두고 설계 리뷰에서 더한 Task를 T-043, T-044로 이어 붙였으므로, 실행 순서는 번호가 아니라 `### Wave N` 소제목 아래의 위치다(예: T-043은 Wave 9, T-044는 Wave 5). 명세 v4 반영으로 새 Task는 없다(Task 44개 그대로). 이미 구현된 코드를 다시 고치는 Task는 줄에 `명세 v4 반영 재작업`이, 시험 기대값만 고치는 Task는 `명세 v4 반영: 시험 기대값 수정`이 적혀 있다.
3. **Task마다 아래를 본다.**
   - `06-file-map.md`: `file`에 적힌 파일의 목적, 주요 export, 의존, 예상 LOC. 파일 경로와 의존 관계는 이 문서를 따른다.
   - `07-test-plan.md`: `check`에 적힌 TC의 전제, 절차, 기대 결과. 시험 이름(testcase)에 TC ID를 넣는다.
   - 필요에 따라 `02-data-model.md`, `03-api-spec.md`, `04-ui-spec.md`, `05-architecture.md` (아래 표 참고).
4. **Task를 끝낼 때** `app/`에서 `npm run lint`, `npm run build`, test 명령이 통과해야 한다. 화면 시험(test:e2e)은 browser TC를 맡은 첫 Task(앱 구동 스모크 T-043)부터 돈다. 사람이 하는 시험 5개(TC-131~TC-134, TC-155)는 구현이 끝난 뒤 인수 확인에서 한다.
5. **설계와 다르게 해야 하거나 설계 문서끼리 어긋나면** 임의로 고치지 말고 `결정 필요`로 보고한다.

## 구현 흐름 예시

T-008(날짜 규칙)을 처리하는 순서다.

1. `01-tech-stack.md`로 `app/`을 셋업한 상태에서(T-001~T-002가 끝나 있다) `08-tasks.md`의 T-008 줄을 읽는다. 만들 파일은 `src/shared/domain/date-rules.ts`와 `tests/cli/domain/date-rules.test.ts`, 담당 TC는 TC-001~TC-005, 선행 Task는 T-002다.
2. `06-file-map.md`의 `date-rules.ts` 상세에서 목적, 주요 export, 의존(`src/shared/types/card.ts`)을 확인한다. `src/shared`에는 `electron`, `node:*`, `window` 같은 것을 쓰면 안 된다(`05-architecture.md`의 의존 규칙).
3. `02-data-model.md`에서 `dueDate`가 시각 없는 `YYYY-MM-DD`라는 것, `03-api-spec.md`의 도메인 함수에서 `isOverdue`와 날짜 검사의 시그니처를 확인한다.
4. `07-test-plan.md`에서 TC-001~TC-005의 전제(오늘을 2026-11-03으로 고정), 절차, 기대 결과를 읽고 구현한다. 시험의 이름에 `TC-001` 같은 ID를 넣는다.
5. `app/`에서 `npm run lint`, `npm run build`, test 명령을 돌려 통과를 확인한다. 설계와 다르게 해야 했던 점이 있으면 `결정 필요`로 보고한다.

## 명세 v4 반영 (2026-11-05)

승인된 명세가 v4로 개정되어(인수 뒤 사용자 개선 요청 7건) 설계 문서와 이미 구현된 코드가 영향을 받는다. 변경 7건: (1) 카드를 만들 때 상태를 할 일·진행 중에서 고른다(FR-001, AC-041·AC-042), (2) 마감일을 달력으로 고르는 날짜 입력 칸(FR-004, AC-043), (3) 캘린더에서 칩을 끌어 마감일을 옮긴다(FR-005, AC-044~AC-046), (4) 기본 창에서 5주인 달이 스크롤 없이 보인다(FR-005, AC-048), (5) 우선순위 이름이 `중간`으로 바뀌고 순서가 없음·낮음·중간·높음이다(FR-008, AC-016), (6) 사이드바 필터 목록에 `전체` 항목이 있다(FR-013, AC-047), (7) 기본 화면이 밝은 판이다(FR-014, AC-038). 영향 문서는 `02-data-model.md`, `03-api-spec.md`, `04-ui-spec.md`와 와이어프레임 `SCR-001~SCR-004.svg`, `05-architecture.md`(ADR-013 추가), `06-file-map.md`, `07-test-plan.md`(TC-156~TC-175 추가), `08-tasks.md`이고 `01-tech-stack.md`는 바뀌지 않았다. 새 구현 파일은 없고 시험 파일 `tests/browser/calendar-drag.spec.ts` 한 개가 늘었다(파일 141개). 새 Task도 없다(Task 44개, T-041이 새 시험 파일을 맡는다). 구현은 이미 `app/`에 있으므로 `06-file-map.md`의 `명세 v4 재작업 대상` 표와 `08-tasks.md`의 `명세 v4 반영 재작업` 표시가 있는 Task가 고칠 곳이다. 저장 형식이 같아 `schemaVersion`은 2 그대로다.

## 미해결 잔존 사항

사용자가 정하지 않았거나 설계 단계에서 확인하지 못한 항목이다. 설계는 "지금 설계의 임시 가정"대로 진행하고, 정해지면 영향 Task의 구현과 시험을 고친다. 표의 출처 문서에 선택지와 권고가 있다.

| 번호 | 항목 | 지금 설계의 임시 가정 | 영향 Task | 출처 문서 |
|------|------|------------------------|-----------|-----------|
| 1 | **앱 이름과 데이터 폴더 이름 상수 `APP_DATA_FOLDER`의 값.** 표시용 앱 이름(`package.json`의 `name`/`productName`, 화면 표시)은 아직 없다. 데이터 폴더 이름은 표시 이름과 분리한 상수라서 표시 이름을 나중에 바꿔도 데이터 위치가 바뀌지 않지만, 상수 값 자체는 한 번 정하면 바꾸지 않는다 | 구현 시작 전에 사용자가 두 값을 준다 | T-001, T-002, T-037, T-038, T-041, T-042 | `05-architecture.md` 결정 필요 3, ADR-012, `06-file-map.md` 결정 필요 3 |
| 2 | **개발 실행의 `-dev` 접미사.** 개발 실행(포장하지 않은 실행)은 데이터 폴더 이름에 `-dev`를 붙여 실제 카드 데이터를 건드리지 않게 했다. 설계 리뷰(RK-004)에서 나온 제안이고 사용자가 확인하지 않았다 | 붙인다. 시험은 `--user-data-dir`로 따로 격리한다 | T-037 | `05-architecture.md` ADR-012 |
| 3 | **자산.** SUIT 글꼴 woff2의 확보 방법과 용량, 글꼴 라이선스 원문(SIL OFL 1.1이라는 것은 저장소 README에서만 확인했고 원문은 열어 보지 못했다), 아이콘 도형의 출처, 앱 아이콘 | 라이선스 문구 파일은 원문을 넣는다. 아이콘 도형은 직접 작성한 것으로 보고, 앱 아이콘은 만들지 않는다. 글꼴 확보 방법은 사용자가 정한다 | T-004, T-006, T-042 | `06-file-map.md` 결정 필요 7, `04-ui-spec.md` 결정 필요 11, 수동 시험 TC-133 |
| 4 | **밝은 판 캘린더 칩에서 할 일과 진행 중의 색 차이가 약하다.** 색 차이는 보조 정보이고, 월 보기 칩에는 상태 글자가 없다 | 상태는 칩의 `aria-label`·`title`과 주 보기·`+N건 더 보기` 팝업의 상태 글자 칩으로 보완한다. 색 차이만으로 구분하지 않는다 | T-027, T-033 | `04-ui-spec.md` (SCR-003 칩 설명과 검증 기록) |
| 5 | **Node 버전.** 이 PC는 22.23.2이고 권고는 24.22.2다. 어느 쪽이든 패키지 엔진 범위는 만족한다(eslint 10.14.0의 `engines`는 T-001이 `npm view`로 확인한다) | 구현 시작 전에 사용자가 고른다. `engines.node`는 `>=22.13.0`이고 24를 고르면 `>=24.0.0`으로 바꾼다 | T-001 | `01-tech-stack.md` 결정 필요 4 |
| 6 | **코드 서명과 업데이트 방식.** 오프라인이라 자동 업데이트를 쓰지 않고, 서명하지 않은 설치 파일은 Windows 경고(SmartScreen)가 뜰 수 있다. Electron 45의 지원 종료일은 2027-04-27이라 그 전에 사용자가 새 메이저로 올려야 한다(RK-005, 아래 `Electron 업그레이드 절차`) | 서명하지 않는다. 자동 업데이트·업데이트 확인 코드를 앱에 두지 않는다(NFR-001) | T-042 | `01-tech-stack.md` 결정 필요 6, 호환성 참고사항 |

### 구현 첫 구동에서 확인할 가정

사용자가 정할 일이 아니라 설계 단계에서 실행해 보지 못한 것이다. 첫 Electron 구동(T-043)과 화면 시험 Task에서 확인하고 어긋나면 `설계 결함`으로 보고한다.

- `sandbox: true`와 `"type": "module"`의 호환: preload를 CJS `out/preload/index.cjs`로 내보내는 설정(`electron.vite.config.ts`)이 먹히는지, `window.kanban` 열두 함수가 노출되는지(TC-129). 안 되면 대안 설정이 `06-file-map.md`에 있고, `sandbox: false`로 낮추는 것은 사용자 결정과 설계 재승인이 필요하다.
- `--user-data-dir`이 `app.getPath('userData')`에 반영되는지, `app.setPath`와의 상호작용, `import.meta.dirname`·`ELECTRON_RENDERER_URL`.
- 쓰기 실패 유도(유효한 저장 파일 옆의 `kanban-data.json.bak` 폴더)가 Windows에서 실제 쓰기 실패가 되는지, 읽기 실패 유도(본 파일 자리의 폴더, `EISDIR`), 창 컨텍스트의 `setOffline`, 프로세스 강제 종료, 창 닫기 직전 main에 도착하지 못한 요청이 없는지(TC-152).
- `<dialog>`·`popover`·끌어다 놓기가 Electron 창에서 동작하는지, preload의 `data-theme` 적기 타이밍(첫 화면 색 깜빡임은 수동 TC-131).
- Chromium 자체 요청 완화 후보(`host-resolver-rules`, `setProxy`)와 `file:` 접두사 비교(대소문자·퍼센트 인코딩), 포장 퓨즈(`electronFuses`) 지원. 넷로그 확인은 수동 TC-132, 퓨즈는 수동 TC-155.
- Playwright의 Electron 지원은 experimental이다. 버전을 올릴 때 `browser` TC 전체를 다시 돌린다. 안 되는 TC는 cli 대역으로 옮기는 것을 구현 단계에서 보고한다.

### 해소된 항목

- **보관한 카드의 삭제**: 사용자가 허용으로 정했다(명세 v3 AC-040). 보관한 카드도 보관함 행과 보기 전용 대화상자에서 확인 단계 뒤 삭제할 수 있고 진행 기록이 함께 삭제된다. 수정과 기록 추가는 할 수 없다. 명세 개정 후보는 없다(v3에 반영됐고 NFR-001의 적용 범위 문구도 v3에서 맞췄다).
- **저장 실패 뒤 추가 조작**: 칸 이동·보관·삭제(와 만들기·수정·기록 추가)는 낙관적으로 반영하지 않는다. 저장이 성공한 뒤에 화면이 바뀌고, `SAVE_FAILED`면 화면이 그대로이며 `다시 저장`이 실패한 요청 한 건을 다시 보낸다. 밝기 전환만 즉시 반영하고 저장 실패 알림을 보인다(사용자 결정 D2).
- **읽기 실패 안내**: 앱 안 복구 동작은 만들지 않고 안내 문구만 보강했다. 읽지 못한 파일 경로, 오류 코드 문구와 OS 코드, 직전 저장본의 경로와 상태, 버전 변환 전 사본의 경로, 직전 저장본이 유효할 때의 수동 절차 문구를 보인다(사용자 결정 D3).
- **`build`의 `tsc` 검사**: `tsc -p tsconfig.node.json --noEmit && tsc -p tsconfig.web.json --noEmit && electron-vite build`로 `01-tech-stack.md`를 고쳤고 루트 `tsconfig.json`은 에디터용 빈 설정이다(FE-001).
- **`node:path` 허용 범위**: `src/main/**`에서 `node:path`만 허용하고 경로 합치기는 `path.join`을 쓴다. 자체 `joinPath`는 없다(FE-010).
- **개발 서버와 CSP**: CSP 메타 태그는 production build에만 주입한다(FE-008).
- **종류·우선순위 필터의 선택 방식**: 명세 v4(AC-047)가 정했다. 목록마다 `전체` 항목이 있고 처음 선택이며, 한 목록에서 하나만 선택하고, 선택된 항목을 다시 눌러도 해제되지 않으며, 두 목록은 AND다.
- **시험 파일과 Task의 어긋남**: TC-010은 `card-rules.test.ts`, TC-036은 `data-file-repository.test.ts`로 옮겨 시험 파일과 소유 Task를 맞췄다(DC-005).

### 기록 (사용자가 정하지 않은 설계 리뷰 제안)

아래는 설계 리뷰가 제안했지만 사용자가 정하지 않아 하지 않은 것이다. 하지 않은 이유를 남겨 둔다.

- **규모 축소**(FE-009, RK-011): 파일을 합쳐 파일 수를 115개 안팎으로 줄이는 안, browser 시험을 smoke 묶음으로 줄이는 안. 단일 책임과 300줄 한도를 지키는 현재 구조를 유지했다.
- **필드 길이 상한**(RK-006): 제목·설명·메모·기록의 길이 상한을 두지 않았다. 아주 큰 붙여넣기가 이후 모든 저장을 느리게 할 수 있고, 성능 기준(CAND-002)이 없어 측정 시험도 만들지 않았다.
- **Task 번호 정리**(FE-012): T-003을 없애고 번호를 당기는 안은 하지 않았다. 기존 번호를 바꾸지 않았다.

### Electron 업그레이드 절차

Electron 45의 지원 종료일은 2027-04-27이다(endoflife.date). 앱은 오프라인이라 자동 업데이트가 없으므로 보안 수정을 받으려면 사용자가 새 메이저로 직접 올려 다시 빌드해야 한다. 순서는 다음과 같다. (1) `app/package.json`에서 electron을 새 메이저의 핀 버전으로 올린다(함께 맞춰야 하는 electron-builder, electron-vite, @playwright/test의 호환 버전도 확인해 핀으로 올린다). (2) `package-lock.json`을 갱신하고 `npm ci`를 돌린다. (3) `npm run lint`, `npm run build`, test 명령, `npm run test:e2e`, `npm run package`를 차례로 돌려 모두 통과시킨다. (4) 수동 시험 TC-131~TC-134, TC-155를 다시 확인한다(특히 TC-132의 넷로그). 하나라도 실패하면 핀과 lock을 되돌리고 원인을 보고한다. 앱 안에서 업데이트를 확인하는 코드는 NFR-001 때문에 두지 않는다.

수동 확인 5개(TC-131 흑백 구분과 첫 화면 색, TC-132 실제 네트워크 차단과 넷로그, TC-133 패키징 글꼴·라이선스 포함, TC-134 저장 중 실제 강제 종료, TC-155 포장 퓨즈)는 어느 Task에도 속하지 않고 구현 뒤 인수 확인에서 사람이 한다.

## 검증 기록

- 설계 결함 수정(BI-003, 구현 중 보고): 저장 단계에서 `sync`를 따로 두지 않고 `write_temp`에 포함해 `write_temp`, `verify`, `backup`, `replace` 네 단계로 고쳤다(`writeFileSynced` 한 호출이 쓰기와 fsync를 함께 한다). 저장 단계 수만 5에서 4로 바뀌었고 파일·컴포넌트·Wave·TC·인터페이스 수는 그대로다.
