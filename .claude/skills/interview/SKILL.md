# /interview — 적응형 요구사항 인터뷰

아이디어를 받아 **질문 → 답변 → 다음 질문 결정**을 반복하며 요구사항을 끌어낸다.
최종 산출물은 `interview.md` — `prd-writer`의 필수 입력이 된다.

정해진 객관식 질문을 순서대로 던지는 방식과 달리, 답에 따라 질문이 바뀌고 모호한 답은 되묻는다.

**스킬은 프로젝트 로컬, 산출물도 프로젝트 로컬.**

---

## 트리거

```
/interview <아이디어> [--depth light|standard|deep] [--from <경로>] [--resume] [--no-web]
```

| 플래그 | 기본값 | 용도 |
|--------|--------|------|
| `--depth` | `standard` | 라운드 상한과 다룰 토픽 수 |
| `--from` | (자동 감지) | 사전 자료 경로. 기본은 `docs/02-research/` 의 조사 결과 |
| `--resume` | false | `interview-log.md`에서 이어하기 |
| `--no-web` | false | WebSearch/WebFetch 비활성화 |

---

## 산출물 경로

```
<프로젝트>/docs/01-interview/
├── interview-log.md   # 라운드별 Q&A 원문 + 커버리지 (매 라운드 갱신, 이어하기 기준)
└── interview.md       # 최종 정리본 (핵심 산출물)
```

산출물의 섹션 이름, ID 형식, 태그는 `contracts/artifact-contract.md`를 따른다. 충돌하면 계약이 우선한다.

## 워크플로우

### Step 0 — 입력 파싱 + 준비

```
주체: Claude (직접 수행)

입력 파싱:
  - 아이디어 텍스트, 플래그 추출
  - 아이디어가 비어 있으면 채팅으로 "어떤 서비스/문제를 생각 중인지 한두 문장으로 알려주세요" 질문

산출물 경로: base = ./docs/01-interview/   (mkdir -p {base})

기존 결과 감지:
  IF {base}/interview-log.md 존재 OR --resume:
    AskUserQuestion("이전 인터뷰 기록이 있습니다. 어떻게 진행할까요?", [
      "이어서 진행 (로그의 커버리지 복원)",
      "보강 (interview.md 유지 + 추가 질문)",
      "처음부터 (기존 파일은 .bak으로 보존)",
      "취소"
    ])

보강 규칙 (기존 interview.md 가 이미 `확정`인데 다시 호출됐을 때 — 조사 결과 반영, PRD 수정 요청 등):
  - 보강으로 결정·요구사항 후보·가정·열린 질문이 하나라도 바뀌면 interview.md 에 슬쩍 덧붙이지 않는다.
    새 라운드를 로그에 R 블록으로 기록하고(Step 2-3), 정리본을 고칠 때 머리의 `> 라운드:`를 올리고
    `> 상태:`를 `초안`으로 되돌린다. `> 확정 라운드:` 줄은 이전 값 그대로 둔다 (게이트 VAL-12 가 이 차이로 재확정 누락을 잡는다).
  - 그 뒤 **Step 3-2 요약과 3-3 확정 질문을 반드시 다시 거친다.** 허브가 호출했어도 생략하지 않는다
    (허브 호출로 생략하는 것은 Step 4 의 완료 배너뿐이다).
  - 3-2 요약 맨 위에 "이번 보강에서 바뀐 것"을 쓴다: 추가·바뀐 D/RC/A/Q 의 ID 와 한 줄 내용. 사용자가 이 줄만 봐도 무엇이 바뀌었는지 알 수 있어야 한다.
  - 사용자가 질문에 답한 것과 최종 정리본을 확정하는 것은 다르다. 답을 받았다고 정리본이 확정된 것이 아니다.
  - 아무것도 바뀌지 않았으면(새로 알게 된 사실이 기록에 영향 없음) 라운드를 올리지 않고 재확정도 필요 없다.

사전 자료 감지 (--from 또는 자동):
  Glob(docs/02-research/*.md)
  IF 존재 → Read → "사전 자료 {N}건 감지: {목록}. 이미 정해진 내용은 다시 묻지 않고 확인만 합니다."
```

### Step 1 — 커버리지 지도 작성

```
주체: Claude (직접 수행)

Read(.claude/skills/interview/references/question-bank.md)

아이디어 + 사전 자료를 토픽별로 분해해 커버리지 표를 만든다.
토픽 정의와 depth별 대상은 question-bank.md 의 "토픽 목록" 참조.

상태: 미확인 / 부분 / 확정
  - 사전 자료에서 채운 항목은 "부분" + [사전자료] 태그 (사용자 확인 전에는 "확정" 금지)
  - 아이디어 문장에서 읽히는 항목도 "부분" + [추론] 태그

→ Write({base}/interview-log.md)  (헤더 + 커버리지 표)

사용자에게 시작 안내 (3줄 이내):
  - 지금 파악한 것 한 줄 요약
  - 앞으로 {N}라운드 안팎, 한 번에 질문 1~2개
  - "충분해요"라고 하면 언제든 정리 단계로 넘어간다
```

### Step 2 — 인터뷰 루프

```
주체: Claude + 사용자 (대화형, 라운드 반복)

depth별 상한:
  light:    4라운드 / 필수 토픽 T1~T6
  standard: 8라운드 / T1~T10
  deep:    14라운드 / T1~T12

[2-1] 다음 질문 선택
  우선순위:
    1. 필수 토픽 중 "미확인"
    2. T1·T3·T4 중 "부분" (이 셋은 반드시 확정해야 다음 단계가 의미 있다)
    3. 직전 답변이 만든 새 모호함·모순
    4. 나머지 토픽 중 영향이 큰 순
  질문 규칙은 question-bank.md 의 "질문 규칙" 따름. 핵심:
    - 한 번에 1~2개, 질문 이유를 한 줄로 덧붙인다
    - 선택지로 갈리는 질문 → AskUserQuestion
    - 사례·서술이 필요한 질문 → 채팅으로 직접 묻고 다음 메시지를 답으로 받는다
    - 사전 자료에 있는 내용 → "조사 결과에는 ~로 되어 있는데 맞나요?" 식 확인 질문

[2-2] 답변 처리
  답을 받으면 즉시 분류해 기록한다:
    D-n  결정 (사용자가 명시적으로 정한 것)
    RC-n 요구사항 후보 (기능/품질 요구, 우선순위 후보 포함)
    SC-n 시나리오 (상황 → 행동 → 기대 결과, 예외)
    A-n  가정 (확인되지 않았지만 진행을 위해 둔 것)
    C-n  제약
    Q-n  열린 질문 (답이 없거나 사용자도 모르는 것)
  번호는 3자리(D-001, RC-001 …)이고 한 번 쓴 번호는 재사용하지 않는다.
  출처 태그를 반드시 붙인다:
    [U] 사용자가 직접 말함 (원문 짧게 인용)
    [S] Claude가 제안하고 사용자가 수락함
    [I] Claude 추론, 사용자 미확인  ← interview.md 에서 따로 모아 보여준다
  모호어(빠르게, 쉽게, 많은, 가끔, 등)가 나오면 수치·예시로 한 번 되묻는다.
  같은 항목을 두 번 물어도 모호하면 A-n 으로 기록하고 넘어간다. 붙잡지 않는다.

[2-3] 로그 갱신 (매 라운드, 필수)
  Edit({base}/interview-log.md) — 라운드 블록 추가 + 커버리지 표 갱신
    ## R{n} — {토픽}
    Q: {질문}
    A: {답변 요지 / 핵심 인용}
    → 기록: D-001, RC-003, A-002
  대화가 압축·중단돼도 로그만으로 이어할 수 있어야 한다.

[2-4] 주기적 확인 (3~4라운드마다)
  지금까지의 결정·요구사항 후보를 5줄 이내로 요약해 보여주고
  AskUserQuestion("잘못 이해한 부분이 있나요?", ["맞아요, 계속", "수정할 게 있어요"])

[2-5] 분기 처리
  (a) 발산 필요 — 사용자가 "아직 없다/모르겠다"를 같은 토픽에서 2회, 또는 T3·T4에서 선택지가 안 보일 때
      → Step 2b 로 이동 후 복귀
  (b) 사실 조사 필요 — 경쟁 서비스 현황, 시장 규모, 규제, 기술 가능성 등
      → 작은 건: WebSearch 1~2회로 확인해 사용자에게 보여 주고, 수락하면 [S]로 기록 (출처는 기록의 비고에 적는다. standard 이상, --no-web 아니면)
      → 큰 건: 인터뷰를 멈추지 않고 "조사 필요 항목"에 기록, 마지막에 /pre-research 권장
  (c) 사용자 이탈 신호("충분해요", "일단 여기까지") → Step 3 으로

[2-6] 종료 조건 (하나라도 충족)
  - 해당 depth의 필수 토픽이 모두 "부분" 이상이고 T1·T3·T4 가 "확정"
  - 사용자가 종료 의사를 밝힘
  - 라운드 상한 도달 → 남은 "미확인/부분" 항목은 Q-n 으로 이관

종료 조건을 충족하면 Step 2c 로 간다 (사용자가 "충분해요"라고 해도 2c 는 한 번 거친다. 건너뛰겠다고 하면 2c-4).
```

### Step 2b — 대안 발산 (필요할 때만)

```
주체: Claude + 사용자

목적: 사용자가 답을 못 정할 때 "빈 칸 채우기"가 아니라 "고르기"로 바꿔준다.

1. 막힌 토픽을 한 줄로 규정 ("핵심 시나리오를 정하지 못함")
2. 서로 방향이 다른 대안 3~4개를 카드로 제시
     각 카드: 이름 / 한 줄 설명 / 잘 맞는 사용자 / 대가(단점)
   - 대안은 사전 자료·조사에서 근거를 가져온다. 근거 없는 대안은 [I] 태그
   - 내 선호를 심지 않는다. 추천이 있으면 하나만, 이유와 함께 표시
3. AskUserQuestion — 선택 / 조합 / 모두 기각(이유 입력)
4. 결과를 D-n 으로 기록, 기각한 대안과 이유도 함께 기록 (나중에 같은 논의 반복 방지)
5. Step 2 로 복귀
```

### Step 2c — 실현 요건 점검

```
주체: Claude + 사용자 (대화형, 최대 1~2라운드)

목적: 단순한 아이디어는 사용자가 모르거나 말하지 않은 채로 빈 곳이 남는다. 그 빈 곳을 가정(A-n)으로 흘려보내지 않고,
      모델이 "이 아이디어를 실현하려면 필요해 보이는 것"을 먼저 제안하고 사용자가 수락·기각·보류만 하게 한다.
원칙: 사용자가 말하지 않은 것을 확정하지 않는다. 제안은 사용자가 수락해야 RC [S] 가 된다.

범위와 상한:
  light: 영향 큰 항목만, 1라운드 / standard·deep: 전 분류, 최대 2라운드
  라운드 상한이 있다 ("붙잡지 않는다"와 같은 원칙). 끝나도 남은 것은 Q-n 으로 간다.

[2c-1] 도출
  입력: 지금까지의 D / RC / SC / A / C, 사전 자료(조사)
  Read(.claude/skills/interview/references/question-bank.md) 의 "실현 요건 도출 기준"으로
  이미 나온 RC·SC 가 전제하는데 아직 항목이 없는 것을 찾는다.
    분류: 사용자·권한 / 데이터·운영 / 외부 연동 / 규제·개인정보 / 비기능 / 운영·지원
  이미 D·RC·Q 로 다룬 것은 다시 제안하지 않는다.
  "설계 영향이 큰 질문" 표의 주제(계정, 기기 간 이어 쓰기, 오프라인, 규모, 개인정보, 운영) 중 아직 안 물은 것은 여기서 선택지로 묻는다.

[2c-2] 제시와 처리
  "말씀하지 않으셨지만 이 아이디어를 실현하려면 필요해 보이는 것입니다" 라고 먼저 밝힌다.
  한 번에 4개 안팎, 영향 큰 순서. 항목마다 한 줄씩: 내용 / 왜 필요한가 / 안 하면 어떻게 되나 / 근거(사전 자료 출처 또는 추론)
  항목마다 AskUserQuestion — 수락 / 기각(이유 입력) / 보류
  - 가격·법규·규제·외부 서비스의 조건처럼 사실로 단정할 수 있는 내용은 단정하지 않는다.
    "~로 알려져 있는데 확인이 필요합니다"로 쓰고, 작은 건은 2-5(b) 의 검색 1~2회로 확인해 근거와 함께 보인다. 큰 건은 `조사 필요 항목`에 남긴다.
  - 추천이 있으면 하나만 이유와 함께 표시한다. 선호를 심지 않는다.

[2c-3] 기록 (사라지는 항목이 없게 연결 ID 를 남긴다)
  수락 → RC-n (출처 [S])        기각 → D-n (이유를 '기각한 대안과 사유'에)        보류 → Q-n
  사용자가 다루지 않기로 한 영향 보통 이하 항목 → '확인되지 않은 추론'에 [I]
  Edit({base}/interview-log.md) — "R{n} — 실현 요건 점검" 블록 (템플릿 참조). 커버리지 표는 건드리지 않는다.
  interview.md 의 `## 실현 요건 점검` 표 (항목 | 분류 | 처리 | 연결) 에 옮긴다. 게이트 VAL-19 가 처리 값과 연결 ID 를 본다.

[2c-4] 건너뛰기·해당 없음
  제안할 것이 없거나 사용자가 건너뛰겠다고 하면 섹션을 비워 두지 말고 "해당 없음: {사유}"라고 쓴다 (예: "해당 없음: 사용자가 건너뜀").
  건너뛴 경우 A-n 으로 흘러간 빈 곳은 그대로 가정으로 남으므로 3-2 요약에 "실현 요건 점검을 건너뜀"을 한 줄 적는다.
```

### Step 3 — 정리 + 확인

```
주체: Claude + 사용자 (반복 루프)

Read(.claude/skills/interview/references/interview-template.md)

[3-1] interview.md 작성
  로그의 D/RC/SC/A/C/Q 를 템플릿 구조로 정리한다. Step 2c 의 결과는 `## 실현 요건 점검` 섹션(템플릿의 `충돌` 다음)에 옮긴다.
```

## 에러 처리

| 시나리오 | 처리 |
|---------|------|
| 사전 자료 Read 실패 | 해당 자료 스킵 + 경고, 아이디어만으로 진행 |
| WebSearch 실패 / `--no-web` | 조사 없이 진행, 사실 확인이 필요한 항목은 Q-n 으로 기록 |
| 사용자 답이 질문과 무관 | 답을 버리지 말고 기록하되, 같은 질문을 표현을 바꿔 한 번 더 |
| 답이 서로 모순 | 즉시 두 답을 나란히 보여주고 어느 쪽이 맞는지 확인 |
| 로그 Edit 실패 | 즉시 중단하고 에러 표시 (로그가 이어하기의 기준이므로 무시하고 진행하지 않는다) |
| "취소" 선택 | 즉시 종료, 기존 파일 보존 |

**공통 원칙**: 어떤 실패든 기존 산출물을 삭제하지 않는다. 사용자가 말하지 않은 것을 [U]로 기록하지 않는다.

## 다른 스킬과의 관계 (옵셔널 참조)

```
아이디어 / 기존 자료 ─▶ interview ─▶ interview.md ─▶ prd-writer ─▶ prd.md ─▶ spec-planner ─▶ spec.md ─▶ design-architect
                          ▲   │
                          └── pre-research ◀── 조사 필요 항목 (허브가 연결)

- interview는 docs/02-research/*.md 를 옵셔널 입력으로 받는다(없어도 동작).
- interview.md 는 prd-writer 의 필수 입력이다. prd-writer 는 `> 상태: 확정` 일 때만 작성한다.
- pre-research 는 interview.md 의 `조사 필요 항목`을 읽어 조사의 초점으로 삼는다.
```
