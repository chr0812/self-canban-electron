> 작성일: 2026-11-03

## 배경

### 문제 정의
본인 1명이 개발 버그와 일반 할 일을 한곳에서 관리할 도구가 지금 없다. 그래서 직접 만들려 한다. 해결 대상은 개발 버그와 일반 할 일 모두다. (인터뷰 문제와 배경 R1, R2) [인터뷰: RC-001], [인터뷰: RC-003]

### 현재 대안과 한계
- 지금 쓰는 도구는 없다고 이해했다. 기존 도구가 맞지 않아서인지 아직 안 써서인지는 확인하지 못했다. 사용자가 직접 써 본 도구와 불편한 점도 듣지 못했다. 기존 도구의 한계는 확정하지 않고 열린 질문으로 남긴다. [인터뷰: A-001]
- 조사에서 확인한 개인용 칸반 도구의 부류: 범용 SaaS(Trello, Todoist 등), 셀프호스팅 서버형(Planka, Vikunja), 오프라인 개인용 앱(Kanri). 대부분 벤더·비교 사이트 글이라 순위와 평가는 참고용이다. [조사: 01-overview.md, S2, S3]

### 시장 맥락
- 조사는 light 깊이이고, 외부 자료의 신뢰도는 대부분 낮음(LOW)이다. [조사: 05-sources.md]
- 개인용 칸반의 기본 원칙으로 "일을 시각화한다 / 진행 중인 일의 수를 제한한다(WIP 제한)"가 소개된다. 사용자는 WIP 제한을 요구하지 않았다. [조사: 01-overview.md, S1]
- Todoist는 보드 뷰를 제공하지만 캘린더 뷰는 유료라는 서술이 있다. [조사: 01-overview.md, S2]
- Kanri는 오프라인으로 동작하는 무료 오픈소스 개인용 칸반 앱이라는 서술이 있다. 독립 리뷰는 찾지 못했다. [조사: 01-overview.md, S3]

## 비전 및 목표

### 비전
개발 버그와 할 일을 한곳의 보드에 모아, 등록부터 해결까지 상태별 보드와 캘린더로 관리하는 내 PC용 1인 칸반보드. [인터뷰: D-007]

### 핵심 목표
| 목표 | 측정 기준 | 근거 |
|------|----------|------|
| 해야 할 일(개발 버그, 일반 할 일)을 전부 보드에 모은다 | 해야 할 일이 메모나 머릿속에 없고 전부 보드에 있는 상태. 수치 기준은 정해지지 않음 | [인터뷰: D-007] |
| 카드의 진행 상황을 상태별 보드와 캘린더로 본다 | 카드를 상태별로 한 화면에서 볼 수 있고, 날짜 기준 캘린더로도 볼 수 있다 | [인터뷰: RC-003], [인터뷰: RC-010] |

### 성공 기준
해야 할 일이 메모나 머릿속에 없고 전부 보드에 모여 있는 상태 (인터뷰 D-007). 수치 기준은 정해지지 않았다. 열린 질문에 올렸다.

## 타겟 사용자

| 사용자군 | 핵심 니즈 | 사용 맥락 | 근거 |
|---------|----------|----------|------|
| 본인 1명 (주 사용자) | 개발 버그와 할 일을 한곳에서 상태별·날짜별로 관리한다 | 내 PC 한 대에서 사용하고, 인터넷 없이도 동작해야 한다 | [인터뷰: RC-011], [인터뷰: D-004] |

### 비사용자 (명시적 제외)
- 부 사용자: 없음. 계정·공유 기능을 두지 않는다. [인터뷰: C-001]
- 여러 기기나 휴대폰에서 쓰는 사용자: 여러 기기 동기화와 모바일은 하지 않는다. [인터뷰: D-004]

## 핵심 기능

| ID | 우선순위 | 기능 | 설명 | 근거 |
|----|---------|------|------|------|
| PF-001 | Must | 카드 만들기 | 보드에서 관리할 개발 버그나 할 일 한 건을 카드로 만든다 | [인터뷰: RC-001] |
| PF-002 | Must | 카드 상태 변경 | 카드의 상태를 할 일, 진행 중, 완료 순서로 바꾼다. 상태는 3단계로 고정한다 | [인터뷰: RC-002] |
| PF-003 | Must | 상태별 보드 | 카드를 상태별로 모아 한 화면에서 본다 | [인터뷰: RC-003] |
| PF-004 | Must | 마감일 | 카드에 마감일을 적는다. 캘린더 보기의 전제다 | [인터뷰: RC-006] |
| PF-005 | Must | 캘린더 보기 | 카드를 날짜 기준 캘린더로도 본다 | [인터뷰: RC-010] |
| PF-006 | Must | 로컬 저장·오프라인 동작 | 데이터를 내 PC에 저장하고 인터넷 없이 동작한다 | [인터뷰: RC-011] |
| PF-007 | Should | 카드 종류 | 카드에 종류(개발 버그/할 일)를 표시한다. 같은 카드에 종류 표시만 다르게 한다 | [인터뷰: RC-004] |
| PF-008 | Should | 카드 항목 | 카드에 상세 설명, 우선순위, 추가 메모를 적는다 | [인터뷰: RC-005], [인터뷰: RC-007], [인터뷰: RC-008] |
| PF-009 | Should | 카드 진행 기록 | 카드별로 진행 단계마다 추가 이슈와 검토사항 기록을 남기고 변경 과정을 추적한다. 직접 적는 기록인지 자동 이력인지는 미정이다 | [인터뷰: RC-009] |
| PF-010 | Should | 완료 카드 보관 | 완료한 카드를 보관(숨김)하고 보관한 카드를 다시 찾아본다 | [인터뷰: RC-012] |
| PF-011 | Should | 카드 수정·삭제 | 카드를 수정하고 삭제한다 | [인터뷰: RC-013] |
| PF-012 | Should | 마감 알림 | 마감이 임박했거나 지난 카드를 알려 준다. 알림 방식은 미정이다 | [인터뷰: RC-014] |
| PF-013 | Should | 검색·필터 | 카드를 검색하고 종류·우선순위로 거른다 | [인터뷰: RC-015] |

- 우선순위는 인터뷰의 후보를 따랐다. 사용자가 직접 필수로 꼽은 것은 카드 생성, 상태 변경, 캘린더 보기다 (PF-001, PF-002, PF-005). 상태별 보드, 마감일, 로컬 저장은 이 세 가지가 성립하려면 필요해 인터뷰가 필수 후보로 둔 것이다 (PF-003, PF-004, PF-006). 나머지는 사용자가 순위를 말하지 않았다.
- 우선순위는 PRD 승인으로 확정된다.

## 범위 및 제약

### MVP 범위
- 필수(Must): PF-001, PF-002, PF-003, PF-004, PF-005, PF-006
- 1차 버전에서 일부러 제외하는 항목은 없다 (인터뷰 D-006). 따라서 Should 기능(PF-007 ~ PF-013)은 제외된 것이 아니다. MVP에 모두 넣을지와 구현 순서는 열린 질문에 두었다.

### 제외 범위
- 인터뷰의 요구사항 후보(RC) 중 제외로 처리한 것은 없다.
- 여러 기기 동기화, 모바일: 내 PC 한 대에서만 쓰기로 했다. [인터뷰: D-004]
- 계정·공유 기능과 서버 저장: 서버와 계정 없이 PC에 저장하기로 했다. [인터뷰: C-001], [인터뷰: D-005]
- 데이터 백업·내보내기: 사용자가 기각했다. 이유는 말하지 않았고, PC 고장 시 데이터 유실은 감수하기로 했다. [인터뷰: D-009]
- 사용자가 칸을 추가·수정하는 기능: 칸은 할 일, 진행 중, 완료 세 개로 고정한다. [인터뷰: D-001]
- 종류별로 입력 항목이 다른 카드: 개발 버그와 할 일은 같은 카드에 종류 표시만 다르게 한다. [인터뷰: D-002]

### 기술·기타 제약
- 내 PC 한 대에서만 쓰고, 서버와 계정 없이 PC에 저장하며, 인터넷 없이 동작한다. [인터뷰: C-001]
- 칸 이름은 할 일, 진행 중, 완료 세 개로 고정한다는 가정이다. [인터뷰: A-002]
- 웹과 Electron 중 어느 쪽으로 만들지는 정해지지 않았다. 설계 단계에서 후보를 비교해 사용자가 결정한다. 열린 질문에 있다.

## 열린 질문

- 지금 어떻게 관리하고 있고, 왜 기존 도구를 쓰지 않는가? (기존 도구가 맞지 않아서인지 아직 안 써서인지 확인하지 못했다.) — 영향 낮음, 사용자가 답한다. (출처: 인터뷰 Q-001)
- 카드 기록의 "히스토리 추적"은 직접 적는 기록인가, 상태 변경 등을 자동으로 남기는 이력인가? PF-009의 범위가 달라진다. — 설계 전 결정 필요, 영향 높음. (출처: 인터뷰 Q-002)
- 마감 알림은 보드 화면 안의 표시인가, PC 알림(시스템 알림)인가? PF-012의 범위가 달라진다. "임박"의 기준도 정해지지 않았다. — 설계 전 결정 필요, 영향 중간. (출처: 인터뷰 Q-004)
- 웹으로 만들지 Electron으로 만들지? PRD에서 정하지 않는다. — 설계 단계의 기술 스택 비교에서 사용자가 결정, 영향 높음. 조사에서는 Tauri와 PWA도 언급되지만 비교 자료가 얕아 후보로 확정하지 않았다. (출처: 인터뷰 Q-005, [조사: 01-overview.md, S4])
- 조사 필요: 웹(브라우저 저장소)과 Electron 중 어느 쪽이 "내 PC 한 대, 로컬 저장, 오프라인, 마감 알림"에 맞는가. 브라우저 로컬 저장소의 용량·보존 한도와 PC 알림 지원 범위를 확인해야 한다. 기존 조사는 PWA와 로컬 저장을 다루지 않았고, Electron 최신 버전 표기가 출처마다 달라 공식 릴리스를 직접 확인해야 한다. — 설계 단계. (출처: 인터뷰 조사 필요 항목, [조사: 01-overview.md, S4])
- 예외·엣지 케이스는 확인하지 못했다 (시나리오 SC-001의 예외가 "미확인"). — 명세 전. (출처: 인터뷰 SC-001, 커버리지 T7)
- 사용 빈도는 확인하지 못했다. — 낮음. (출처: 인터뷰 커버리지 T2)
- 성공 기준의 수치 기준이 정해지지 않았다. 필요한지 사용자가 정해야 한다. — 명세 전. (출처: 인터뷰 커버리지 T5)
- Should 기능(PF-007 ~ PF-013)을 1차 버전에 모두 넣는가, 일부를 뒤로 미루는가? 구현 순서를 정할 기준이 필요하다. — PRD 승인 때 사용자 확인. (출처: 신규)
- 조사 발견 후보: 진행 중인 일의 수를 제한하는 WIP 제한. 개인용 칸반의 기본 원칙으로 소개되지만 사용자는 요구하지 않았다. 사용자 확인 전에는 기능이 아니다. ([조사: 01-overview.md, S1])
