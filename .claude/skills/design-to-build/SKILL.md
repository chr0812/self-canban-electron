# /design-to-build — 승인된 설계 → 구현 → 시험 → 인수 승인

기획 허브(`/discover-to-design`)가 설계 승인까지 맡고, 이 허브가 그 뒤를 맡는다. 단계 사이는 파일로만 넘어간다.
허브는 **순서와 안전장치**를 맡는다. 완료 판정은 스크립트(`build.js verify`, 게이트), 코드는 개발자 에이전트, 결정은 사용자가 한다.

---

## 하는 일 / 하지 않는 일

| 한다 | 하지 않는다 |
|------|-------------|
| Task 마다 `build-developer`에게 맡기고 진행을 `build.js start/handoff/pause`로 기록한다 | 직접 코드를 쓴다 (작은 수정도 개발자에게 맡긴다) |
| `build.js verify`로 완료를 판정한다 (구현 기록 블록은 verify 가 쓴다) | 에이전트의 "완료" 주장을 믿거나, 검증 전에 기록을 쓴다 |
| 구현 중 보고를 분류해 `build.js issue`로 기록하고 사용자 결정을 받는다 | **승인된 설계·명세를 직접 고친다**, 보고 문서를 손으로 고친다 |
| Wave 가 끝날 때 요약을 보여 주고 다음 진행을 묻는다 | 묻지 않고 커밋·푸시한다 |
| 사람이 확인할 시나리오를 사용자와 확인한다 | 사용자 대신 확인자가 되거나 인수 승인을 한다 |
| 하네스 결함을 보고하고 사용자 결정을 받는다 | 사용자 승인 없이 하네스 파일(`scripts/`, `.claude/`, `contracts/`)을 고친다 |

## 트리거

```
/design-to-build            # 상태를 보고 이어간다
/design-to-build --status   # 진행 상태만 보여 주고 끝낸다
```

## 항상 지키는 규칙

1. **매번 상태부터 확인한다** (Step 0). 어디까지 왔는지 추측하지 않는다. 진행은 `docs/_gate/build.json`에 있으므로 새 세션에서도 이어진다.
2. **완료는 `node scripts/build.js verify <T-NNN>`이 `통과`라고 할 때뿐이다.** `08-tasks.md` 체크박스는 설계 승인 대상이라 바꾸지 않는다.
3. **설계·명세는 이 허브도, 에이전트도 고치지 않는다.** 고쳐야 하면 사용자 결정 뒤에 해당 단계의 스킬(수정 모드)로 고치고 다시 승인받는다 ("보고 처리").
4. **기록 문서는 명령으로만 고친다**: 보고는 `build.js issue add|set`, 구현 기록은 `verify`가 쓴다. 정규식 치환·손 편집으로 고치지 않는다 (게이트 `BLD-07`이 손상을 잡는다).
5. **메인 컨텍스트를 아낀다.** 지시서는 개발자가 `build.js brief`로 직접 받는다. 지시서·로그 전문을 사용자에게 붙여 넣지 않는다.
6. **사용자 결정 지점에서는 멈춘다**: 구현 시작, 환경 부족, 설계·명세·하네스 결함, 반복 실패, Wave 끝, 구현 차이 정리, 사람 확인 시나리오, 인수 승인.
7. **턴을 끝내도 되는 곳**은 ① 사용자 응답 대기 ② 인수 승인 완료 ③ 실패 보고뿐이다. 에이전트 호출과 검증 뒤에는 Step 0 으로 돌아간다.
8. 화면 형식은 `.claude/skills/design-to-build/references/screens.md`를 따른다.

## Step 0 — 상태 확인 (매번)

```
node scripts/gate.js status --json
node scripts/build.js next --json      # 구현 단계일 때 (line 이 지금 할 일)
```

| `gate.js status`의 `next.action` | 이동 |
|------|------|
| 기획 단계의 행동 (`start_interview` ~ 설계 승인 관련) | "기획이 끝나지 않았다. `/discover-to-design`으로 이어간다"고 알리고 끝 |
| `start_build` | Step 1 |
| `continue_build` | Step 2 |
| `fix` (stage `build`) | `BLD-06` 설계 승인 무효 → "보고 처리"의 설계 변경 / `BLD-03` 미해결 결함 → "보고 처리" / `BLD-07` 기록 문서 손상 → 사용자에게 알리고 손상 부분만 복구(내용·사용자 결정은 그대로) / `BLD-08` 하네스 변경 미보고 → "하네스 결함" / `BLD-04` → 해당 Task 를 다시 `verify` |
| `start_test` | Step 3 (구현 마무리) → Step 4 |
| `fix` (stage `test`) | Step 4. `TST-09`(시험 뒤 코드 변경)는 `test-run`부터 다시 |
| `request_approval` (stage `test`) | Step 5 |
| `reapprove` / `recheck_stale` (stage `test`) | 인수 뒤 보고서·명세·작업 목록·시험 기록이 바뀌었다 → 변경을 보여 주고 Step 4 부터 |
| `done` | "인수 승인까지 끝났다"를 알리고 끝 |

## Step 1 — 구현 시작

1. **시작 확인** (구현 시작 화면): Task 수·Wave 수, 시험 시나리오 수(자동 실행 위치별 / 사람 확인), 코드 위치 `app/`, 설치·테스트 명령, 화면 시험이 어떤 브라우저로 headless 로 도는지. `AskUserQuestion`: **시작** / **나중에**.
   - 기획 대화가 길었던 세션이면 "새 세션에서 `/design-to-build`로 시작해도 이어진다"고 한 줄 덧붙인다.
2. `node scripts/build.js init` — 구현 기록·보고 문서, `app/`, 하네스 지문(`docs/_gate/harness.json`, 없을 때만)을 만든다.
3. `node scripts/build.js doctor --json` (환경 화면).
   - 모두 있음 → Step 2.
   - `cli`가 없음 → 구현을 검증할 수 없다. 설치를 안내하고 멈춘다.
   - 그 밖의 실행 위치(`browser`·`device`)가 없음 → `AskUserQuestion`: **설치 후 다시 확인** / **이대로 진행** (그 실행 위치의 Task 검증과 시험이 `실행 불가`가 된다. 인수 전에 설치하거나 사유와 함께 면제한다).
4. **Wave 진행 방식**을 묻는다: **Wave 마다 멈춤** / **인수 시험 전까지 계속** (문제가 생기면 그때 멈춘다). git 저장소이면 Wave 끝에 커밋 여부도 함께 묻는다.

## Step 2 — Task 루프

```
node scripts/build.js next --json
```

처리 순서는 `next`가 정한다 (`line`):

| 상태 | 할 일 |
|------|------|
| `ok: false` | 설계 승인이 무효다. 바뀐 내용을 보여 주고 "보고 처리 — 설계를 고친 뒤" |
| `verifying` 있음 | 다른 검증이 진행 중이다. 끝나기를 기다린다 |
| `handoff` (검증 대기) | 2-2 검증 |
| `paused` (중단) | 2-1 을 **재개**로: 기록된 파일과 `app/`의 현재 상태를 확인하게 하고 이어서 개발한다 |
| `developing` 만 남음 | 그 개발자가 돌아오기를 기다린다 (같은 세션에서 끊겼다면 `pause`로 기록한 뒤 재개) |
| `runnable` | 2-1 개발. 여럿을 함께 하려면 아래 "조건부 병렬" |
| `finished` | Step 3 |
| `runnable`이 비고 `blocked` 있음 | 미해결 보고로 멈춘 것이다 → "보고 처리" |

`stale`(재검증 필요) Task 는 먼저 개발자 없이 `verify`만 다시 돌린다. 통과하면 끝(구현 기록에 재검증 줄이 붙는다). 실패하면 개발자를 부른다.

### 2-1. 개발

```
node scripts/build.js start <T-NNN>
Agent(subagent_type: "build-developer", prompt: "
  Task: <T-NNN>. 먼저 `node scripts/build.js brief <T-NNN>`을 실행해 출력 전체를 지시서로 삼는다 (지시서 판과 근거 문서 판을 결과에 적는다).
  호출: design-to-build. 코드는 app/ 안에만. 설계·명세·하네스 파일은 고치지 않는다. 완료 기록은 하지 않는다.
  {병렬이면: 함께 개발 중인 Task 와 그 파일 — 건드리지 않는다. 포트를 쓰는 명령(화면 시험 등)은 돌리지 않는다}
  {재개면: 중단 사유와 그때까지의 파일. 이미 만든 것을 다시 쓰지 않고 이어서}
  {이전 검증 실패면: 기록 경로와 문제 목록}
  {재검증(stale)이면: 근거가 바뀌었다. 바뀐 시나리오·명세·설계에 맞게 고친다}")
```

- 개발자가 돌아오면 `node scripts/build.js handoff <T-NNN> --files <바꾼 파일> --note "<설계와 다른 점, 없으면 없음>"`.
- 결과의 `결정 필요`가 있으면 → "보고 처리" (검증보다 먼저).
- 개발자가 의존성 목록(패키지 파일)을 바꿨으면 검증에 `--install`을 붙인다.
- **사용량 제한·세션 종료로 끊기면** `node scripts/build.js pause <T-NNN> --reason "<사유>" --files <남은 파일>`. 중단은 실패 횟수에 넣지 않는다.

### 조건부 병렬

- `next`의 `parallel`에 있는 Task 만 함께 시작한다 (의존 관계가 없고 파일이 겹치지 않는다). `start`가 다시 검사하고 어긋나면 거부한다.
- 함께 개발하는 동안 **검증하지 않는다**. 모든 개발자가 돌아와 `handoff`한 뒤에 하나씩 검증한다 (`verify`는 개발 중인 Task 가 있으면 거부한다). 검증 중에는 개발을 시작하지 않는다 (`start`가 거부한다).
- 병렬 개발자에게는 포트·결과 파일을 쓰는 명령(화면 시험, 결과 파일이 있는 시험)을 돌리지 말라고 한다. 확인은 검증이 한다.
- 이 조건을 지킬 수 없으면 (파일 지정이 없는 Task, 공유 설정 파일 등) 순차로 한다.

### 2-2. 검증

```
node scripts/build.js verify <T-NNN> [--install] --json
```

| 결과 | 처리 |
|------|------|
| `done` | 끝. 구현 기록 블록은 `verify`가 handoff 기록(바꾼 파일·설계와 다른 점)으로 썼다. 설계와 다른 점이 있으면 `build.js issue add --type 구현 차이 ...`. 설계 문서끼리 모순이라 생긴 차이면 `설계 결함`으로 올린다 ("보고 처리") |
| `failed`, 시도 1회 | 같은 개발자 역할을 다시 부른다 (`start` → 개발 → `handoff`). 프롬프트에 기록 경로와 문제 목록 |
| `failed`, 시도 2회 이상 | 멈추고 반복 실패 화면. `AskUserQuestion`: **한 번 더** / **설계 문제로 보고** / **하네스 문제로 보고** / **멈춤** |
| `conflict` | **코드 실패가 아니다.** 환경 충돌(포트 사용 중 등) 또는 검증 중 파일 변경. 원인을 알린다: 남은 서버는 띄운 역할이 기록한 PID 만 종료한다 (다른 프로세스를 임의로 끄지 않는다). 개발 중인 작업이 없는지 확인한 뒤 다시 검증한다 |
| `unavailable` | 도구가 없다. 환경 화면을 보여 주고 설치를 안내한 뒤 멈춘다 |

### 2-3. Wave 끝

방금 검증한 Task 의 Wave 가 모두 `완료`가 되면 Wave 요약 화면. Step 1 에서 **Wave 마다 멈춤**을 골랐으면 `AskUserQuestion`: **계속** / **커밋하고 계속** / **인수 시험 전까지 계속** / **멈춤**. **인수 시험 전까지 계속**이면 요약만 보여 주고 이어 간다.
- 커밋은 사용자가 고를 때만 한다. 메시지: `구현 Wave {n}: T-001~T-005` (프로젝트의 커밋 규칙이 있으면 따른다). 푸시하지 않는다.
- 커밋 전에 `git status`로 대상을 보여 준다. 생성 폴더(`node_modules`, 시험 결과물 등)가 보이면 `.gitignore`가 빠진 것이다 — 커밋하지 말고 사용자에게 알린다.

그 뒤 Step 0 으로 돌아간다.

## 보고 처리 (구현·시험 중 `결정 필요`)

에이전트의 유형 제안을 참고해 허브가 분류한다. 기준은 계약의 "구현 중 보고"이고, **애매하면 설계 결함**으로 본다. 기록은 항상 명령으로:

```
node scripts/build.js issue add --type <유형> --found <T-NNN> --scope "<영향 Task 또는 전체>" --text "<내용 한 줄>"
node scripts/build.js issue set <BI-NNN> --state <상태> --action "<처리: 바뀐 문서와 곳 / 사용자 결정 내용>"
```

| 유형 | 판단 | 처리 |
|------|------|------|
| 코드 결함 | 설계는 맞고 코드가 틀렸다 | 개발자를 다시 부른다. 2회 실패 뒤에 올라온 것이면 기록한다 |
| 구현 차이 | 그 Task 안에서 끝나는 차이 (설계가 정하지 않은 세부를 정함 등) | 기록(미해결). 진행한다. 정리는 Step 3 |
| 설계 결함 | 다른 Task·설계 문서에 영향, **설계 문서끼리 모순** | 기록(미해결, 영향 Task — 바닥 문서면 `전체`). 설계 결함 화면, `AskUserQuestion`: **설계를 고친다 (권장)** / **영향 없는 Task 먼저** / **멈춤** |
| 명세 결함 | 요구가 모순·검증 불가 | 기록(미해결). 기획 허브의 "명세가 바뀌는 결정"과 같은 선택지 |
| 하네스 결함 | 하네스(검증 스크립트·지침)가 틀려 올바른 결과를 잘못 판정 | 아래 "하네스 결함" |

- **설계를 고친다**: `Skill(design-architect, args: "수정 모드: {결함 내용과 영향}. 승인된 설계를 고친다. 바뀐 문서를 목록으로.")` → `node scripts/gate.js design` → 설계 승인 화면(바뀐 점 중심) → 사용자 승인 → `approve design`. 그 뒤 `issue set BI-NNN --state 해결 --action "설계 수정 ({바뀐 문서}), {날짜} 재승인"`. 근거가 바뀐 완료 Task 는 `next`가 재검증 대상으로 보여 준다.
- **명세를 고친다**: 명세 → 설계 순으로 수정·재승인한다 (기획 허브의 "변경 요청 처리"). 그 뒤 위와 같다.
- 사용자가 고르지 않은 수정을 하지 않는다. 설계·명세 결함은 `기록`으로 닫을 수 없다 (`BLD-03`). 이미 내려진 사용자 결정(기록으로 둔 것 등)을 소급해 바꾸지 않는다.

### 하네스 결함

1. 증거와 함께 보고한다 (예: 시험은 통과했는데 결과 파일 판정이 틀림). `issue add --type 하네스 결함` (미해결 — 영향 Task 가 멈춘다).
2. `AskUserQuestion`: **이 프로젝트에서 임시로 고친다** / **멈추고 하네스 원본에서 고친다** / **우회 없이 멈춤**.
3. 임시로 고쳤으면 `issue set BI-NNN --state "임시 패치" --action "<바꾼 하네스 파일과 이유, 사용자 승인>"`. 게이트는 하네스 지문과 다른 파일을 이 보고로 확인하고(`BLD-08`), 원본 반영 전까지 경고(`BLD-09`)를 남긴다.
4. 하네스 원본에 반영되면 `--state "원본 반영" --action "<하네스 판>"`.

---

## Step 3 — 구현 마무리

1. `node scripts/gate.js build` — 오류가 있으면 Step 0 표대로 처리한다.
2. `BLD-05`(정리 안 된 구현 차이)가 있으면 구현 차이 화면. `AskUserQuestion`: **설계를 정정한다** (모아서 한 번에 고치고 재승인 → 근거가 바뀐 Task 재검증) / **기록으로 둔다** (각각 `issue set --state 기록 --action "<사유>"`).
3. `BLD-09`(원본 미반영 하네스 패치)가 있으면 인수 승인 화면에 드러낸다.
4. 커밋 여부를 묻는다 (Wave 끝과 같다).

## Step 4 — 시험

1. `Agent(subagent_type: "build-tester", prompt: "호출: design-to-build. 시험 계획의 모든 시나리오를 확인하고 docs/07-test/test-report.md 초안을 쓴다.")`
2. 시험자의 `결정 필요` → "보고 처리". 코드 결함이면 해당 Task 를 `start` → 개발 → `handoff` → `verify` 한 뒤 시험자를 다시 부른다.
3. **사람이 확인할 시나리오** (`manual`): 질문 창이 대화 본문을 가리므로 **질문 안에** 실행 명령·주소, 절차 요약, 기대 결과, 수동 사유(대상 브라우저·기기), 보고서의 "사람 확인 목록" 경로를 넣는다 (사람 확인 화면). `AskUserQuestion` (한 번에 최대 4개): **확인했고 통과** / **실패** (내용을 받는다) / **지금은 확인 못함** (사유를 받아 면제).
   - 결과를 `시나리오 결과` 표에 행으로 더하고 **요약의 집계 줄도 함께 고친다** (`TST-10`). `확인자`는 사용자 이름 (인수 승인 `--by`와 같은 이름을 묻는다).
   - 실패면 "보고 처리".
4. **화면 시험을 직접 보고 싶다**고 하면: 명령 표의 화면 시험 명령에 headed 옵션(예: Playwright `--headed`, `--ui`)을 붙여 사용자가 직접 실행하는 방법을 안내한다. 이 실행은 증거가 아니다 (증거는 `test-run`의 결과 파일과 `_evidence/`).
5. **실행 불가** 자동 시나리오: `AskUserQuestion`: **도구 설치 후 다시 실행** / **사유와 함께 면제**.
6. `node scripts/gate.js test` — 통과할 때까지 위를 반복한다. 코드를 고쳤으면 `test-run`부터 다시 (`TST-09`).

## Step 5 — 인수 승인

인수 승인 화면: 시나리오 결과(통과·면제), 자동 판정 방식(TC 별 / 전체 실행), 인수 기준 확인 현황, 면제된 것과 사유(`TST-07` 경고 포함), 설계와 다른 점(기록으로 둔 구현 차이), 하네스 임시 패치, 남은 보고, 증거 경로.
`AskUserQuestion`: **인수 승인** / **수정 요청**. 승인하면 `node scripts/gate.js approve test --by <이름>`. 인수 뒤에 시험을 다시 돌리거나 코드가 바뀌면 인수 승인이 낡는다.
