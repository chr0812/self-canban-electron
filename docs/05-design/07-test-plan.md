명세의 인수 기준(AC-001~AC-048)과 비기능 요구사항(NFR-001~NFR-004)을 시험 시나리오(TC)로 펼친 문서다. 시험의 기준은 명세이고 코드가 아니다. 화면 문구는 `04-ui-spec.md`의 문구를 관찰 지점으로 썼다. 문구가 바뀌면 시험을 함께 고친다. 명세가 정하지 않은 것(결정 필요)은 기대 결과로 만들지 않았고 아래 `결정 필요`에 남겼다.

## 시험 전략

- 단위 (`cli`, Vitest 5.1.0, `test` 명령): 화면과 파일 시스템 없이 확인할 수 있는 순수 규칙. 마감 지남 판정, 날짜 검증, 입력 검증, 카드 규칙(상태 변경·보관·삭제), 진행 기록, 설정, 검색·필터 조건, 보드·캘린더 표시 모델, 입력칸 값 변환, 문구 표, 채널 목록. 화면 상태 reducer와 변경 실행기(가짜 `KanbanApi` 주입). 시계와 아이디는 고정 값으로 주입한다.
- 통합 (`cli`, Vitest, `test` 명령): 저장 모듈을 `FileSystemPort` 대역(`memory-fs`, `fault-fs`)으로 돌린다. 저장 네 단계, 단계별 실패 주입, 강제 종료 흉내(해당 호출에서 중단하고 새 저장소로 다시 열기), 이전 버전(버전 1) 파일 읽기, 읽기 실패 분류와 읽기 실패 상태의 쓰기 호출 0건, 저장소 흐름. `node-file-system`만 실제 임시 폴더에서 확인한다(Windows의 이름 바꾸기 덮어쓰기 포함). IPC 핸들러는 electron 모듈 대역으로 확인한다.
- E2E (`browser`, Playwright 1.64.1 `_electron`, `test:e2e` 명령): 실제 Electron 창을 임시 `--user-data-dir`로 띄워 화면 흐름, 앱 재시작 뒤 유지, 프로세스 강제 종료(저장 완료 표시 뒤) 뒤 재실행, 요청 관찰(NFR-001), 앱 번들 폴더 밖 `file:` 요청 차단, 빌드 결과의 CSP, 모달, 캘린더, 끌어다 놓기(보드의 칸 이동과 캘린더 칩 끌기), 창 크기별 캘린더 스크롤(메인 프로세스에서 `BrowserWindow`의 크기를 읽고 바꾼다), 밝기 전환, 색 외 구분 요소의 존재, 칸 이동·보관·삭제·칩 끌기의 저장 실패 시 화면 불변을 확인한다. 브라우저가 그리는 날짜 선택 달력 팝업은 DOM 밖이라 시험 코드가 조작할 수 없으므로, 달력이 입력칸에 넣는 값과 같은 경로(날짜 입력칸의 값 설정)와 키보드 직접 입력으로 확인한다(TC-165). 창이 뜨는 시험이라 헤드리스가 아니다.
- 수동 (`manual`): 사람의 지각 판단이나 실제 환경 조작이 필요해 자동화가 부담인 5건만 둔다. 흑백 구분과 첫 화면 색(NFR-004), 실제 네트워크 차단과 넷로그(NFR-001), 패키징 앱의 글꼴·라이선스 포함(NFR-001), 저장 중 실제 강제 종료(NFR-002), 포장한 앱의 퓨즈(NFR-001). 포장 퓨즈를 뺀 수동 TC는 같은 요구의 측정 가능한 부분을 자동 TC로 나누었다. 대상 환경은 Windows 11, Electron 45.2.1(`npm run package`의 `app/release/` 실행 폴더).
- 실행 위치는 `01-tech-stack.md`의 `시험 환경` 표에 있는 `cli`, `browser`만 쓴다. `device`는 쓰지 않는다.
- 시험 데이터: 모두 가짜 카드(실제 개인정보 없음). `cli`는 `tests/cli/support`의 빌더와 고정 파일(`fixtures/data-v1.json`, `data-v2.json`)을 쓴다. `browser`는 시험마다 빈 임시 데이터 폴더를 쓰고 이전 데이터를 재사용하지 않는다. 앱 시계를 바꾸는 코드가 없으므로 마감 지남 관련 `browser` 시험은 실행하는 날의 실제 날짜에서 마감일을 계산해 넣는다. 캘린더 끌기와 5주 달 시험(TC-165~TC-172)은 실행일과 무관하게 2026년 11월(일요일 시작, 30일이라 5행, 12월 1~5일이 뒤쪽 이 달 밖 칸)로 고정한다. 앱은 오늘이 든 달로 열리므로 시험 도우미가 `‹`/`›`를 눌러 기간 제목이 `2026년 11월`이 될 때까지 이동한다. 5주인 달은 2026-10, 2026-11, 2026-12, 2027-02, 2027-03이고 2027-01은 6주다(`new Date(y, m-1, 1).getDay()`와 말일로 확인한 값). 처음 실행 기본 판은 밝은 판이다(ASM-017).
- 시험 파일 경로는 앱 루트 `app/` 기준이다. 시험 이름(testcase)에는 TC ID를 넣는다.
- `browser` 공통 전제: 빌드된 앱(`out/main/index.js`), 시험마다 새 임시 데이터 폴더, 저장 파일 없음(처음 실행). 시드가 필요한 TC는 `launch-app.ts` 도우미로 구동 전에 저장 파일(현재 버전)을 넣는다. 아래 TC의 `전제`에서 "공통"은 이를 뜻한다.

### TC-143 상태 reducer는 요청 수, 실패한 요청, 카드 목록, 조건을 규칙대로 바꾼다

- 수준: 단위
- 실행: cli
- 시험 파일: tests/cli/state/reducers.test.ts
- 전제: 할 일 카드와 완료 카드가 든 보드 목록, 보관된 카드가 든 보관함 목록의 `DataState`, 빈 조건의 `UiState`, `saved`인 `SaveState`.
- 절차: 초기 `DataState`를 만들어 판을 읽는다. `saveReducer`에 요청 시작 두 번, 성공 한 번, 실패 한 번(다시 보낼 요청 한 건 포함)을 차례로 적용한다. `dataReducer`에 상태를 바꾼 카드로 교체, 카드 삭제, 보관(보드 목록에서 빼고 보관함 목록에 넣기)을 적용한다. `uiReducer`에 검색어와 종류 조건을 적용하고 모두 지운다.
- 기대 결과: 초기 `DataState`의 판은 기본 판 `light`다(AC-038). `saveReducer`는 시작마다 진행 중 요청 수가 늘고 요청 수가 0이 되었을 때 마지막 요청이 성공이면 `saved`, 실패면 `failed`와 다시 보낼 요청 한 건을 갖는다. `dataReducer`는 교체한 카드만 바뀌고 삭제한 카드가 사라지며 보관한 카드가 보드 목록에서 빠져 보관함 목록에 들어간다. 입력 상태 객체는 바뀌지 않는다(새 객체). `uiReducer`는 조건을 담고 모두 지우면 빈 조건이 된다.

### TC-165 마감일은 날짜 입력칸에서 달력으로 고르거나 직접 입력해 저장하고 칩을 열어 고칠 수도 있다

### TC-131 색을 제거한 흑백 화면에서도 카드 종류와 마감 지남이 구분되고 첫 화면이 선택한 판의 색으로 열린다

- 수준: E2E
- 실행: manual

- 전제: 개발 버그 카드, 할 일 카드, 마감이 지난 카드(어제 마감, 미완료), 마감일이 오늘인 카드가 모두 있는 데이터. Windows 설정에서 색 필터를 켜고 `회색조`를 고른다.

- 전제: 포장한 실행 폴더. 퓨즈 설정(`electronFuses`)이 electron-builder 26.18.0에서 지원되는 경우에만 해당한다. 구현 Task가 지원 여부를 보고하고, 지원되지 않아 설정하지 않았다면 이 TC는 `면제`로 사유를 적는다.
- 절차: (1) 환경 변수 `ELECTRON_RUN_AS_NODE=1`을 설정하고 실행 파일을 실행한다. (2) 환경 변수 `NODE_OPTIONS=--inspect=9230`을 설정하고 실행한다. (3) 인자 `--inspect=9229`로 실행한다. 각 실행 중 `netstat -ano`로 9229, 9230 포트가 열렸는지 본다.
- 기대 결과: (1)은 Node 모드로 동작하지 않고 앱 창이 일반 앱처럼 뜬다. (2)와 (3)에서 디버그 포트가 열리지 않는다.

시험 환경에서 확인하지 못한 점 (설계 단계에서 실행해 보지 않았다):

- 쓰기 실패 유도: TC-114~TC-116, TC-151, TC-173은 유효한 저장 파일을 두고 같은 폴더에 `kanban-data.json.bak` 이름의 폴더를 만들어 저장의 직전본 복사 단계를 실패시키는 방식을 가정한다(임시 파일 이름에 프로세스 아이디가 붙어 `.tmp` 이름의 폴더를 미리 만들어 둘 수 없다). Windows 11에서 이것이 실제로 쓰기 실패가 되는지 확인하지 못했다. 안 되면 해당 TC를 `cli`의 `FileSystemPort` 대역(`tests/cli/state/change-runner.test.ts`의 가짜 `KanbanApi`와 TC-051, TC-053)으로 옮기고, 화면 쪽 확인은 별도 방법을 정해야 한다.
- 읽기 실패 유도: TC-153은 `kanban-data.json` 자리에 폴더를 만들어 읽기 오류 `EISDIR`를 만든다. Windows에서 실제 코드가 `EISDIR`인지 확인하지 못했다.
- 창 닫기 직전의 요청: TC-152는 창이 닫히는 순간 main에 아직 도착하지 않은 요청이 없다고 가정한다. 설계 단계에서 확인하지 못했다.
- 앱 번들 폴더 접두사: TC-154는 Windows의 `file:` 주소 대소문자·퍼센트 인코딩이 접두사 비교와 어긋나지 않는다고 가정한다(첫 구동에서 확인).
- Chromium 프로세스 자체의 요청: `browser` 시험은 앱 창의 요청만 본다. 수동 TC-132의 넷로그 확인이 이를 본다.
- 포장 퓨즈: TC-155는 electron-builder 26.18.0이 `electronFuses` 설정을 지원한다고 가정한다(확인하지 못함).
- preload의 판 적기: 첫 화면 색 깜빡임은 수동 TC-131이 본다.
- 오프라인 전환: TC-127은 Electron 창의 컨텍스트에서 `setOffline(true)`가 동작한다고 가정한다. 동작하지 않으면 TC-125의 외부 요청 0건 관찰과 TC-132(수동)로 AC-012를 확인한다.
- 데이터 폴더 지정: `browser` 시험은 `--user-data-dir`이 앱의 데이터 폴더(`userData`)에 반영된다고 가정한다(`05-architecture.md`가 구현에서 확인하기로 한 사항).
- 프로세스 강제 종료: TC-111은 `browser` 시험 코드에서 Electron 프로세스를 직접 종료할 수 있다고 가정한다.
- 날짜 선택 달력 팝업: TC-165는 브라우저가 그리는 달력 팝업을 열고 누를 수 없어(팝업이 DOM 밖) 달력이 칸에 넣는 값과 같은 경로(값 설정)와 키보드 직접 입력으로 대신 확인한다. 팝업이 실제로 열리고 날짜를 고르는 모습은 자동 시험이 확인하지 못하며 인수 단계의 사람 확인이 맡는다(수동 TC로 늘리지 않았다).
- 날짜 입력칸의 입력하다 만 값: TC-080, TC-165는 키보드로 월·일·연 칸을 입력해 `validity.badInput`을 만들 수 있다고 가정한다. 한국어 로케일에서 칸의 입력 순서(연·월·일 또는 월·일·연)는 확인하지 못했다. 시험은 칸을 `Tab` 순서가 아니라 입력 가능한 구획 이름(월, 일, 연)으로 찾아야 한다.
- HTML5 끌어다 놓기: TC-166~TC-170, TC-173은 Playwright의 끌기(`dragTo`)가 Electron 창에서 칩의 `draggable` 끌기를 일으킨다고 가정한다(보드의 TC-071과 같은 가정, 확인하지 못함).
- 창 크기 조작과 화면 크기: TC-171, TC-172는 `_electron` 앱의 메인 프로세스에서 `BrowserWindow.getSize()`/`setSize()`를 쓸 수 있다고 가정하고, 시험 PC 화면이 920px 높이 창을 담을 수 있다고 가정한다(작업 표시줄을 뺀 작업 영역이 더 낮으면 창 크기가 달라질 수 있음).
- Playwright의 Electron 지원은 공식 문서가 "experimental"로 표시한다(`01-tech-stack.md`). 버전을 올릴 때 `browser` TC 전체를 다시 돌려야 한다.
