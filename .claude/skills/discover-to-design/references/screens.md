# 화면 형식

허브가 사용자에게 보여 주는 화면의 형식. 원칙: **ID보다 내용을 먼저**, 선택지마다 **무엇이 달라지는지**, 길면 줄인다.

---

## 상태 화면

`node scripts/gate.js status` 결과를 그대로 쓰되, 단계마다 한 줄로 요약한다.

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
진행 상태
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
인터뷰  ✔ 확정
PRD     ✔ 승인됨 (홍길동, 10-21)
명세    ▶ 승인 대기
설계    · 아직 없음
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
다음: 명세 승인을 요청합니다.
```

- `stale` / `blockedBy`가 있으면 해당 줄 끝에 "상류 변경됨 — 재검토 필요"를 덧붙이고, `staleBy`가 있으면 바뀐 상류 문서를 함께 적는다.

## 단계 전환 안내

각 단계가 끝날 때마다 쓴다. 사용자가 다음에 무슨 일이 일어나는지 모르는 채로 결정하지 않게 한다.

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{단계} 완료 — {핵심 수치 한 줄}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
방금 한 일: {두세 줄}
다음 단계: {단계 이름} — {그 단계가 하는 일 한 줄}
```

그다음 `AskUserQuestion`으로 선택지를 준다. 각 선택지의 `description`에 **선택하면 일어나는 일**을 쓴다.

## 조사 결정 화면

인터뷰 확정 직후, 조사를 아직 하지 않았을 때.

```
인터뷰가 확정됐습니다. PRD를 쓰기 전에 조사를 할지 정해 주세요.

조사가 하는 일: 인터뷰로는 알 수 없는 외부 사실(경쟁 서비스, 관련 규제, 시장 동향)을
웹에서 찾아 출처와 함께 정리합니다. 결과는 PRD의 '배경·시장 맥락'에 쓰입니다.

인터뷰에서 조사가 필요하다고 표시한 항목: {N}건
  - {항목 한 줄씩, 최대 3개}
```

선택지:
- **조사 후 PRD** — 위 항목을 조사하고 결과를 인터뷰에 반영한 뒤 PRD를 씁니다 (몇 분 더 걸립니다). `조사 필요 항목`이 있으면 권장합니다.
- **조사 없이 PRD** — 바로 PRD를 씁니다. 시장 맥락은 "조사 없음"이 되고, 확인할 것은 열린 질문으로 남습니다.
- **인터뷰 더** — 아직 정리할 것이 있을 때.

## PRD 승인 화면

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PRD 확인: {프로젝트명}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
비전: {1줄}
타겟: {사용자군}

핵심 기능 {N}개
  꼭 필요(Must) {a}: {기능 이름들}
  있으면 좋음(Should) {b}: {기능 이름들}
  나중에(Could) {c}: {기능 이름들}
이번에 하지 않는 것 {d}: {항목들}

아직 정해지지 않은 질문 {e}개 (설계 전에 확인): {가장 중요한 2~3개}
인터뷰 후보 {n}건 모두 처리됨 (기능 {a+b+c} / 제외 {d} / 질문 {q})
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

선택지: **승인** (이 PRD가 고정되고 명세의 기준이 됩니다) / **수정 요청** / **인터뷰 보강 후 다시** / **조사 후 다시**.

## 명세 승인 화면

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
명세 확인: {프로젝트명}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
기능 요구사항 {N}개 (P0 {a} / P1 {b} / P2 {c}), 비기능 {n}개, 화면 {s}개, 유스케이스 {u}개
이번에 하지 않는 것: {항목들}
인수 기준 {n}개 — 승인하면 이 기준이 "다 됐다"의 판단 기준이 되고, 설계의 시험이 이것을 확인합니다
  - {P0 FR의 인수 기준 한 줄씩, 최대 10개. 넘치면 "외 {k}개 (spec.md 기능 요구사항)"}
리뷰: {리뷰어 수}명 검토, 자동 반영 {x}건, 사용자 결정 {y}건, 기록만 {z}건
우선순위가 PRD와 달라진 것: {없음 | 목록}

⚠ 설계에 영향이 큰 가정 {h}개 (아직 확인하지 않음)
  - {가정 한 줄} — 틀리면: {다시 만들어야 하는 설계 문서·이유}
  - …
  승인하면 이 가정이 설계의 전제가 됩니다. 이것은 사실인지 조사한 결과가 아니라, 설계가 무엇에 기대는지입니다.
그 밖의 가정: 보통 {m}개 · 낮음 {l}개
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

선택지 (영향 높음 가정이 있을 때): **높음 가정을 하나씩 확인한 뒤 승인** / **수정 요청**. 확인 질문은 가정마다 **이 가정으로 설계한다** / **가정을 바꾼다**(명세를 고친 뒤 다시 이 화면으로) / **보류**(열린 질문으로 남긴다). 확인한 가정의 ID는 승인 비고에 남긴다.
영향 높음 가정이 없으면: **승인** / **가정을 먼저 확인** / **수정 요청**.

## 기술 스택 후보 화면

설계 단계에서 기술 스택 문서(`01-tech-stack.md`의 `후보 비교`)가 나온 직후. 사용자가 후보를 보고 고른다. 전문용어 대신 **이 선택이 무엇을 쉽게/어렵게 하는가**(운영 부담, 비용, 배우는 시간, 나중에 바꾸기)로 쓴다.

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
기술 스택 후보
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
A (추천)  {기술 이름과 한 줄}
          쉬워지는 것: {…}
          어려워지는 것(대가): {…}
B         {기술 이름과 한 줄}
          쉬워지는 것: {…}
          어려워지는 것(대가): {…}
C         …
추천 이유: {한 줄}
확인할 것: {명세에 없어 후보 판단이 갈리는 제약 — 팀이 아는 기술, 배포 환경, 운영할 사람, 기존 시스템. 후보와 엮어 구체적으로. 없으면 줄 생략}
  예) A는 서버를 직접 운영해야 하고 B는 필요 없습니다. 운영할 사람이 있나요?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

선택지: **추천안으로** (A로 진행) / **다른 후보로** (고른 후보로 기술 스택 문서를 다시 씁니다) / **조건을 더해 다시** (말씀하신 조건으로 다시 조사합니다).

- 추천은 하나만, 이유와 함께 보인다. 사용자가 고르기 전에 "이게 좋다"고 유도하지 않는다.
- 다시 만들기는 합쳐서 1회다. 사용자가 후보를 고르면 `선택` 칸이 바뀐 문서를 게이트(`VAL-21`)로 다시 검사한다.
- 설계 승인 뒤에 기술 스택을 바꾸면 모든 설계 문서를 다시 만들어야 한다. 이 화면이 그 전에 고를 마지막 기회임을 한 줄로 알린다.

## 시안 선택 화면

설계 단계에서 화면 설계 전에, 서로 다른 디자인 방향의 시안을 보고 고르게 한다. 두 부분이다.

### 취향 질문 (시안을 만들기 전, 2문항, 건너뛰기 허용)

```
화면 느낌을 정하려고 합니다. 시안을 만들기 전에 두 가지만 여쭤볼게요.
  1. 좋아하는 서비스나 사이트가 있나요? (이름이나 링크, 1~3개) 반대로 싫어하는 느낌은요?
     이유: 시안이 모두 비슷해지는 것을 막으려고요
  2. 이 서비스를 쓸 때 어떤 분위기이길 바라세요?  (차분 / 활기 / 전문적 / 친근 / 직접 입력)
```

선택지에 **건너뛰기**를 둔다. 건너뛰면 타겟 사용자와 서비스 성격만으로 방향을 고른다.

### 시안 제시와 선택

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
화면 시안 {n}가지
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
V-A {이름}  {한 줄}
  잘 맞는 곳: {…}      대가: {…}
  핵심 선택: {글꼴 이름 · 색 · 모서리 · 밀도}
  파일: docs/05-design/_variants/V-A-SCR-001.svg
V-B {이름} …
V-C {이름} …
서로 다른 점: {쌍마다 다른 축 개수와 가장 눈에 띄는 차이 한 줄}
참고: 글꼴이 기기에 없으면 시안은 대체 글꼴로 보입니다. 파일은 브라우저로 열어 보세요.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

선택지: **V-A로** / **V-B로** / **V-C로** / **조합** (예: A의 색 + B의 구성. 어느 부분을 가져올지 묻는다) / **전부 기각** (이유를 받는다) / **취향을 바꿔 다시**.

- 시안을 보기 전에 "이게 좋다"고 유도하지 않는다. 추천은 쓰지 않는다. 역할이 추천을 올렸으면 하나만 이유와 함께 덧붙인다.
- 기각한 시안과 사유도 기록한다 (`choice.md`). 같은 논의를 반복하지 않기 위해서다.
- 시안을 다시 만드는 것은 "전부 기각"과 "취향을 바꿔 다시"를 합쳐 1회다. 그 뒤에는 남은 시안에서 고른다.
- 고른 뒤 화면 설계(`04-ui-spec.md`)와 와이어프레임은 선택된 방향을 따른다. 설계 승인 뒤에 방향을 바꾸면 화면 설계와 와이어프레임을 다시 만들어야 한다고 한 줄로 알린다.
